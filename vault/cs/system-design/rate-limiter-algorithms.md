```
fixed window: burst на стыке окон

окно 1 [12:00:00 – 12:00:59]     окно 2 [12:01:00 – 12:01:59]
        счётчик: K ✓                     счётчик: K ✓
   ────────────────────●●●●●│●●●●●────────────────────
                       └──── 2K за пару секунд ────┘
                       оба счётчика в норме, лимит фактически пробит ✗
```

**TL;DR:** одно семейство алгоритмов, один размен: точность «в любом окне» стоит памяти (события), приближение стоит O(1) (счётчики). Точные: log/ring O(K), buckets O(W). Приблизительные: fixed window, sliding counter, token bucket — O(1).

## Семейство

| алгоритм | память/ключ | точный? | суть |
|---|---|---|---|
| sliding window log (deque) | O(M в окне) | да | все таймстемпы окна, evict старых, `len > K?` |
| ring K таймстемпов | O(K) | да | только K последних; `t − t[−K] < W?` → [[sliding-window-rate-check]] |
| bucket counters | O(W) | да, при целых t | счётчик на секунду + скользящая сумма |
| fixed window | O(1) | **нет** | счётчик на календарное окно; пропускает burst на стыке (см. схему) |
| sliding window counter | O(1) | нет | интерполяция двух соседних fixed-окон; точнее, но приближение |
| token bucket | O(1) | нет (другой инвариант) | ведро токенов, refill rate; ограничивает **среднюю** скорость + допускает burst до ёмкости ведра |

## Выбор

- Точный «в любом окне» → ring O(K) vs buckets O(W): брать что меньше. Лимит «10^6 за минуту» → 60 счётчиков, не 10^6 таймстемпов
- Enforcement на проде (API gateway, per-key limits, миллионы ключей) → обычно приблизительные: O(1)/ключ, граничная неточность приемлема
- Token bucket ≠ sliding window по семантике: он *разрешает* burst (ёмкость ведра) и держит среднюю скорость — часто это и есть желаемая политика (QoS)

## Когда точное кольцо не годится

- поток не отсортирован / несколько источников с clock skew → watermark-буферизация
- K и W оба огромны, ключей миллионы → память; переходить на приближение
- запросы с весами (cost ≠ 1) → «K назад» не работает, нужен deque с суммой весов
- распределённый лимит без шардинга по ключу → централизованное состояние (Redis) или приближённая синхронизация счётчиков

## Не только в API

- **Сети (QoS):** token bucket — стандарт policing/shaping трафика на роутерах (RFC 2697)
- **ОС:** cgroups блокируют CPU/IO той же механикой ведра токенов (`cpu.cfs_quota`)
- **Kafka:** client quotas — скользящие окна на producer/consumer byte-rate
- **Брокеры/очереди:** consumer prefetch limit — тот же инвариант «не больше K необработанных»

Общее везде: инвариант «объём за окно ≤ лимит», и один размен — точность окна vs память на состояние.
