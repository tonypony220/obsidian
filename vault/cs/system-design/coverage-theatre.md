```
     ┌──── тест ────┐
     │  expect(X)   │  ◀───┐
     └──────────────┘      │  один источник:
                           │  моё представление
                           │  об X
     ┌── компонент ─┐      │
     │  call(X)     │  ◀───┘
     └──────────────┘

     оба зелёные ↔ оба неправильные
     (баг в одном и в другом одинаковый)
```

**TL;DR:** Тест зелёный, но целевой класс бага не ловит. Три способа получить: (1) мокать то, что должен проверить; (2) списать assertion с кода вместо независимого источника; (3) заготовленная fixture расходится с реальным контрактом. Симптом: 100% coverage, но регрессии проходят.

## Три формы театра

### 1. Мок глушит проверяемое

Тест мокает именно тот слой, поведение которого проверяется. Реальный код не запускается — сверка идёт между моком и ожиданием, оба из одного источника (автора теста).

```ts
// пример из [[rtl-wiring-test]]
vi.mock('~/lib/cart/add-to-cart')
render(<AddToCart listingId="abc" />)
click('Add')
expect(mockPerformAdd).toHaveBeenCalledWith({ listingId: 'abc', qty: 1 })
```

Real `performAdd` — с сериализацией, `fetch`, обработкой ошибок — не тронут. Проверилось только «моя копия ожидания совпала с моей же копией вызова». Если и в компоненте, и в `expect` опечатка `id` вместо `listingId` — оба зелёные, баг летит.

**Fix:** мокать самую внешнюю границу за проверяемым слоем (сеть, DB), не сам проверяемый слой.

### 2. Тест списан с кода (mirror test)

Assertion пишется по имплементации: та же формула, те же константы, тот же алгоритм. Тест копирует любую логическую ошибку кода → баг + тест сходятся.

```ts
// код: расчёт налога
export const calcTax = (subtotal: number) => subtotal * 0.13   // должно быть 0.10

// тест
it('calcTax', () => {
  const subtotal = 100
  expect(calcTax(subtotal)).toBe(subtotal * 0.13)   // ← копия формулы, оба сходятся
})
```

**Fix:** expected value — **константа** из независимого источника (спека, документация, ручной расчёт), не формула из кода:

```ts
it('calcTax: 13% Ontario HST', () => {
  expect(calcTax(100)).toBe(13)   // ← если ставка изменится, тест поймёт
})
```

Если ставка в требованиях меняется на 10 — этот тест краснеет и напоминает; предыдущий бесшумно принимает `subtotal * 0.10`.

### 3. Fixture расходится с реальным контрактом

MSW/stub отдаёт заранее заготовленный ответ, но форма ответа не совпадает с тем, что реально шлёт сервер. Клиент подстраивается под мок → тест зелёный → на проде undefined.

```ts
server.use(
  http.get('/api/cart', () => HttpResponse.json({
    status: 'ok',              // реальный сервер шлёт { success: true }
    data: [{ id: 1 }],          // реальный шлёт { items: [...] }
  }))
)
```

Клиент читает `res.data[0].id` → работает в тесте, `undefined.id` на проде.

**Fix:** fixture генерится из **общего источника** — типов shared-пакета, contract-generated stubs, или integration test бьёт реальный сервер. См. также [[round-trip-test]] — если canonical type и schema имеют общий источник, drift невозможен by construction.

## Симптомы

- «100% coverage, а на проде баг» — типично при форме №1 (моки глушат проверяемое)
- «Изменил код — все тесты зелёные, ничего не заметил» — типично при форме №2 (mirror)
- «Локально всё работает, на проде undefined» — типично при форме №3 (fixture drift)
- «Тест написали одновременно с кодом, оба под одного человека» — риск №2
- «В тесте больше `vi.mock` чем реального импорта» — риск №1

## Reframe-вопросы

Перед тем как принять тест, спроси:

1. **Что реально исполняется?** Если между `render/act` и `expect` мокается ВСЁ — тест не проверяет ничего кроме своих же моков.
2. **Откуда expected value?** Формула-копия из кода → mirror test. Константа из спеки/документации/ручного расчёта → OK.
3. **Если внести баг в код — тест покраснеет?** Если нет — тест не связан с кодом. Формально это проверяют [mutation testing](https://en.wikipedia.org/wiki/Mutation_testing) фреймворки (`stryker`, `pitest`), в ручном режиме — просто попробовать бросить дефект.
4. **Fixture совпадает с реальным ответом сервера?** Если не сгенерена из общего источника — надо интеграционный тест или round-trip.

## Отношение к другим слоям

Coverage theatre — **противоположность** дисциплине [[baseline-positive-boundary-reject]]: positive-тесты должны строить body реальным builder'ом, negative — рукописный мусор. Как только positive пишется руками с копией из кода — начинается театр формы №2.

[[fitness-function]] — структурный тест инвариантов репо (grep/AST) — почти не подвержен театру, потому что assert идёт по факту существования кода, а не по логике.

[[walking-skeleton]] и [[round-trip-test]] — оба режут реальный код (никаких моков внутри) и потому дают истинное покрытие своего среза; их существование прямо снижает риск театра.

## Не только в тестах

Театр — общая форма «инструмент показывает зелёный, реальность красная». Встречается везде, где detector и target имеют общий источник:

| Домен | Форма театра |
|---|---|
| Health-check endpoint | endpoint возвращает 200 без проверки реальной работоспособности сервиса |
| Monitoring | alert написан по метрике, которая производится тем же кодом, что и падает |
| Type-check | `as any` в критичном месте — компилятор счастлив, prod падает |
| Backup verification | резервная копия делается, но никто не проверял восстановление |
| ML evaluation | модель тестируется на данных, на которых училась (data leakage) |
| Static analysis | линтер настроен так, чтобы не ругаться на текущий код (rules relaxed to green) |

Общее везде: **зелёный сигнал производится тем же источником, что генерит проблему**, поэтому не может её обнаружить. Fix везде один — независимый источник истины для проверки: real recovery drill, holdout dataset, contract от другой команды, независимая метрика.
