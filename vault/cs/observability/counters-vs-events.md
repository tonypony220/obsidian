```
Prometheus: counter + scrape → средняя скорость по двум точкам

время:     12:00:00   12:00:15   12:00:30   12:00:45
счётчик:      1000       1150       1150       1450
                                        └── +300 ──┘
rate(...[1m]) = (1450−1000)/45 ≈ 10 req/s

но КАК пришли эти 300? равномерно или все за 1 сек?
внутри scrape-интервала — темнота. burst невидим.
```

**TL;DR:** счётчик отвечает «сколько в среднем», события отвечают «был ли хоть один плохой отрезок». Агрегация = необратимая потеря информации: что храним — определяет, на какие вопросы вообще сможем ответить.

## Механика Prometheus

- Приложение держит накопительный counter (`http_requests_total`), отдельные запросы не хранятся
- Prometheus раз в scrape interval записывает значение → временной ряд сэмплов
- `rate(x[1m])` = Δcounter / Δt по крайним точкам окна → **средняя** скорость

## Что невозможно из counter'а

- «был ли burst > K в любом окне W» — нужен каждый таймстемп → access-лог + [[sliding-window-rate-check]]
- распределение внутри scrape-интервала — для латентности эту дыру закрывают histogram'ы, но и они = бакеты-агрегаты, не события

| | события (лог) | counter (Prometheus) |
|---|---|---|
| память | O(N) | O(1) на ключ |
| отвечает | точно «∃ окно с > K?» | средняя скорость за окно |
| burst внутри интервала | видит | не видит |

## Не только в мониторинге

- **Профилирование:** sampling profiler (агрегат) vs tracing (каждый вызов) — sampling не видит редкие короткие пики
- **Сети:** NetFlow/sFlow (сэмплированные счётчики потоков) vs full packet capture
- **БД:** materialized view / rollup-таблица vs raw rows — свернул до суммы → детали не восстановить
- **Аналитика:** downsampling метрик (retention: 15s → 5m точки) — старые burst'ы стираются ретенцией

Общее везде: агрегат дешевле на порядки, но фиксирует набор отвечаемых вопросов **в момент записи**; события дороги, но вопрос можно придумать задним числом.
