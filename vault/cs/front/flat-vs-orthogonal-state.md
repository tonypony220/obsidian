# Flat vs Orthogonal State

moc: [[front-moc]]
next: [[chrome-mode-fsm]] [[ui-chrome-vocabulary]] [[stack-vs-step-navigation]]

---

```
  Плоский (одна ось)           Ортогональный (несколько осей)
  ┌─────────────────┐          ┌──────────┐  ┌───────────────┐  ┌──────────────┐
  │  kind: idle     │          │ playback │  │    muted      │  │   repeat     │
  │  kind: loading  │          │ ─────── │  │ ───────────── │  │ ──────────── │
  │  kind: success  │          │ playing  │  │ true | false  │  │ off|one|all  │
  │  kind: error    │          │ paused   │  └───────────────┘  └──────────────┘
  └─────────────────┘          │ stopped  │       независимы — масштаб: +
   N вариантов, один           └──────────┘       (не × как в плоском)
```

Два способа моделировать состояние UI. Выбор сводится к одному вопросу: **сколько у состояния реальных осей?**

## Плоский — одно поле, discriminated union

Всё состояние — одно дискриминирующее поле `kind`, каждое значение — "лист":

```ts
type Request =
  | { kind: 'idle' }
  | { kind: 'loading' }
  | { kind: 'success'; data: T }
  | { kind: 'error'; error: Error }
```

**Когда подходит:** одна ось с взаимоисключающими альтернативами. Здесь `data` существует только в `success`, `error` — только в `error`. Невалидные комбинации (`loading` с выставленным `data`) **структурно невозможны** — их нельзя даже написать.

## Ортогональный — кортеж независимых полей

Состояние — несколько полей, каждое со своей маленькой осью:

```ts
{
  playback: 'playing' | 'paused' | 'stopped',
  muted: boolean,
  repeat: 'off' | 'one' | 'all',
}
```

**Когда подходит:** несколько реально независимых измерений. Громкость не знает про repeat, repeat не знает про playback — они живут параллельно.

Плоским это было бы 3 × 2 × 3 = 18 листьев. Добавил `shuffle` — 36. Добавил ещё ось — 72. Это называется **state explosion**.

В ортогональном варианте добавление новой оси — **одно новое поле**, существующие не трогаешь. Сложение вместо умножения.

## Правило

- **Одна ось** → плоский discriminated union. Типы сами блокируют невалидные комбинации.
- **Две и больше независимых осей** → ортогональный кортеж. Масштабируется сложением, не умножением.

## Кто обеспечивает связи между осями

Ключевой тонкий момент. В плоском union'е инварианты обеспечивают **типы** — невалидную комбинацию нельзя сконструировать, TypeScript не даст. В ортогональном — **никто автоматически**. Поля независимы, и если есть правило "пока `submission === 'submitting'`, форму нельзя переключать" — это правило должен кто-то **явно** проверять.

Три места, где обычно живут такие проверки:

1. **Reducer / action handler.** Лучшее место. Action `SWITCH_FORM` в начале проверяет `state.submission !== 'submitting'` и либо применяется, либо игнорируется. Правило централизовано, один источник истины для переходов.

2. **UI-слой.** Кнопка переключения `disabled={submission === 'submitting'}`. Правило в компоненте, а не в state. Работает, но опасно — если появится другое место, откуда можно триггернуть `SWITCH_FORM` (keyboard shortcut, deep link), правило надо дублировать.

3. **Selectors / derived state.** Вычисляемое поле `canSwitchForm = submission !== 'submitting'`, которым пользуется и reducer, и UI. Компромисс.

**Правило большого пальца:** если связь обязательная (нарушение = баг) — **в reducer'е как guard**. Если это только UX-подсказка (сейчас нельзя, но и не страшно) — в UI-слое.

**Если связей слишком много** — оси не ортогональны. Перепридумай декомпозицию или слей их в одну ось через плоский union.

## Прагматика

Можно делать ортогонально **без всякого XState** — просто три поля в объекте state и три группы action'ов в одном reducer'е. XState добавляется поверх, когда количество переходов внутри каждой оси становится большим и их хочется видеть как диаграмму, а не как длинный switch. Идея ортогональности и библиотека — это разные вещи.
