**TL;DR:** Для нетривиальных изменений двигайся от слоя с дешёвой верификацией к слою с дорогой. Правки слева (типы, state-модель) удешевляют работу справа (UI, e2e). Правки справа поверх кривой левой модели — иллюзия прогресса; всё равно придётся переделывать, когда дойдёшь до настоящего дерева.

## Принцип

Для нетривиальных изменений (рефакторинг, новая фича, «причесать фичу») двигайся **от архитектуры к частностям**, от слоя с **дешёвой** верификацией к слою с **дорогой**. Цена верификации растёт по градиенту слева направо на порядки:

- Слева: типы и pure-логика. Падает за секунды на unit-тесте, падение детерминированное, легко локализовать.
- Справа: интеграция, браузер, глаза оператора, прод. Падает медленно, иногда нестабильно, локализация через бинарный поиск.

Изменения слева **удешевляют** работу справа: чистая state-модель → простой view + дешёвые его тесты. Изменения справа **не чинят** левое — это полировка поверх кривого основания.

## Градиент Frontend

```
types → reducer/selectors/FSM → pure hooks → stateful hooks/containers → components → styles/animation
```

- **types** — компилятор. Падает в IDE, мгновенно.
- **reducer/FSM** — чистая функция, тестируется без рендера. Секунды.
- **pure hooks** — хуки без side-effects, тестируются с `renderHook`. Секунды.
- **stateful hooks / containers** — нужно подкатить контексты, моки. Десятки секунд.
- **components** — рендер-тесты, query DOM. Минуты на полный прогон.
- **styles/animation** — глаза оператора в браузере, ручное QA, screenshot-тесты. Минуты-часы.

## Градиент Backend

```
types/модели → domain logic → use-cases → адаптеры/репозитории → HTTP/RPC handlers → инфра/CI
```

- **types/доменные модели** — компилятор + value-object тесты.
- **domain logic** — чистые функции, юнит-тесты без БД и сети.
- **use-cases** — оркестрация, моки портов.
- **адаптеры/репозитории** — нужна тестовая БД / контейнер. Секунды-минуты.
- **HTTP/RPC handlers** — поднять процесс, готовый http-клиент. Минуты.
- **инфра/CI** — деплой в staging, прогон e2e, нагрузка. Минуты-часы.

## Якорь-вопрос

Перед тем, как полезть в слой справа, спроси: **«модель слева уже корректно выражает то, что нужно справа?»**

Примеры:
- «Добавляю mount/unmount-анимацию модалки» — state-машина уже выражает `open → closing → closed`, или там только `isOpen: boolean`? Если второе — сначала расширь state, потом анимация становится тривиальной (см. [[fsm-closing-state]]).
- «Тормозит компонент на 1000 строк таблицы» — модель данных уже нормализована и стабильна по ссылкам, или внутрь `useState` кладётся новый массив на каждый рендер? Сначала чини reducer/мемоизацию, потом думай про виртуализацию.
- «Хэндлер ручки `POST /orders` 800 строк» — доменная логика уже выделена в чистые функции, или вся бизнес-логика в коллбэках express'а? Сначала вытащи domain в pure, потом упрощай хэндлер.

Если левый слой кривой — не лезь в правый. Сначала почини левый, **потом** правый окажется тривиальным.

## Red flags — что ты на не том конце градиента

Сигналы, что нужно сдвинуться **левее**:

1. **Добавляю булев флаг в `useState` / локальную переменную, чтобы обойти переход, которого нет в reducer/FSM.** Значит, FSM не покрывает реальное множество состояний — расширь её.

2. **`useEffect`, который заново выводит state-переходы из пропсов** (`if (open && !prevOpen) ...`). Это работа reducer'а, не эффекта. Эффект — наблюдатель, а не источник истины.

3. **View / handler ветвится на 3+ булевых флагов, «которые в норме не сосуществуют»**: `if (isLoading && !hasData && !isError && !isRefetching)`. Это несплющенный FSM протёк в верхний слой — конвертируй в discriminated union.

4. **«Анимация мигает при ре-рендере родителя» / «хэндлер тормозит, когда X»** — скорее всего референциальная нестабильность или кривой контракт уровнем ниже, **не CSS/handler-проблема**. Не лезь в `will-change`, проверь сначала memo/ссылки.

5. **«Тест компонента упал, но юнит-тесты reducer'а зелёные»** при том, что reducer покрывает только тривиальные сценарии. Реальное состояние ушло в компонент мимо reducer'а — затягивай обратно.

6. **«Каждая новая фича требует править hook+component+style одновременно»** — границы между слоями размыты, происходит знание просачивается через все три. Скорее всего нет чистого нижнего слоя, в который можно было бы добавить только логику.

## Когда правило НЕ применять

- **Левый слой уже чистый** — идти прямо во view / handler. Не выдумывай работу.
- **Чисто косметическая правка** (цвет, отступ, опечатка в тексте, typo в логе) — чинить на месте, не тянуть архитектуру.
- **Оператор просит явную заплатку с осознанным долгом** — сделать заплатку, зафиксировать долг словами в коммите/issue. Принцип не догма.
- **Hot-fix продакшена** — сначала останови кровь (правкой справа), потом спокойно перепиши слева в плановом порядке.
- **Эксперимент / прототип** — наоборот, идти справа налево: быстро накидать UI с захардкоженной фейковой моделью, проверить продуктовую гипотезу, потом возвращаться к state.

## Концепция шире

Тот же градиент «стоимость обнаружения растёт слева направо» встречается везде, где есть pipeline проверок:

- **Compile-time → runtime → prod incidents.** Compile-time error: 0 секунд. Runtime exception в QA: минуты. Prod incident: часы + потерянное доверие. Любая проверка, сдвинутая в compile-time, экспоненциально дешевле.

- **Test pyramid**: много быстрых юнит-тестов внизу, меньше интеграционных, единицы e2e наверху. Цена прогона и нестабильность растут к вершине. Та же геометрия.

- **Shift-left в DevSecOps**: переносить security-checks, code-quality, lint, type-check на ранние стадии CI (или даже pre-commit). Каждый шаг влево уменьшает стоимость инцидента.

- **Unix mantra «text streams are cheap, GUIs are expensive»** — текст диффится, грепается, скриптуется; GUI требует глаз и кликов.

- **Product discovery vs delivery**: дешевле провести 5 customer-интервью до фичи, чем переделывать релизнутую фичу. Та же логика, в продуктовом контексте.

- **Architecture decisions vs implementation**: ADR на этапе планирования стоит часы, та же ошибка, обнаруженная после релиза, стоит недели миграций.

Общее везде: **обнаруживай и фикси проблему на самом раннем/дешёвом слое, где она видна**. Цена пропуска ошибки в следующий слой растёт по экспоненте, не по линии.
