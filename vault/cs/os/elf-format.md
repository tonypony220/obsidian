# ELF format

next:

- [[boot-process]]

---

```
kernel.bin (ELF-файл):
┌──────────────────────────┐
│ ELF header («накладная») │
│  magic: 0x7F 'E' 'L' 'F' │
│  arch: i386, 32-bit      │
│  entry: 0x001000xx ──────┼──▶ куда прыгать
│  таблица: что куда ──┐   │
├──────────────────────┼───┤
│ .text   (код)      ◀─┤   │
│ .rodata (константы)◀─┤   │
│ .data   (глобалы)  ◀─┘   │
└──────────────────────────┘
```

**TL;DR:** ELF — формат исполняемого файла: заголовок-«накладная» говорит загрузчику, какие куски файла по каким адресам памяти разложить и на какой адрес прыгнуть после этого.

## Аналогия

Мебель в плоской упаковке: коробка (файл) содержит детали (секции) и инструкцию (заголовок + таблицы) — «деталь A ставится в позицию X», плюс отметку «пользоваться начинай отсюда» (entry point). Загрузчик — сборщик: тупо следует инструкции, не понимая, что за мебель.

## Кто пишет, кто читает

- **Пишет линкер** — по [[linker-script]]: именно там решено, какая секция по какому адресу окажется и что entry = `_start`.
- **Читает загрузчик** — GRUB ([[boot-process]]): парсит заголовок, копирует секции в RAM по указанным адресам, прыгает на entry. Так же Linux читает ELF при запуске обычной программы — формат тот же.
- Посмотреть глазами: `i686-elf-readelf -h kernel.bin` (arch, entry), `-S` (секции и их адреса).

## Тонкость: секции vs сегменты

В ELF два «вида» на один файл: секции (детально, для линкера) и сегменты (крупно, для загрузчика). Для KFS достаточно думать секциями — GRUB загрузит как надо.

## Не только ELF

Та же роль у [[cross-compilation|других платформ]]: Mach-O (macOS), PE (Windows). Поэтому хостовый clang на маке и не годится — он выпускает «накладные» другого формата, которые GRUB не читает.
