```
CPU ──шина PCIe──▶ контроллер SATA ──кабель──▶ диск
 │ пишет в регистры:   │ вся физика тут:
 │ «сектор №0 → RAM    │ головки, напряжения…
 │  по адресу X»       │ данные сам кладёт в RAM
 │                     │ (DMA), ставит бит «готово»
 └── poll «готово?» ◀──┘
```

**TL;DR:** CPU не видит устройств — только регистры контроллеров, доступные через [[memory-mapped-io]]; контроллер-посредник прячет всю физику, а шины спроектированы опрашиваемыми: прошивка узнаёт «что подключено» перекличкой.

## Слои

- **CPU** умеет одно: читать/писать адреса и порты ([[bus-cycle]]). Диск к нему не подключён — ножки у CPU только свои (A-пучок, D-пучок, управление), и подключены они к одной микросхеме: чипсету. Всё остальное — за ним.
- **Мост (bridge)** — микросхема-переводчик между двумя шинами: принимает циклы одной, воспроизводит на другой. Чипсет = мосты + декодер. За host-мостом — вторичные шины: шина памяти (планки RAM), PCI-шина (слоты). У PCI-шины провода адреса/данных ОБЩИЕ для всех слотов, плюс личный провод IDSEL от чипсета к каждому слоту — дорожки на материнке, не ножки CPU: способ выбрать слот, не используя адрес.
- **Современно**: параллельной PCI-шины нет — PCIe это точка-точка: у каждого устройства личный последовательный линк, конфиг-обращения ездят пакетами с координатами bus:device:function в заголовке, IDSEL-проводов больше нет. Контракт (конфиг-пространство, BAR, перекличка) пережил смену физики нетронутым. Чипсет усох: контроллер памяти и PCIe-корень переехали внутрь корпуса CPU, снаружи остался один чип медленной периферии (Intel PCH)
- **Контроллер** — чип-посредник с регистрами наружу: принимает команду («бланк заказа»), физически исполняет, кладёт данные в RAM сам (**DMA** — мимо CPU), поднимает бит «готово».
- **Устройство** висит на контроллере; его физика (моторы, ячейки flash) не видна даже BIOS. Внутри диска — свой контроллер: «лента пронумерованных секторов» тоже абстракция, номера транслируются в реальные ячейки.

## Перекличка (enumeration) — как узнать, что подключено

- **PCI/PCIe**: у каждого устройства кроме рабочих окон есть стандартный блок регистров — **конфигурационное пространство** (vendor/device ID, класс, 6 BAR'ов). Решает chicken-and-egg «как говорить с картой, которой ещё не назначили адресов»: адресуется **географически** — координатами bus:device:function (у каждого слота своя линия выбора IDSEL), а не адресом памяти. Дверь на x86 — два замороженных порта: `0xCF8` (записать координаты+offset регистра) и `0xCFC` (прочитать/записать сам регистр). Прошивка перебирает все координаты: vendor ID = 0xFFFF → пустой слот (линии никто не тянет, электрически все-единицы); иначе читает анкету
- **Назначение окон (BAR sizing)**: прошивка пишет в BAR все-единицы, читает обратно — младшие биты у карты прошиты нулями, их количество кодирует размер окна (вернулось 0xFF000000 → 16 МБ); затем выбирает свободный диапазон и записывает базу в BAR — с этого момента контроллер отвечает на диапазон ([[memory-mapped-io]]: vga.vram на 0xFD000000 в QEMU)
- **USB**: хаб замечает изменение напряжения на порту («воткнули»), контроллер присваивает адрес и запрашивает дескриптор-анкету («я накопитель»)
- Итог переклички = список устройств → из него строится boot order ([[boot-process]])

## Стандартные классы = hardware-ABI

Раскладка регистров стандартизована по классам: AHCI (SATA), NVMe (SSD), xHCI (USB). Контракт того же жанра, что [[multiboot]], но между прошивкой/ОС и кремнием: BIOS, написанный до рождения твоего диска, работает с ним — потому что говорит не с диском, а со стандартным классом контроллера.

## Почему виртуализация «просто работает»

QEMU реализует ту же раскладку регистров программно: SeaBIOS пишет в «регистры» → QEMU перехватывает и отвечает как настоящий чип. Гость отличить не может — контракт это интерфейс, не реализация.

## Концепция шире

- Драйвер ОС — тот же разговор с регистрами контроллера, что у BIOS, только богаче
- virtio: паравиртуальные устройства — контракт, спроектированный сразу «для VM», без имитации легаси-чипов
- Облачные API: код говорит с S3-интерфейсом, не со стойкой дисков — тот же трюк «стандартный интерфейс прячет реализацию»

Общее везде: стандартизованный интерфейс на границе отделяет пользователя от физики; реализацию можно подменить (в т.ч. программной) незаметно для клиента.
