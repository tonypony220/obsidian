```
          source S
             │
           R_src
             │
             │ PIM Register (к RP, encap пакета unicast'ом)
             ▼
           R_RP          ← root shared-tree (RPT), известен всем заранее
           ╱ ╲
          ╱   ╲          ← размножение на любом branching-point
     R_mid1  R_mid2
        │       │
      R_leaf1 R_leaf2    ← знают подписчиков через IGMP
        │       │
     list_A   list_B

   Listener'ы подписались → leaf'ы шлют Join вверх к RP
   → дерево наращивается снизу вверх
   Source начал слать → первый пакет к RP через Register
   → трафик течёт по готовому дереву вниз
```

**TL;DR:** PIM — L3 control-plane протокол **между роутерами underlay'я**, строящий деревья доставки multicast от source к подписчикам. Основной режим в ДЦ — **PIM-SM (Sparse Mode)**, pull-based: leaf-роутеры при появлении подписчика шлют **PIM Join** вверх, но не к source (его адрес неизвестен), а к заранее известному **Rendezvous Point (RP)**. Дерево наращивается снизу вверх hop-by-hop. Петли предотвращает **RPF-проверка** по unicast RIB. Размножение распределённое — на каждом branching-point дерева. «Protocol Independent» = PIM не строит свою таблицу маршрутов, использует готовую [[rib-vs-fib|unicast RIB]] (OSPF/BGP/static).

## Задача — откуда она берётся после IGMP

После работы [[igmp|IGMP]] у каждого leaf-роутера есть **локальное** знание: «за таким-то интерфейсом есть подписчики на группу G». Но:

- **самого трафика у него нет** — source находится где-то по ту сторону underlay'я,
- **адрес source неизвестен** — в IGMP Report только группа, не source IP.

Задача PIM — построить путь между `R_src` и всеми `R_leaf` с подписчиками через underlay, и гнать по этому пути multicast-трафик. Это distribution-часть из двух подзадач [[ip-multicast|IP-multicast]].

## Два подхода: push vs pull

Когда и как строить путь доставки — дихотомия, задающая режим PIM.

### Push — Dense Mode (PIM-DM)

Предположение: **подписчики везде**.

```
   R_src шлёт → underlay фладит пакеты во все направления
        │
   ветки без подписчиков → шлют Prune обратно
        │
   остаются только ветки к реальным listener'ам
        │
   периодически всё перефлаживается (чтобы подцепить новых)
```

Хорошо когда подписчиков реально много. Плохо в ДЦ: бесполезный трафик по всему underlay хотя бы до первого prune'а. Исторический режим для маленьких плотных сетей.

### Pull — Sparse Mode (PIM-SM)

Предположение: **подписчиков нет нигде** по умолчанию.

```
   R_leaf видит IGMP Report → "нужна G"
        │
   шлёт PIM Join upstream
        │
   Join идёт hop-by-hop, каждый роутер запоминает "сюда хотят G"
        │
   дерево наращивается снизу вверх ТОЛЬКО в ветках, где реально нужно
        │
   трафик source пускается по уже готовому дереву
```

Хорошо когда подписчиков мало относительно сети — **это наш случай в ДЦ и VXLAN**. Дальше в заметке обсуждается в основном SM.

## Проблема pull: Join — **куда**?

Идея «шлю Join upstream к source» ломается о простую вещь: **leaf не знает где source.** Всё что leaf знает — это группа `G` (из IGMP). А `S` находится где-то в underlay'е, и на leaf'е про него никакой информации нет.

Хуже того, source может ещё **не начать** слать — listener может подписаться заранее и ждать. В такой момент вообще нигде нет trace'а откуда он появится.

Нужна **заранее известная всем точка**, в которую leaf'ы шлют Join, а source регистрируется когда начинает работать:

```
   listener                      source
      │                            │
    R_leaf                       R_src
      │                            │
      │ PIM Join(G)                │ PIM Register(S в G)
      │ "хочу G"                   │ "я source для G"
      ▼                            ▼
             R_RP  (Rendezvous Point)
             адрес всем PIM-роутерам известен
             заранее — config / BSR / Auto-RP / Anycast-RP
```

Эта точка — **Rendezvous Point (RP)**. Она решает координационную проблему: listener не знает source, source не знает listener'ов, но оба знают RP.

**В PIM-SM RP обязателен — это каркас протокола, не оптимизация.** Без RP Join некуда адресовать. Оптимизация появляется позже (SPT switchover, см. ниже).

## RP — роль, не отдельный компонент

Все PIM-SM роутеры запускают одинаковый PIM-стек. Роль RP присваивается одному (или нескольким) из них **административно**. Остальные — обычные PIM-роутеры, просто знающие адрес RP.

Как роутеры узнают адрес RP:

- **Static RP** — прописан в конфиге каждого роутера. Простой вариант, удобен в ДЦ и BADASS-лабе.
- **Auto-RP** — Cisco-механизм: RP анонсирует себя через `224.0.1.39` / `224.0.1.40`.
- **BSR (Bootstrap Router)** — стандартизированный динамический выбор RP.
- **Anycast-RP** — несколько роутеров с общим IP, синхронизируются между собой через MSDP; отказоустойчивость без изменения конфигов остальных.

## Protocol Independent

PIM **не** строит свою карту топологии underlay'я, не обменивается префиксами, не считает метрики. Для выбора upstream-интерфейса и RPF-проверки он просто **читает готовую unicast RIB**. Какой протокол её заполнил (OSPF, BGP, ISIS, static) — PIM всё равно.

Отсюда «Protocol Independent». PIM живёт **поверх** существующего unicast-роутинга:

```
   unicast RIB: "к IP 10.0.0.250 (RP) next-hop через интерфейс X"
                         │
                         ▼
   PIM: "значит мой upstream для группы G — интерфейс X"
```

## Два дерева в PIM-SM: RPT и SPT

В PIM-SM для одной группы может одновременно существовать **два дерева**:

- **RPT (shared tree, `(*, G)`)** — root = RP. Строится сразу при первом Join от listener'а. Существует всегда, пока есть подписчики.
- **SPT (source tree, `(S, G)`)** — root = сам source. Появляется **после SPT switchover** — опциональной оптимизации.

**SPT switchover**: когда первый пакет дошёл до leaf-роутера по RPT, leaf видит в нём фактический `src IP` (= source `S`). Теперь он может послать новый Join напрямую к `S` (обход RP), получить источник по короткому пути, и сбросить RPT-ветку. Switchover уменьшает нагрузку на RP и даёт оптимальный путь, но усложняет состояние — можно отключить (тогда весь трафик всегда через RP).

## Как летит Join от leaf до RP

PIM Join — **не** broadcast и **не** глобальный multicast. Это hop-by-hop сообщение между соседними PIM-роутерами, отправляемое на link-local multicast `224.0.0.13` (All-PIM-Routers) — этот адрес не роутится, его принимают только прямые соседи по интерфейсу. Каждый роутер обрабатывает Join и, если надо, генерирует новый Join себе upstream.

Трасса: `R_leaf ── R_mid ── R_RP ── R_src ── S`. `R_leaf` только что получил IGMP Report от хоста на `G`.

```
  ШАГ 1 — R_leaf
   RP для G = 10.0.0.250 (из конфига)
   unicast RIB: "к 10.0.0.250 через интерфейс к R_mid"
   → создаёт запись (*, G):
       iif = интерфейс к R_mid     (upstream к RP)
       OIL = [интерфейс к хосту]   (downstream подписчик)
   → шлёт PIM Join(*, G) на 224.0.0.13 через upstream-интерфейс

  ШАГ 2 — R_mid получает Join
   создаёт свою запись (*, G):
       iif = интерфейс к R_RP     (опять unicast RIB, next-hop к RP)
       OIL = [интерфейс к R_leaf]  ← добавил downstream
   шлёт свой Join(*, G) upstream к R_RP

  ШАГ 3 — R_RP получает Join
   "это я и есть RP для G"
   создаёт запись (*, G):
       OIL = [интерфейс к R_mid]
   Join дальше не отправляется — дошёл до корня
```

Итог — участок shared-tree построен:

```
  R_leaf  (*, G)  iif=к_R_mid    OIL=[к_хосту]
    │
  R_mid   (*, G)  iif=к_R_RP     OIL=[к_R_leaf]
    │
  R_RP    (*, G)                 OIL=[к_R_mid]
```

Когда source начнёт слать, его first-hop роутер (`R_src`) инкапсулирует пакеты в **PIM Register** и отправит unicast'ом к RP. RP раскрывает и пускает по своему OIL вниз по RPT — дальше по уже готовой цепочке.

## RPF — защита от петель

Reverse Path Forwarding — ключевая проверка на каждом роутере при обработке пришедшего multicast-пакета:

```
  пакет (src=S, dst=G) пришёл на интерфейс X
       │
       ▼
  unicast RIB: "какой next-hop к S?"
       │
       ▼
  "если бы я слал unicast'ом к S, я пошёл бы через Y"
       │
       ├── X == Y  → RPF OK, принять, переслать по OIL
       │
       └── X != Y  → RPF FAIL, дроп
```

Смысл: multicast-пакет принимается **только если пришёл по обратному пути к source**. Это гарантирует что деревья остаются деревьями (без циклов) — если тот же пакет пришёл «не с той стороны», значит он проехал по петле.

Практическое следствие: **PIM сильно зависит от корректной unicast RIB**. Если unicast-роутинг выдаёт неконсистентный next-hop к RP или source на разных роутерах — RPF будет дропать валидные пакеты. Типичная проблема при дебаге multicast.

## Где происходит размножение (fan-out)

Размножение копий — **распределённое**, на каждом branching-point дерева:

```
                       S
                       │
                     R_src          ← 1 downstream → не размножает
                       │
                     R_core         ← 2 интерфейса в OIL → копирует на 2
                      ╱ ╲
                    R1    R2        ← 1 downstream → не размножает
                     │      │          (в сегменте уже L2: свитч / bridge)
                 (сегмент) (сегмент)
                     │      │
                  list_A  list_B
```

Правило: один пакет пришёл на iif → **N копий** вышло, по одной на каждый интерфейс в OIL. OIL из одного интерфейса — просто forward без дупликации. OIL из пяти — пять копий уходит в пять разных направлений.

Главная экономия multicast: **fan-out происходит как можно позже**, прямо перед расхождением веток. В отличие от N unicast'ов (где полоса ×N занята на первом же hop'e у источника), здесь полоса «делится» только там, где дерево ветвится. Source шлёт ровно один пакет независимо от числа подписчиков.

## PIM-DM и PIM-SSM вкратце

- **PIM-DM** — push-based, flood-and-prune, без RP. Простой, для маленьких плотных сетей. В современных ДЦ не используется.
- **PIM-SSM** — source-specific: listener через IGMPv3 указывает пару `(S, G)`, leaf-роутер сразу строит SPT к S, RP не нужен вообще. Работает только в диапазоне `232.0.0.0/8`. Подходит когда source известен заранее (спутник, video stream).

## В VXLAN multicast mode

Underlay-роутеры между VTEP'ами запускают PIM-SM. Полная цепочка:

1. VTEP через [[igmp|IGMP]] подписывается на `239.1.1.1` на своём first-hop router
2. First-hop router шлёт PIM Join к RP
3. Дерево строится: RP и все промежуточные роутеры создают `(*, G)` записи
4. Source-VTEP шлёт BUM-кадр с outer dst = `239.1.1.1`
5. Первый пакет попадает на RP через PIM Register, RP раскрывает и пускает по RPT
6. Underlay по дереву доставляет копии всем VTEP'ам-членам VNI

Требования к underlay:
- PIM включён на всех интерфейсах
- RP настроен и достижим (static или Anycast-RP)
- Unicast-роутинг корректный (для RPF)

**Это цена multicast-режима VXLAN**: underlay обязан уметь полноценный IP-multicast, что в современных BGP-only фабриках ДЦ часто не реализовано — поэтому на масштабе переходят на EVPN, где control plane multicast в underlay не требует.

## Связь с BADASS

В P2 multicast-режиме:
- Выбираешь `group 239.1.1.1` (или другой admin-scoped адрес) для VNI 10
- На VTEP-роутерах: `ip link add vxlan10 type vxlan id 10 group 239.1.1.1 ...`
- На underlay-роутерах: включить PIM-SM на всех интерфейсах, прописать static RP (один из роутеров сам себе RP, остальные указывают на него)
- IGMP Report VTEP'ы шлют автоматически через ядро
- Дальше PIM-дерево строится при первом Join, трафик идёт как описано выше

В P3 всё это становится ненужным — переход на EVPN убирает multicast из underlay, BUM идёт через head-end replication по Type 3 маршрутам BGP.
