**TL;DR:** Адресация multicast — обычный L3-префикс (`224.0.0.0/4`), на этом уровне ничего нового. Но **forwarding — другая логика**: у multicast-пакета один dst (группа), но может быть 0, 1, 5 выходных интерфейсов одновременно — в unicast FIB такое не укладывается. Поэтому на роутере появляется **вторая, параллельная таблица — multicast FIB** (`(S,G) → iif + OIL`), которую наполняют два L3-протокола: [[igmp|IGMP]] (membership, хост↔router) и [[pim|PIM]] (distribution-деревья, router↔router). Unicast-маршрутизация (OSPF/BGP) остаётся как была — multicast **накладывается** сверху как отдельный контур, используя unicast RIB только для RPF.

## Три типа доставки

| | Unicast | Broadcast | Multicast |
|---|---|---|---|
| Кому | 1 получатель | все в сегменте | подписчики группы |
| dst-адрес | IP конкретного хоста | `255.255.255.255` / broadcast подсети | групповой IP `224.0.0.0/4` |
| Масштаб | любой | один L2-сегмент (через роутеры не идёт) | любой (если underlay умеет) |
| Знает получателей | отправитель | никто не знает, всем | никто не перечисляет, подписка |

Multicast нужен когда получателей **много, но не все**, и отправитель **не должен их перечислять**: видеостриминг, рыночные данные биржи, OSPF hello (`224.0.0.5`), VXLAN BUM-флуд в режиме multicast.

## Group address — не адрес хоста, а ярлык группы

Group IP — обычный 32-битный IPv4 из диапазона `224.0.0.0/4`. В пакете лежит как любой `dst IP`. Семантически — **идентификатор группы, не адрес устройства**.

```
  unicast IP (10.0.0.20)         multicast IP (239.1.1.1)
  ─────────────────────          ─────────────────────────
  назначен интерфейсу            НЕ назначен никому
  один owner — конкретный хост   владельца нет, есть подписчики
  ARP "кто такой 10.0.0.20?"     ARP не нужен и не работает
  пингуется, отвечает один       пингуется — отвечают все подписчики
```

Никакой машины с IP `239.1.1.1` не существует. Это метка «трафик для группы X». Кто хочет получать — подписывается, его NIC принимает кадры с mapped MAC, дальше это становится IGMP-сигналом для роутера.

**Откуда берётся конкретное значение** — три источника (диапазоны — в следующем разделе):

1. **Well-known** — назначены IANA, захардкожены в протоколах. `224.0.0.5` = OSPF DR, `224.0.0.2` = все роутеры, `224.0.0.251` = mDNS. OSPF-демон **знает**, что hello слать на `224.0.0.5`.
2. **Admin-scoped** — админ выбирает сам, как RFC1918 для unicast. Для VXLAN VNI=10 админ декларирует «пусть будет `239.1.1.10`» — договорённость в рамках underlay'я.
3. **SSM** — приложение выбирает пару `(source, group)` явно.

**Что происходит при подписке:** хост вызывает `setsockopt(IP_ADD_MEMBERSHIP, 239.1.1.1)`. Ядро настраивает NIC принимать кадры с mapped MAC, шлёт [[igmp|IGMP]] Report роутеру → роутер включает интерфейс в OIL для этой группы. **Никаких ARP** — mapping IP→MAC у multicast детерминированный (см. ниже).

## Адресация

- IPv4: `224.0.0.0/4` — весь multicast-диапазон
  - `224.0.0.0/24` — link-local, никогда не роутится (`224.0.0.5` — OSPF DR, `224.0.0.2` — все роутеры)
  - `232.0.0.0/8` — SSM (Source-Specific Multicast, явная пара (S, G))
  - `239.0.0.0/8` — admin-scoped, приватные группы (VXLAN обычно тут)
- IPv6: `ff00::/8`

MAC-mapping при укладке IP-multicast в Ethernet:
- IPv4: `01:00:5e` + младшие **23 бита** IP-группы. Группа 28-битная → 5 бит теряются → возможны коллизии MAC для разных групп.
- IPv6: `33:33` + младшие 32 бита.

## Но forwarding — другая задача

Адресация multicast тривиальна: префикс как префикс. А вот **forwarding-решение** принципиально отличается от unicast:

```
  UNICAST                      MULTICAST
  ───────                      ─────────
  dst = конкретный хост        dst = группа G (не хост)
  FIB: dst → ОДИН next-hop     решение: размножить копии КУДА?
  выход один                   выходов может быть 0, 1, 5
  решение локальное, по dst    зависит от глобального state
                               "кто где подписан"
```

Обычный unicast FIB вида `dst-IP → next-hop` такое не описывает. Поэтому на роутере появляется **вторая параллельная таблица forwarding'а** — multicast FIB (MFIB / mroute table). Записи в ней имеют форму:

```
  (Source S, Group G) → Incoming Interface (iif)
                      → Outgoing Interface List (OIL) = [if1, if3, ...]
```

Логика forwarding'а: пакет от source S к группе G должен прийти на **iif** (иначе drop по RPF); если пришёл — размножить копии в каждый интерфейс из **OIL**. Запись `(*, G)` — shared-tree (работает для любого source этой группы), `(S, G)` — source-specific tree.

## Параллельный forwarding plane

На роутере, умеющем multicast, живут **две пары** control/data plane **рядом**, а не внутри друг друга:

```
  ┌──────────── CONTROL PLANE ────────────┐   ┌──── DATA PLANE ─────┐
  │                                       │   │                     │
  │  OSPF / BGP / static ──▶ unicast RIB ─┼─▶ │  unicast FIB        │
  │                                │      │   │  (dst → next-hop)   │
  │                                │ RPF  │   │                     │
  │                                ▼      │   │                     │
  │  IGMP (host↔router)                   │   │                     │
  │  PIM  (router↔router) ────▶  mc RIB ──┼─▶ │  multicast FIB      │
  │                                       │   │  ((S,G) → iif, OIL) │
  └───────────────────────────────────────┘   └─────────────────────┘
```

- Unicast и multicast FIB — **две разные таблицы**. Dst из `224.0.0.0/4` → multicast FIB, иначе → обычный.
- Unicast-роутинг (OSPF/BGP/static) и multicast-роутинг (IGMP + PIM) — независимы, наполняют разные RIB.
- Единственная связь: [[pim|PIM]] **читает** unicast RIB для RPF-проверки (чтобы гарантировать дерево без петель), но сам unicast RIB не трогает.

**Т.е. multicast накладывается на существующую маршрутизацию как второй слой, не заменяя её.** Можно включить multicast на уже работающей сети с OSPF/BGP — ничего не сломается, рядом просто появится второй контур.

## Два control-plane-протокола — оба L3

Оба — обычные IP-протоколы, просто payload у них — control-сообщения, а не пользовательские данные (ровно как OSPF/BGP для unicast):

| | IGMP | PIM |
|---|---|---|
| IP protocol number | `2` | `103` |
| Между кем | хост ↔ first-hop router | router ↔ router |
| Область | один L2-сегмент (local) | вся multicast-зона underlay |
| Что решает | **membership** — кто подписан на группу | **distribution** — как построить дерево |
| Что наполняет | membership state роутера (OIL) | multicast RIB (записи `(*,G)` / `(S,G)`) |

Разделение буквальное: **IGMP ничего не знает про деревья между роутерами; PIM ничего не знает про индивидуальных хостов.** IGMP говорит своему роутеру «в этом направлении есть подписчики на G», PIM собирает такие сигналы с leaf-роутеров и строит из них дерево от source через underlay.

## IGMP snooping — L2-оптимизация

Обычный L2-свитч флудит multicast-кадры как [[bum-traffic|BUM]] на все порты. С **IGMP snooping** свитч слушает IGMP-сообщения хостов, понимает на каком порту реально подписчики, и шлёт multicast только туда. Это L2-оптимизация, использующая L3-протокол как сигнал.

## В VXLAN multicast mode

Каждому VNI сопоставлена multicast-группа в underlay (например, VNI 10 → `239.1.1.1`). Цепочка:

1. VTEP создаётся с `group 239.1.1.1` → ядро Linux шлёт [[igmp|IGMP]] Membership Report
2. First-hop router узнаёт "на этом интерфейсе есть подписчик на 239.1.1.1"
3. [[pim|PIM]] включает этот интерфейс в дерево группы
4. Source-VTEP шлёт [[bum-traffic|BUM]]-кадр в группу → underlay по дереву доставляет копии всем VTEP'ам VNI

Это и есть смысл multicast-режима VXLAN: **делегировать размножение BUM-копий underlay'ю** вместо head-end-replication на source-VTEP. Цена — underlay должен уметь полноценный IP-multicast (PIM + IGMP), а это не всегда так в современных ДЦ.

## Где multicast реально работает (и где нет)

Главное практическое ограничение: **multicast не маршрутизируется в публичном интернете** и обычно **запрещён в дефолтном underlay облачных VPC**.

| Работает | Не работает |
|---|---|
| Один L2-сегмент (VLAN, bridge) | Публичный интернет (PIM между AS никто не включает) |
| ДЦ с настроенным PIM | Дефолтная VPC у AWS/GCP/DO/Hetzner |
| Внутри overlay-туннеля | Напрямую между двумя публичными VPS |
| Локальные VM/контейнеры через общий bridge | |

Причины:

- ISP не маршрутизируют multicast — MSDP/MBGP теоретически есть, на практике никто не включает (нет коммерческого интереса).
- Облака запрещают multicast в shared underlay из соображений масштабируемости (broadcast/flood плохо живёт на общей инфраструктуре). AWS даёт Transit Gateway Multicast отдельной платной фичей.

**Обходные пути когда underlay не умеет multicast:**

1. **Overlay-туннель** (WireGuard, GRE, VXLAN в unicast-режиме) — multicast работает **внутри** туннеля, underlay видит обычный unicast между endpoint'ами. Группу выбираешь сам из `239.0.0.0/8`.
2. **Head-end replication / EVPN** ([[vxlan-modes]]) — source-VTEP сам шлёт unicast-копии каждому удалённому VTEP'у по списку, multicast в underlay не нужен.
3. **Pub/sub-брокер** (NATS, Kafka, MQTT, Redis Pub/Sub) поверх TCP — та же семантика fan-out, но fan-out делает брокер, а не сеть. Для большинства прикладных задач это и есть правильный ответ.

`239.1.1.1` — не адрес «который надо где-то получить», а метка которую ты сам выбираешь. Вопрос только в том, **донесёт ли underlay** эту метку до подписчиков. Между двумя публичными VPS напрямую — нет.

Multicast в underlay живёт там, где оператор контролирует всю сеть: финансовые биржи (рыночные данные), корпоративные стриминговые системы, IPTV. В публичной/мульти-облачной среде — почти не встречается.

## Не только в сетях

- **Pub/sub брокеры** (Kafka, NATS, MQTT) — один publisher шлёт в topic, брокер раздаёт всем подписчикам; subscribe = "хочу получать"
- **mDNS / multicast DNS** — link-local discovery без центрального сервера через `224.0.0.251`
- **Событийные шины GUI** — один источник события, N зарегистрированных обработчиков; фреймворк делает dispatch
- **Reactive streams / Observable** — один source, много subscriber'ов, runtime отвечает за fan-out

Общее везде: **отправитель не знает получателей, получатели сами подписываются, промежуточный слой отвечает за fan-out**. Различие только в том, где живёт "промежуточный слой": сеть (IP multicast), брокер (pub/sub), runtime (events). Это одна из форм паттерна «publish–subscribe с разделением producer и consumer через посредника».
