```
   ┌──────────── ОДИН L2-СЕГМЕНТ ────────────┐
   │                                         │
   │  host A  (хочет G) ───"Report G"───▶    │
   │  host B  (не хочет)                     │──▶ R1 (first-hop router)
   │  host C  (хочет G) ───"Report G"───▶    │
   │                                         │
   └─────────────────────────────────────────┘
                       │
           R1 знает: "за этим интерфейсом
           есть подписчики на G"
                       │
                       ▼
           включает интерфейс в OIL своей
           multicast FIB для группы G
                       │
                       ▼
              дальше — PIM (это уже НЕ IGMP)
```

**TL;DR:** IGMP — L3 control-plane протокол на **одном L2-сегменте** между хостом и first-hop роутером. Отвечает только на один вопрос: «кто на сегменте подписан на какую группу», чтобы роутер понимал — лить ли копию multicast-трафика в этот интерфейс. Работает **в ядре хоста**, приложение подписывается через обычный socket API. Не занимается ни деревьями между роутерами (это [[pim|PIM]]), ни открытием «какие группы существуют» (это out-of-band — конфиг, well-known, application-протоколы).

## Задача — откуда она берётся

Минимальный сценарий: один L2-сегмент, один роутер `R1`, три хоста, часть из них хочет получать группу `G`:

```
   host A (хочет G) ──┐
   host B            ├──▶ R1  ──▶ (дальше в сеть)
   host C (хочет G) ──┘
```

У `R1` конкретная задача: когда по дереву [[pim|PIM]] к нему из-за спины придёт пакет для группы `G`, нужно решить — **дублировать его в интерфейс этого сегмента или нет**. Т.е. должен ли этот интерфейс быть в OIL записи `(S, G)` в его [[ip-multicast|multicast FIB]].

- Есть хоть один подписчик → должен быть в OIL
- Нет подписчиков → зря занятая полоса и спам на NIC'ах всех хостов сегмента

**Сам роутер это не может вычислить** — состояние хостов снаружи ему не видно. Значит, нужен протокол, где хосты явно об этом сообщают. Это и есть IGMP.

## Зона ответственности — только local segment

```
  хост  ◀── IGMP ──▶  router              в пределах одного broadcast-домена

  router ◀── PIM ──▶ router               между роутерами — это уже НЕ IGMP
```

IGMP закрывает **membership**-часть из двух подзадач [[ip-multicast|IP-multicast]]. PIM берёт эту информацию с leaf-роутеров и собирает из неё дерево доставки через underlay.

## Кто на хосте «подписывает»

На обычном Linux IGMP-логика живёт **в ядре**, отдельного IGMP-демона на хосте нет. Приложение просто использует стандартный socket API:

```
  приложение              ядро                       NIC / провод
  ──────────              ────                       ────────────
  socket(UDP)
       │
       ▼
  setsockopt(              ┌─ добавляет (iface, G)
    IP_ADD_MEMBERSHIP,     │  в свою membership table
    group = G,             │
    iface = eth0           ├─ программирует NIC на приём
  )           ───────────▶ │  MAC 01:00:5e:...
                           │
                           ├─ шлёт IGMP Membership Report  ──▶ R1
                           │
                           └─ отвечает на IGMP Query       ◀── R1
```

Технический момент: NIC по умолчанию фильтрует чужие MAC'и. Чтобы принимать multicast-кадр с `01:00:5e:..`, ядро **программирует NIC** специально — иначе кадр будет отброшен на железе ещё до того как попадёт в стек.

### В VXLAN

Здесь «приложением» выступает сам VXLAN-модуль ядра. Когда ты пишешь:

```bash
ip link add vxlan10 type vxlan id 10 dev eth0 group 239.1.1.1
```

— модуль `vxlan` внутри ядра делает эквивалент `IP_ADD_MEMBERSHIP` на `239.1.1.1` через `eth0`. Никаких user-space программ для IGMP не нужно, всё происходит автоматически при создании интерфейса.

## IGMP — не discovery-протокол

IGMP умеет ровно одно: «вступить/выйти из группы с адресом G». **Сам адрес группы** (`239.1.1.1`, `224.0.0.5` и т.п.) IGMP не открывает — он приходит **out-of-band**:

```
   "какие группы существуют?"      "кто подписан?"         "как доставить?"
   ──────────────────────────      ───────────────         ────────────────
   OUT-OF-BAND                     IGMP                    PIM
   (config / well-known / app)     (хост ↔ router)         (router ↔ router)
```

Варианты откуда берётся адрес:

1. **Well-known в RFC.** Жёстко в спецификации протокола: OSPF DR — `224.0.0.5`, mDNS — `224.0.0.251`, все роутеры на сегменте — `224.0.0.2`. Приложения знают эти адреса «по книжке».
2. **Конфигурация.** Админ решает и вписывает. **Это случай VXLAN:** адрес группы для VNI выбираешь сам и пишешь в `ip link add`.
3. **Application-level сигналы.** SAP, SDP, DNS, HTTP API — приложение сначала по отдельному каналу узнаёт группу, потом делает `IP_ADD_MEMBERSHIP`.

Параллель с unicast: DNS/config даёт IP сервера, IP-роутинг довозит пакет. Здесь та же структура: внешний слой даёт **адрес группы**, IGMP+PIM довозят. Разные слои, не перемешиваются.

## Сообщения (IGMPv2, базово)

- **Membership Query** — роутер периодически шлёт general query на `224.0.0.1`, проверяя кто ещё подписан. Нужен потому что хост может пропасть молча без Leave.
- **Membership Report** — хост говорит «я в группе G». Шлётся на адрес самой группы (не unicast'ом к роутеру — см. ниже).
- **Leave Group** — хост явно сообщает «больше не хочу G». Роутер в ответ делает group-specific query: если никто не отозвался — перестаёт пересылать.

**IGMPv3** добавляет source-filtering: хост может указать «хочу G **только** от source S» (или «кроме S») — нужно для SSM-режима PIM.

### Почему Report шлётся на адрес группы, а не unicast'ом

Отчёт идёт на сам `G`, и это намеренно: его **видят другие хосты** сегмента. Если хост A уже отрепортил `G`, хост B может **подавить** свой Report — роутеру достаточно знать «хоть кто-то подписан», дублировать не нужно. Экономит broadcast-шум в плотном сегменте.

## IGMP snooping — L2-оптимизация

Обычный L2-свитч обрабатывает multicast-кадры как [[bum-traffic|BUM]]: флудит на все порты. С **IGMP snooping** свитч подсматривает IGMP-сообщения хостов и знает, на каком порту реально подписчик. Дальше multicast-кадр идёт только этим портам.

Это L2-оптимизация, использующая L3-протокол как источник сигнала. Формально свитч остаётся L2-устройством — он не роутит, только фильтрует флудинг.

## В VXLAN multicast mode

Полная цепочка как IGMP встраивается:

1. Админ: `ip link add vxlan10 type vxlan id 10 dev eth0 group 239.1.1.1`
2. VXLAN-модуль ядра подписывается на `239.1.1.1` через `eth0`
3. Ядро автоматически шлёт **IGMP Membership Report** → first-hop router
4. Router запоминает: «за интерфейсом к этому хосту есть подписчик на 239.1.1.1»
5. Включает этот интерфейс в OIL своей multicast FIB для группы
6. Отправляет PIM Join вверх к RP, чтобы попасть в дерево группы

Без шага 3 роутер не будет сливать BUM-трафик VNI 10 к этому VTEP'у, даже если PIM-дерево группы где-то построено — он просто не знает, что за его интерфейсом есть слушатель.
