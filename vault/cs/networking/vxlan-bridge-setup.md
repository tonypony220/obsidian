# VXLAN + Bridge Setup

---

```
   ЧТО УЖЕ ЕСТЬ (underlay):

   Router-1 ──── L3-сеть ──── Router-2
   eth0                       eth0
   10.0.0.1                   10.0.0.2

   оба роутера пингуют друг друга по IP
   хостов нигде ещё нет, VXLAN ещё нет


   ЧТО СОБИРАЕМ (overlay поверх):

   host ── veth ── [ br0 ] ── vxlan10 ── eth0 ── underlay ── eth0 ── vxlan10 ── [ br0 ] ── veth ── host
                  L2-свитч    туннель    физ.                физ.    туннель   L2-свитч
```

**TL;DR:** На каждом роутере у нас только underlay (`eth0` в L3-сеть). Чтобы хосты на разных сайтах оказались в одном L2-сегменте, добавляем **VXLAN-интерфейс** (делает encap/decap поверх underlay) и **bridge** (соединяет локального хоста и туннель в один L2). Bridge обязателен, потому что VXLAN-интерфейс — точка инкапсуляции, не свитч.

## Прежде чем собрать — зачем вообще bridge

Главное правило:

> **Bridge нужен там, где надо соединить несколько L2-интерфейсов в один сегмент. Если интерфейс один — bridge не нужен.**

Два базовых сценария, на которых это видно.

### Сценарий A — один локальный хост, bridge НЕ нужен

Host подключён к роутеру одним линком (GNS3-линк = виртуальный кабель между контейнерами):

```
  [ host ]                        [ router ]
   eth0 ════════════════════════════ eth1
   10.0.0.2/24                       10.0.0.1/24
```

```bash
# на роутере
ip addr add 10.0.0.1/24 dev eth1
ip link set eth1 up
```

Хост и роутер в одном L2-сегменте физически (через GNS3-линк). Никаких "нескольких интерфейсов в один сегмент" нет — bridge не нужен. `ip addr` навешивается прямо на `eth1`.

### Сценарий B — два локальных хоста, нужен bridge

Два хоста подключены к роутеру. Задача — оба в одной подсети, видят друг друга по L2:

```
  [ host1 ]━━━ eth1 ─┐
                     ├── ??? ── [ router stack ]
  [ host2 ]━━━ eth2 ─┘
```

Без bridge: если дать `eth1` и `eth2` разные IP-подсети, получится маршрутизация — роутер будет форвардить между ними на L3, но это не **один L2-сегмент** (broadcast между ними не пройдёт, ARP не пройдёт).

С bridge — два интерфейса объединяются в один L2:

```
  [ host1 ]━━━ eth1 ─┐
                     ├── br0 (IP 10.0.0.1/24) ─── [ router stack ]
  [ host2 ]━━━ eth2 ─┘
```

```bash
ip link add br0 type bridge
ip link set br0 up
ip link set eth1 master br0
ip link set eth2 master br0
ip addr add 10.0.0.1/24 dev br0        # IP на br0, не на eth1/eth2
```

Теперь `br0` — виртуальный свитч. `eth1` и `eth2` — его порты. Хосты `10.0.0.x` видят друг друга, broadcast флудится между портами, ARP работает.

Именно здесь появляется **необходимость в bridge** — когда из нескольких интерфейсов надо сделать один L2-сегмент.

### Сценарий C — наш BADASS-случай

Два роутера, у каждого по одному локальному хосту. На каждом роутере надо соединить **два L2-интерфейса** (к локальному хосту + VXLAN к удалённому) в один сегмент. Это тот же паттерн, что в B — только вместо второго ethernet-интерфейса здесь VXLAN-интерфейс. Дальше разбираем именно этот случай.

## Что есть до начала

На каждом роутере — **только underlay**:

```
  Router-1              Router-2
  ┌─────────┐           ┌─────────┐
  │ eth0    │           │ eth0    │
  │ 10.0.0.1│ ── L3 ──  │ 10.0.0.2│
  └─────────┘           └─────────┘
```

- Между роутерами настроена L3-сеть (static routes или OSPF)
- `ping 10.0.0.2` с Router-1 работает
- **Никаких хостов на роутерах ещё нет.** `veth-host` появится только тогда, когда мы его создадим
- Никакого VXLAN, никакого bridge — пусто

## Шаг 1 — создаём VXLAN-интерфейс

```bash
ip link add vxlan10 type vxlan \
    id 10 \                    # VNI
    dstport 4789 \             # UDP порт
    dev eth0 \                 # через какой физ. интерфейс слать
    local 10.0.0.1             # свой IP в underlay
ip link set vxlan10 up
```

Появляется виртуальный интерфейс `vxlan10`. Для ядра — обычный интерфейс (как `eth0`), но внутри него логика:

- "Если в меня положили L2-кадр — я добавляю VXLAN+UDP+IP+Ethernet заголовки и отправляю через `eth0`"
- "Если из underlay пришёл UDP-пакет на порт 4789 с моим VNI — я снимаю заголовки и выдаю inner-кадр"

Пока к `vxlan10` никто не подключён — он сам по себе, трафика нет.

## Шаг 2 — создаём bridge и подключаем в него локального хоста + туннель

```bash
ip link add br0 type bridge
ip link set br0 up

ip link set vxlan10 master br0     # порт 1: туннель
ip link set veth-host master br0   # порт 2: локальный хост
```

`br0` — виртуальный L2-свитч. У него теперь два порта:

```
                 ┌──── br0 (L2-свитч) ────┐
                 │                        │
     veth-host ──┤ порт 1        порт 2   ├── vxlan10
      (к хосту)  │                        │   (к удалённому VTEP)
                 └────────────────────────┘
```

С точки зрения `br0` оба порта равноправны. Кадр пришедший с одного порта флудится/форвардится на другой по обычной L2-логике свитча.

## Итоговая вертикаль на одном роутере

```
  host ──── veth ──── [ br0 ] ──── vxlan10 ──── eth0 ──── underlay
   │         │         │             │           │
   L2       L2-кабель  L2-свитч      encap       L3-интерфейс
```

Два разных способа "подключения" для `vxlan10`:

- **vxlan10 ↔ underlay** — через параметр `dev eth0 local 10.0.0.1` при создании. Это внутренняя логика ядра, не `ip link set master`
- **vxlan10 ↔ bridge** — через `ip link set vxlan10 master br0`. Тут `vxlan10` выступает как обычный порт свитча

VXLAN не "втыкается в L3-сеть" — он **использует L3-сеть как транспорт** для инкапсулированных пакетов.

## Растянутый мост — главная ментальная модель

Если смотреть только на один роутер — видно `br0` с двумя портами. Если охватить обе стороны сразу — становится видно что происходит на самом деле:

```
        br0 на Router-1                              br0 на Router-2
      ┌────────────────────┐                       ┌────────────────────┐
host1 │  eth1              │                       │              eth1  │ host2
 ─────┤                    │                       │                    ├─────
      │           vxlan10  │═══════════════════════│  vxlan10           │
      └────────────┬───────┘  L2 кадры в UDP-      └───────┬────────────┘
                   │          туннеле через               │
                   │          underlay                    │
                   ▼                                      ▼
                  eth0 ───────── L3 ────────── eth0
               10.0.0.1                        10.0.0.2
                              UNDERLAY
```

Оба `br0` — локальные сущности на своих роутерах, физически разные. Но соединённые через VXLAN они ведут себя как **один растянутый виртуальный свитч**. С точки зрения `host1` и `host2` — они включены в один свитч на четыре порта:

```
        логическая модель для хостов:
        
   host1 ──┤ port              port ├── host2
           │   единый виртуальный   │
           │        свитч           │
           └────────────────────────┘
```

Хосты не знают ничего про туннель, encap/decap, underlay. Для них это просто L2. Именно это и даёт [[vxlan|VXLAN]] — иллюзию единого свитча поверх маршрутизируемой сети.

Физика под иллюзией:
- На каждом роутере — свой локальный bridge
- VXLAN-интерфейсы переносят кадры между bridge'ами через L3
- Вместе они образуют "распределённый свитч" на уровне поведения

## Зачем bridge — почему нельзя `veth-host` прямо в `vxlan10`

Короткий ответ: **VXLAN-интерфейс — это точка инкапсуляции, а не свитч**. К нему нельзя подключить другой интерфейс как порт.

Чуть подробнее:

- `ip link set veth-host master vxlan10` — **не сработает**. `master` можно указывать только для устройств которые умеют быть "хозяином" интерфейсов (bridge, bond, team). `vxlan10` к таким не относится
- Интерфейс `vxlan10` — "конечная точка": кадры либо кладут в него (он encap'ит), либо достают из него (после decap). Он не коммутирует кадры между несколькими интерфейсами
- Нужен отдельный объект, который:
  1. Принимает кадры с нескольких портов
  2. Решает куда их переслать (по dst MAC)
  3. Флудит broadcast/unknown
- Этот объект — **Linux bridge**. Это буквально виртуальный L2-свитч

Плюс ещё один аргумент: если на роутере **несколько локальных хостов** в одном VNI, они должны общаться друг с другом без ухода в туннель. Bridge это даёт из коробки. Без него каждый локальный кадр между host-1 и host-2 шёл бы через encap → underlay → decap → обратно, что бессмысленно.

```
  без bridge (не собирается):
     veth-host-1 ──??── vxlan10        host-1 и host-2 не видят друг друга,
     veth-host-2 ──??── vxlan10        и vxlan10 не знает откуда брать кадры

  с bridge:
     veth-host-1 ─┐
                  ├── br0 ── vxlan10 ── underlay
     veth-host-2 ─┘
     host-1 ↔ host-2 локально через br0
     оба ↔ удалённые хосты через vxlan10
```

В P2 BADASS на каждом роутере по одному хосту, но bridge всё равно нужен — это канонический способ подключить `vxlan10` к локальному интерфейсу в Linux.

## Что дальше

Вертикаль собрана, но один важный вопрос остался: **как `vxlan10` узнаёт на какой удалённый VTEP слать кадр?** Внутри `vxlan10` лежит FDB (таблица MAC → remote VTEP IP), но кто её заполняет — это и есть суть выбора режима ([[vxlan-modes|static / multicast / EVPN]]).
