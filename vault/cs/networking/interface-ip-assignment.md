# Когда интерфейсу нужен IP

---

```
  endpoint (IP нужен)           transit (IP не нужен)
  ────────────────────          ─────────────────────
  host сам шлёт/принимает       host только пересылает
  пакеты с этим src/dst IP      L2-кадры в другой интерфейс
  или является gateway'ем       (bridge-порт, trunk-порт)
  для этого сегмента
```

**TL;DR:** IP живёт на интерфейсе, а не на машине. Главный тест: **интерфейс сам терминирует IP-трафик (endpoint) или просто форвардит L2 (transit)?** Endpoint → IP нужен. Transit (bridge-порт, trunk-порт, свитч-порт) → не нужен. Один и тот же тип интерфейса может быть endpoint в одной конфигурации и transit в другой — роль решает, не тип.

## Тест-вопрос

Мысленно перехвати кадр на этом интерфейсе:

- Host **достаёт его из L2 и отдаёт в IP-стек** (локально обрабатывает `dst IP`, маршрутизирует дальше, отвечает на ARP как владелец IP) → **IP нужен**.
- Host **просто перекладывает в другой L2-интерфейс по `dst MAC`** → IP не нужен.

## Пример 1. Обычный хост

```
  ┌──────────────────────┐
  │ host                 │
  │ eth0 = 10.0.0.5/24   │  ← endpoint
  └──────────────────────┘
           │
      gateway 10.0.0.1
```

Хост шлёт пакеты с `src IP = 10.0.0.5`, принимает с `dst IP = 10.0.0.5`. Без IP он не участник сети.

## Пример 2. Роутер с двумя ногами

```
  LAN 192.168.1.0/24               WAN 203.0.113.0/24
          │                                 │
  ┌───────┼─────────────────────────────────┼──────┐
  │   eth0=192.168.1.1/24        eth1=203.0.113.5/24
  │              router (маршрутизирует LAN ↔ WAN)  │
  └─────────────────────────────────────────────────┘
```

Оба интерфейса — endpoint каждый в своей подсети, оба отвечают на ARP как gateway. IP нужен на обоих.

## Пример 3. Linux bridge как «тупой свитч» (P2 setup)

Полная картина — чтобы было видно куда идёт underlay eth0:

```
  HOST-A (30.1.1.1/24)                           HOST-B (30.1.1.2/24)
    │ eth0                                           │ eth0
    │                                                │
    │ ═══ L2 cable ═══                               │ ═══ L2 cable ═══
    ▼                                                ▼
  ┌───────────────────────────────┐        ┌───────────────────────────────┐
  │ ROUTER-A                      │        │ ROUTER-B                      │
  │                               │        │                               │
  │  eth1 (БЕЗ IP) ─┐             │        │          ┌─ eth1 (БЕЗ IP)     │
  │                 ├──▶ br0      │        │     br0 ◀┤                    │
  │  vxlan10 ───────┘   (БЕЗ IP)  │        │ (БЕЗ IP) └─ vxlan10 (БЕЗ IP)  │
  │  (БЕЗ IP)              │      │        │              ▲                │
  │     │                  │      │        │              │ декапсуляция   │
  │     │ инкапсуляция в UDP      │        │              │                │
  │     ▼                         │        │              │                │
  │  eth0 = 10.0.0.1/24 ◀─ IP!    │        │  IP! ─▶ eth0 = 10.0.0.2/24    │
  └──────────────┬────────────────┘        └──────────────┬────────────────┘
                 │                                        │
                 │           UDP(VXLAN)                   │
                 └──────────▶┌──────────┐◀────────────────┘
                             │  switch  │  underlay L2
                             └──────────┘
```

На роутере IP **только на underlay-eth0** — потому что это endpoint L3-туннеля (VTEP source). `eth1`, `br0`, `vxlan10` — transit: кадр от host-A проходит `eth1 → br0 → vxlan10` не попадая в IP-стек роутера. Роутер здесь **не участник overlay-сегмента `30.1.1.0/24`**, он просто бриджит кадры между host-портом и туннелем.

## Пример 4. Тот же bridge, но с IP (Docker `docker0`)

```
  ┌──────────────────────────────────────────────────┐
  │ host (Docker daemon)                             │
  │                                                  │
  │   veth-c1 ──┐                                    │
  │   veth-c2 ──├──▶ docker0 = 172.17.0.1/24 ◀─ IP!  │
  │   veth-c3 ──┘         (и bridge, и gateway)      │
  │                              │                   │
  │                              │ NAT / routing     │
  │                              ▼                   │
  │                          eth0 наружу             │
  └──────────────────────────────────────────────────┘

  контейнеры: 172.17.0.2, 172.17.0.3, ... → default via 172.17.0.1
```

Тот же L2-бридж, но **с IP**. Почему? `docker0` играет **две роли одновременно**: L2-свитч между контейнерами **и** gateway для них (172.17.0.1). Когда контейнер шлёт пакет наружу — `dst MAC = docker0`, host достаёт кадр из L2 через docker0 в IP-стек и маршрутизирует/NAT'ит дальше.

**Урок:** bridge — L2-устройство, IP на нём появляется только если host хочет быть endpoint через этот бридж. В P2 — не хочет, в Docker — хочет.

## Пример 5. VXLAN в routed-режиме (контраст с P2)

```
  ┌────────────────────────────────────────────┐
  │ router                                     │
  │                                            │
  │   vxlan10 = 172.16.0.1/24 ◀─ IP!           │
  │      │       (L3-туннель, НЕ в бридже)     │
  │      │                                     │
  │   eth0 = 10.0.0.1/24 ← underlay            │
  └────────────────────────────────────────────┘

  ip route add 192.168.0.0/16 via 172.16.0.2 dev vxlan10
```

Тот же тип интерфейса, что в P2, но **не в бридже** — используется как обычный routed-интерфейс. Роутер сам шлёт/принимает пакеты через него → endpoint → IP нужен.

**Один и тот же `vxlan10`: в P2 без IP, тут с IP. Роль разная, ответ разный.**

## Пример 6. Router-on-a-stick (VLAN subinterfaces)

```
  ┌────────────────────────────────────────────┐
  │ router                                     │
  │                                            │
  │   eth0 ← trunk, БЕЗ IP                     │
  │    │                                       │
  │    ├── eth0.10 = 192.168.10.1/24 ◀─ IP! VLAN 10
  │    └── eth0.20 = 192.168.20.1/24 ◀─ IP! VLAN 20
  └────────────────────────────────────────────┘
```

`eth0` без IP — переносит тегированные кадры нескольких VLAN'ов, сам ничего не терминирует. Subinterface'ы `eth0.10` / `eth0.20` — endpoint'ы в своих VLAN'ах (gateway'и для inter-VLAN routing), IP нужен.

## Пример 7. Loopback

```
  ┌──────────────────────────┐
  │ router                   │
  │                          │
  │   lo = 127.0.0.1/8       │
  │   lo:1 = 10.255.255.1/32 │  ← router-id для BGP/OSPF
  └──────────────────────────┘
```

Виртуальный интерфейс, физически никуда не подключён, но **всегда endpoint** для локальных сервисов. BGP/OSPF часто используют IP с loopback как router-id — потому что физические линки могут упасть, а loopback всегда up.

## Сводное правило

| Роль интерфейса | IP |
|---|---|
| Endpoint: host сам шлёт/принимает IP-пакеты | ✅ |
| Gateway для подсети (отвечает на ARP как gateway) | ✅ |
| Endpoint туннеля (VPN, VXLAN в routed-режиме, GRE) | ✅ |
| Loopback / management | ✅ |
| Bridge-порт (физический порт или вложенный интерфейс в bridge) | ❌ |
| Bridge сам, если используется как чистый L2-свитч | ❌ |
| Trunk-порт без subinterface'ов | ❌ |
| Физический порт свитча / свитч-подобного устройства | ❌ |

Правило короткое: **IP на интерфейсе ⇔ интерфейс терминирует IP-трафик**. Тип интерфейса (eth, bridge, vxlan, vlan) ни о чём не говорит сам по себе — роль решает.
