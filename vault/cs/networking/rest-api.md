# REST API

moc: [[networking-moc]]
next: [[graphql]] [[grpc]] [[api-gateway]]

---

```
GET    /users/42      ──▶ Read   (200 OK)
POST   /users         ──▶ Create (201 Created)
PUT    /users/42      ──▶ Update (200 OK)
DELETE /users/42      ──▶ Delete (204 No Content)
```

Архитектурный стиль для API, основанный на HTTP-методах и ресурсах. Каждый URL — ресурс, HTTP-метод — действие.

## Ключевые принципы

- **Ресурсы** — URL обозначает сущность: `/users/42`, `/posts/1/comments`
- **HTTP-методы** — `GET` (чтение), `POST` (создание), `PUT/PATCH` (обновление), `DELETE` (удаление)
- **Stateless** — каждый запрос содержит всё необходимое, сервер не хранит сессию
- **Кэширование** — по URL тривиально: `GET /users/42` кэшируется по ключу URL

## Сильные стороны

- Простота — HTTP-методы + URL, понятно без документации
- Кэширование — CDN, браузер, прокси кэшируют по URL из коробки
- Инструменты — curl, Postman, браузер — всё работает сразу
- Стандартизация — HTTP status codes, content negotiation

## Слабые стороны

- **Overfetching** — `GET /users/42` возвращает все поля, даже если нужно только имя
- **Underfetching** — для связанных данных нужны цепочки запросов
- **Версионирование** — `/v1/users` vs `/v2/users`, сложно эволюционировать

## Когда использовать

- Простой CRUD с 1-5 сущностями
- Публичное API — максимально понятно для внешних разработчиков
- Там где важно кэширование (CDN-friendly)
