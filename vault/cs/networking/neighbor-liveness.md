# Neighbor Liveness & Convergence

moc: [[l3-routing-moc]]
back: [[rib-vs-fib]]
next: [[rib-vs-fib]], [[frrouting]]

---

```
  ┌── Router A ──┐                          ┌── Router B ──┐
  │              │   Hello каждые 10 сек    │              │
  │   ospfd      │ ───────────────────────▶ │   ospfd      │
  │              │ ◀─────────────────────── │              │
  │              │                          │              │
  │   таймер ──▶ │   "не слышал 40 сек →    │              │
  │              │    сосед мёртв"          │              │
  └──────────────┘                          └──────────────┘
         │
         ▼
   протокол пересчитывает маршруты
   → обновляет zebra RIB
   → zebra обновляет FIB
```

Ядро само не замечает что сосед "за хопом" умер — оно видит только свои интерфейсы (см. [[packet-forwarding]]). Живость соседей отслеживают **сами протоколы маршрутизации**.

## Зачем это нужно

Пакет идёт `A → B → C`. Внезапно `B` упал (кабель, питание, kernel panic). С точки зрения `A`:
- линк до `B` — может быть жив (upstream-свитч работает)
- `A` продолжает слать пакеты на next-hop `B`
- пакеты уходят в чёрную дыру

**А должен понять что `B` мёртв** и переключиться на другой маршрут (если есть). Для этого протоколы маршрутизации непрерывно проверяют соседей.

## Три механизма детекции

### 1. Сам линк упал (мгновенно)

Если интерфейс ушёл в DOWN (`ip link show eth0` → state DOWN) — ядро **сразу** удаляет все маршруты через него. Это бесплатно, ждать не надо. Протокол тоже узнаёт через netlink-уведомление и пересчитывает.

Проблема: работает только для **прямых** соседей на том же линке. Если `B` упал, но свитч между `A` и `B` живой — `A` видит линк UP, а `B` нет.

### 2. Hello / Keepalive — периодический heartbeat

Каждый протокол шлёт маленькие пакеты соседу с определённым интервалом. Если N подряд не пришло — сосед считается мёртвым.

| Протокол | Интервал | Таймаут (сосед мёртв) |
|---|---|---|
| OSPF Hello | 10 сек | 40 сек (4 пропущенных) |
| BGP Keepalive | 30 сек | 90 сек (3 Hold timer) |
| IS-IS Hello | 10 сек | 30 сек |

**Почему такие большие цифры** — это trade-off. Меньше интервал = быстрее детекция, но больше служебного трафика и риск false-positive (перегруженный CPU на секунду задержал ответ — считать мёртвым?). Для IGP в стабильной сети 10 сек — разумно.

### 3. BFD — быстрый детектор за миллисекунды

**Bidirectional Forwarding Detection** (RFC 5880) — отдельный лёгкий протокол, заточенный только под "жив/не жив". Умеет детектить падение за **150–300 мс** (три пропущенных пакета с интервалом 50–100 мс).

```
  ┌── Router A ──┐                          ┌── Router B ──┐
  │  OSPF        │    Hello / 10 сек ─────▶ │  OSPF        │
  │  BGP         │    Keepalive / 30 сек ─▶ │  BGP         │
  │  BFD ═══════════  50 мс ═════════════▶  BFD            │
  │              │                          │              │
  │  BFD упал ──▶ "сосед мёртв"             │              │
  │   │          нотифицирует OSPF и BGP    │              │
  │   ▼                                     │              │
  │  OSPF/BGP мгновенно сносят маршруты     │              │
  └──────────────┘                          └──────────────┘
```

BFD сам не знает про маршруты — он просто стучит. Когда сосед перестаёт отвечать, BFD **кидает уведомление** в OSPF/BGP, и те сразу пересчитывают маршруты, не дожидаясь своих таймаутов. В проде BFD часто включают поверх OSPF/BGP ради **быстрой сходимости**.

## Что происходит после детекции — кто пушит в FIB

Важный нюанс: **протоколы не пушат маршруты в FIB напрямую.** Они обновляют RIB через zebra, а zebra уже сама решает и пушит в FIB.

```
1. ospfd не получил Hello от соседа за 40 сек
2. ospfd: "сосед мёртв, все его маршруты инвалидны"
3. ospfd пересчитывает свои маршруты (Dijkstra)
4. ospfd → zebra: "удали маршруты X, Y, Z; добавь A, B"
5. zebra обновляет RIB (свою таблицу кандидатов)
6. zebra для каждого изменённого префикса:
   - смотрит оставшихся кандидатов (BGP, static, другие OSPF-маршруты)
   - выбирает winner по AD/metric
7. zebra → kernel (netlink): обновляет FIB
8. ядро теперь форвардит по новому FIB
```

То есть **цепочка**: протокол → zebra → kernel. Протокол сам в FIB не лезет, это полномочие zebra. Зебра — **единственный** компонент, который общается с ядром на тему маршрутов.

**Почему так:** если бы каждый демон пушил в ядро напрямую, они бы затирали друг друга. Нужен арбитр который знает про всех и выбирает winner по общему правилу.

## Convergence time — что это

**Convergence** (сходимость) — время от падения до полного восстановления маршрутизации. Складывается из:

```
  детекция падения  +  пересчёт на всех роутерах  +  обновление FIB
```

- С **Hello/Keepalive** — минимум десятки секунд (40 сек у OSPF — уже это)
- С **BFD** — сотни миллисекунд до 1–2 сек

В проде это критично. При падении магистрального линка крупного оператора 30 секунд "чёрной дыры" = миллионы упавших соединений. Поэтому везде пихают BFD, fast reroute, pre-computed backup paths.

## В BADASS

В P1 всё это ещё не играет — демоны подняты, но сессий нет. В P3 появятся реальные OSPF-сессии между роутерами, и можно будет руками уронить линк в GNS3 (отключить кабель) и посмотреть через `vtysh -c "show ip ospf neighbor"` как сосед переходит в `DOWN`, как маршруты переезжают.
