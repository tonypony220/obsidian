# RIB vs FIB

moc: [[l3-routing-moc]]
next: [[packet-forwarding]], [[linux-routing-table]], [[neighbor-liveness]], [[control-plane-data-plane]]

---

```
  ┌──── userspace (FRR) ─────────────────────┐
  │                                          │
  │   bgpd ─────▶ "я знаю 10.0.0.0/24        │
  │                via 192.168.1.1"          │
  │                          ╲               │
  │   ospfd ────▶ "я тоже знаю 10.0.0.0/24   │
  │                via 192.168.1.2"          │
  │                          ╲   ╲           │
  │                           ▼   ▼          │
  │                        ┌────────┐        │
  │                        │ zebra  │        │
  │                        │  RIB   │        │  ← ВСЕ кандидаты
  │                        └───┬────┘        │
  │                            │  выбор      │
  │                            │  лучшего    │
  └────────────────────────────┼─────────────┘
                               ▼ netlink
  ┌──── kernel ─────────────────────────────┐
  │                        ┌────────┐       │
  │                        │  FIB   │       │  ← только winners
  │                        └────────┘       │   (ip route show)
  │                            │            │
  │                            ▼            │
  │                      форвардинг пакетов │
  └─────────────────────────────────────────┘
```

До этого мы видели **одну** таблицу маршрутов — ту, что показывает `ip route show`. Это **FIB**. Но когда появляются протоколы маршрутизации (OSPF, BGP), возникает **вторая** таблица — **RIB** в userspace. Разберём зачем.

## Проблема — один префикс, много источников

Представь роутер, к которому приходит информация про сеть `10.0.0.0/24` сразу из нескольких источников:

- **OSPF-сосед** говорит: "иди через меня, через `192.168.1.2`, cost 20"
- **BGP-сосед** говорит: "иди через меня, через `192.168.1.1`, AS-path [65002, 65003]"
- **Админ** прописал static: "иди через `192.168.1.5`"
- **Connected** — возможно одна из подсетей напрямую подключена

Все четыре источника хотят положить запись в таблицу ядра. Но в ядре можно держать **один** активный маршрут на префикс (с одинаковой метрикой — ECMP, но это частный случай).

**Кто-то должен выбрать.** Это делает [[frrouting|zebra]].

## RIB — Routing Information Base

RIB — это **внутренняя таблица zebra в userspace**, где хранятся **все кандидаты от всех источников**. Один префикс может иметь несколько записей — по одной от каждого протокола.

```
RIB в zebra:

10.0.0.0/24  [OSPF]    via 192.168.1.2  cost=20
10.0.0.0/24  [BGP]     via 192.168.1.1  as-path=[65002,65003]
10.0.0.0/24  [Static]  via 192.168.1.5
10.0.0.0/24  [Connected] dev eth0
```

RIB = **всё что я знаю** про маршруты. Superset всех мнений.

## FIB — Forwarding Information Base

FIB — это **таблица в ядре** (та самая, что видна через `ip route show`). В ней **только winners** — по одному маршруту на префикс, выбранных zebra'ой.

```
FIB в ядре (ip route show):

10.0.0.0/24 via 192.168.1.2 dev eth0 proto ospf
```

FIB = **то, по чему реально форвардятся пакеты**. Это то, что использует ядро для [[packet-forwarding|lookup'а]] при форвардинге.

## Как выбирается winner — Administrative Distance

Zebra выбирает по правилу **administrative distance (AD)** — "насколько я доверяю этому источнику". Меньше = приоритетнее:

| Источник | AD |
|---|---|
| Connected | 0 |
| Static | 1 |
| eBGP (внешний) | 20 |
| OSPF | 110 |
| IS-IS | 115 |
| RIP | 120 |
| iBGP (внутренний) | 200 |

В примере выше победит **Connected** (AD=0). Если connected не было бы — **Static** (1). Если ни того ни другого — **eBGP** (20). И так далее.

Логика:
- Connected очевиден, ядро уверено
- Static прописал админ, он знает лучше
- eBGP — внешние маршруты, более специфичные чем внутренние IGP
- OSPF — внутренний IGP, но менее приоритетен чем внешний BGP
- iBGP в самом низу — часто это транзитные маршруты, лучше иметь их как "last resort"

Если два источника **одинаковые** (два OSPF-маршрута до одной сети) — сравнивают **метрику внутри протокола** (cost в OSPF, AS-path в BGP).

## Зачем вообще разделять

### 1. Конкуренция источников

Главная причина. Без разделения непонятно как рассудить между OSPF и BGP — нужна структура, где видны оба кандидата, и механизм выбора.

### 2. Fallback при падении

Если лучший маршрут умирает — zebra сразу берёт следующий из RIB и пушит в FIB. Без RIB пришлось бы заново запрашивать у всех протоколов.

```
OSPF-сосед упал → OSPF-маршрут удаляется из RIB
                → zebra смотрит следующего в RIB (Static, AD=1)
                → ставит его в FIB
                → трафик продолжает идти, минимальный downtime
```

**Важный нюанс — кто именно пушит в FIB.** Протоколы (`ospfd`, `bgpd`) сами **не трогают FIB**. Цепочка такая:

```
  ospfd детектит падение соседа  (см. [[neighbor-liveness]])
       │
       ▼
  ospfd → zebra: "убери мои маршруты X, Y, Z, добавь A, B"
       │
       ▼
  zebra обновляет RIB, выбирает новых winners
       │
       ▼
  zebra → kernel (netlink): обновляет FIB
       │
       ▼
  ядро форвардит по новому FIB
```

Протокол **инициирует** изменение (он детектит падение и знает что маршруты невалидны), но **арбитр и единственный писатель в FIB — zebra**. Это важно: если бы каждый демон пушил в ядро напрямую, они бы затирали друг друга. Zebra — единственная точка, которая видит всех кандидатов и решает по AD.

### 3. Производительность

FIB в ядре оптимизирован под **lookup на скорости провода**: trie-структуры, в железе — TCAM. Держать там все варианты от всех протоколов было бы медленно и накладно.

RIB в userspace может быть "раздутой" (миллионы записей) — это нормально, её не читают на каждый пакет. Читают только когда меняется топология.

### 4. Control plane vs data plane

Классическое разделение в сетевой архитектуре (см. [[control-plane-data-plane]] — это общий паттерн далеко за пределами сетей):

```
control plane:  кто-то думает,        ← RIB + протоколы
                считает, договаривается
                
data plane:     кто-то форвардит       ← FIB + ядро/ASIC
                пакеты как можно быстрее
```

Можно рестартовать/обновлять control plane, пока data plane продолжает форвардить по текущему FIB. Это называется **graceful restart** — применяется в проде чтобы не ронять трафик при обновлении роутинг-демонов.

## Где это смотреть

```bash
# FIB (то что в ядре, по чему реально идёт трафик)
ip route show
ip route show proto ospf      # фильтр по источнику

# RIB (то что zebra знает — все кандидаты)
vtysh -c "show ip route"
vtysh -c "show ip route 10.0.0.0/24"   # детали по префиксу
```

Пример вывода `show ip route` в [[frrouting|vtysh]]:

```
O>* 10.0.0.0/24 [110/20] via 192.168.1.2, eth0, 00:05:12
B   10.0.0.0/24 [20/0]   via 192.168.1.1, eth0, 00:03:45
S   10.0.0.0/24 [1/0]    via 192.168.1.5
```

- `O` = OSPF, `B` = BGP, `S` = static
- `>` = выбран best'ом в RIB
- `*` = установлен в FIB ядра
- `[110/20]` = `[AD/metric]`

Тут видно: OSPF победил (лучший AD после connected и static, но static выше — значит static тут не анонсился или был перебит). Wait, static=1, OSPF=110 — static должен был победить. Значит в этом примере static отсутствует, я напутал. Давай корректнее:

```
O>* 10.0.0.0/24 [110/20] via 192.168.1.2, eth0, 00:05:12   ← установлен в FIB
B   10.0.0.0/24 [20/0]   via 192.168.1.1, eth0             ← есть в RIB, не в FIB
```

Хотя eBGP AD=20 < OSPF AD=110, и должен был победить eBGP. Значит здесь либо iBGP (AD=200), либо OSPF предпочтён по политике. На практике такие сценарии детальнее — важно что **можно смотреть оба уровня** и видеть почему вышло так.

## Итог одной картинкой

```
  источники маршрутов               что видно пользователю
  ────────────────────              ──────────────────────

  connected ┐
  static    │
  OSPF      ├──▶ RIB (zebra) ──▶ FIB (kernel) ──▶ форвардинг
  BGP       │    "всё что знаю"    "что выбрал"
  ...       ┘
            
            control plane            data plane
            vtysh show ip route      ip route show
```

## В BADASS

В P1 FRR поставлен, но ничего не настроено — RIB у zebra есть, но почти пустой (только connected-маршруты с интерфейсов). В P3 появятся маршруты от OSPF и BGP/EVPN — вот тогда RIB станет содержательным, и концепция "выбор лучшего кандидата" заработает по-настоящему.
