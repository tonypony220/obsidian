# Packet Forwarding

moc: [[l3-routing-moc]]
next: [[linux-routing-table]], [[linux-bridge]]

---

```
         ┌─────────── ROUTER ───────────┐
         │                              │
  pkt ──▶│ eth0    ┌─────────┐   eth1   │──▶ pkt
  dst=   │  in ──▶ │ lookup  │ ──▶ out  │
  10.0.5 │         │ в FIB   │          │
         │         └─────────┘          │
         │    "dst=10.0.0.5 → eth1,     │
         │     next-hop=192.168.1.1"    │
         └──────────────────────────────┘
```

## Что делает роутер — одно предложение

Принимает пакет → смотрит `dst IP` → находит в **таблице маршрутов** куда его отправить → отправляет дальше. Всё.

Это называется **форвардинг** (forwarding). Не "маршрутизация" — маршрутизация это процесс **построения** таблицы (кто-то где-то посчитал пути). Форвардинг — само **действие** пересылки пакета по уже готовой таблице.

## Роутер vs свитч

Частая путаница. Оба "пересылают кадры", но работают на разных уровнях:

|                | Свитч (L2)                      | Роутер (L3)                         |
| -------------- | ------------------------------- | ----------------------------------- |
| Смотрит на     | MAC-адрес                       | IP-адрес                            |
| Область работы | один сегмент сети               | между сегментами                    |
| Таблица        | MAC-table (кто за каким портом) | routing table (префиксы → next-hop) |
| Знает про IP?  | нет                             | да                                  |
| Аналог в Linux | [[linux-bridge]]                | ядро с `ip_forward=1`               |

Свитч — это "внутри подъезда": соседи по лестничной клетке напрямую. Роутер — "между городами": связывает разные подъезды, районы, города.

## В Linux форвардинг встроен в ядро

Любой Linux-компьютер **умеет** быть роутером. Ядро уже содержит всю логику: принять пакет → глянуть таблицу → отправить. Но по умолчанию **выключено** — иначе твой ноут начал бы ретранслировать чужой трафик между Wi-Fi и Ethernet, что редко кому нужно.

Включается одной настройкой:

```bash
sysctl -w net.ipv4.ip_forward=1
```

После этого ядро начинает форвардить пакеты, у которых `dst IP` — не его собственный.

## Как пакет идёт через Linux-роутер (пошагово)

1. **Приём.** Пакет приходит на `eth0`, попадает в сетевой стек ядра.
2. **Решение "мне или не мне".** Ядро смотрит `dst IP`. Если это собственный IP роутера — отдаёт наверх (TCP/UDP → приложение). Если чужой — идёт на форвардинг.
3. **Lookup в FIB.** Ядро ищет самый длинный совпадающий префикс в таблице маршрутов (`ip route show`). Находит запись: `10.0.0.0/24 via 192.168.1.1 dev eth1`.
4. **ARP для next-hop.** Надо узнать MAC-адрес `192.168.1.1`. Если его нет в ARP-кэше — шлёт ARP-запрос.
5. **Отправка.** Пакет упаковывается в Ethernet-кадр с найденным MAC, отправляется через `eth1`.

На каждом роутере в цепочке повторяется то же самое. Пакет "прыгает" от next-hop'а к next-hop'у, пока не доходит до сети назначения.

## Таблица маршрутов — откуда она берётся

Ядро умеет **форвардить по таблице**. Но **кто кладёт записи в таблицу?** Три варианта (см. [[l3-routing-moc]]):

- **Connected** — сами подключённые сети, ядро добавляет автоматически
- **Static** — руками через `ip route add`
- **Dynamic** — протоколы маршрутизации (OSPF, BGP) через userspace-софт вроде FRR

## Мини-пример — Linux как роутер руками

Две сети, между ними Linux-машина с двумя интерфейсами:

```
  сеть A                 Linux-роутер                сеть B
  10.0.1.0/24  ──── eth0 │ eth1 ──── 10.0.2.0/24
                         │
                      ip_forward=1
```

```bash
# включить форвардинг
sysctl -w net.ipv4.ip_forward=1

# connected-маршруты ядро добавит само, когда ты поднимешь интерфейсы
ip addr add 10.0.1.1/24 dev eth0
ip addr add 10.0.2.1/24 dev eth1
ip link set eth0 up
ip link set eth1 up

# проверить таблицу
ip route show
# 10.0.1.0/24 dev eth0  proto kernel  scope link  src 10.0.1.1
# 10.0.2.0/24 dev eth1  proto kernel  scope link  src 10.0.2.1

# всё, хосты из сети A теперь могут пинговать сеть B через эту машину
```

Это **полноценный роутер**. Без Cisco, без FRR. Только ядро Linux и две команды.

## Зачем тогда BGP/OSPF/FRR

Пока у тебя 2 сети и 1 роутер — хватит и static. Как только появляются 3+ роутера и нетривиальная топология — руками становится невозможно. Нужны протоколы, чтобы роутеры сами договаривались.

Но физику форвардинга всё равно делает ядро. FRR только **наполняет таблицу** — само действие пересылки пакета происходит там же, где и в нашем ручном примере.
