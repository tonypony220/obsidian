# DHCP

moc: [[networking-moc]]
next: [[linux-network-interface]], [[linux-routing-table]]

---

```
   Client (no IP yet)              DHCP Server

        │   DISCOVER (broadcast)         │
        │ ───────────────────────────▶   │   "кто тут есть?"
        │                                │
        │   OFFER                        │
        │ ◀───────────────────────────   │   "вот тебе 192.168.1.100/24,
        │                                │    gateway .1, DNS 8.8.8.8,
        │                                │    lease 24 часа"
        │   REQUEST (broadcast)          │
        │ ───────────────────────────▶   │   "принимаю"
        │                                │
        │   ACK                          │
        │ ◀───────────────────────────   │   "зафиксировано"
```

**DHCP** (Dynamic Host Configuration Protocol, RFC 2131) — протокол, по которому хост автоматически получает IP и остальные сетевые параметры от сервера. Это то, что происходит когда ты подключаешься к Wi-Fi и "всё магически работает".

## Зачем нужен

Альтернатива — назначать адреса [[linux-network-interface|руками через `ip addr add`]] на каждой машине. Для офиса на 500 ПК — невозможно. Плюс:
- гости со своими ноутами
- телефоны, ТВ, IoT — всё что появляется и исчезает
- переезд в другой сегмент сети

DHCP решает это: **централизованный пул адресов, машины сами запрашивают на время**.

## Как машина знает что надо идти к DHCP

В конфиге интерфейса стоит режим "использовать DHCP":
- `netplan` / `/etc/network/interfaces` — `dhcp4: true`
- `NetworkManager` — чекбокс "Automatic (DHCP)"
- Windows — "Obtain an IP address automatically"

При старте интерфейса ОС запускает **DHCP-клиент** (`dhclient`, `dhcpcd`, `systemd-networkd`), который выполняет DORA-процедуру. Если в конфиге static IP — клиент не стартует.

## DORA — четыре шага

**D**iscover → **O**ffer → **R**equest → **A**ck.

### Почему всё через broadcast

У клиента **ещё нет IP**, он ещё не член сети. Адресовать некому, адресовать не от кого. Поэтому:
- **L2 broadcast** — `ff:ff:ff:ff:ff:ff` (всем в сегменте)
- **L3 broadcast** — `255.255.255.255` (ограниченный, не роутится)

DHCP-сервер — единственный в сегменте (обычно), кто слушает broadcast на UDP-порту 67. Клиент слушает 68.

### Детальнее по шагам

**1. DISCOVER** — клиент broadcast'ом "кто-нибудь есть?". В пакете передаёт свой **MAC** (единственный идентификатор, который у него уже есть).

**2. OFFER** — сервер видит DISCOVER, выбирает свободный IP из пула, формирует ответ с параметрами:
- IP + маска (`192.168.1.100/24`)
- default gateway
- DNS-серверы
- NTP-серверы (опционально)
- длительность аренды (`lease time`)

**3. REQUEST** — клиент broadcast'ом "принимаю этот offer от такого-то сервера". Broadcast, а не unicast — чтобы **другие DHCP-серверы** в сегменте тоже увидели и поняли что offer не выбран (у них может быть несколько серверов для отказоустойчивости).

**4. ACK** — выбранный сервер подтверждает, фиксирует аренду у себя. С этого момента IP забронирован за MAC-адресом клиента на `lease time`.

## Что выдаёт сервер (не только IP)

Полезная мысль: DHCP — **не только про IP**. Сервер отдаёт всё необходимое для полной сетевой настройки:

```
IP адрес:          192.168.1.100
Маска:             /24 (255.255.255.0)
Default gateway:   192.168.1.1         ← в [[linux-routing-table]] уйдёт как default
DNS:               8.8.8.8, 1.1.1.1
NTP:               pool.ntp.org
Lease time:        86400 сек (24ч)
DHCP server ID:    192.168.1.1
```

Одной транзакцией машина настраивается **полностью** — и сразу готова выходить в интернет.

## Lease и renewal

IP выдан не навсегда, а **на время** (lease). Зачем:
- клиент может уйти из сети, IP нужно вернуть в пул
- пул может быть меньше числа устройств (cycled)

Клиент **обновляет аренду** в середине lease (по умолчанию T1 = 50% времени). Если сервер жив — продлевает, если нет — пытается на T2 (87.5%), если и тогда нет — DORA заново.

## DHCP relay — когда сервер в другой подсети

Проблема: DHCP-запросы идут broadcast'ом, broadcast **не роутится** (роутер не форвардит broadcast). Значит DHCP-сервер должен быть в том же сегменте что и клиент.

В корпоративной сети 100 подсетей — ставить 100 DHCP-серверов накладно. Решение: **DHCP relay** (RFC 3046). Роутер-relay перехватывает DHCP-пакеты в своём сегменте, упаковывает в unicast и пересылает на центральный DHCP-сервер. Ответ — тем же путём обратно.

Так один DHCP-сервер обслуживает сотни VLAN'ов.

## Безопасность — чему верить

DHCP исторически **не имеет аутентификации**. Это источник атак:

- **Rogue DHCP** — кто-то поставил свой сервер в сегменте, отдаёт свой IP как default gateway → ты пускаешь весь трафик через атакующего (MITM).
- **DHCP starvation** — атакующий шлёт миллион DISCOVER с фейковыми MAC'ами, выжирает весь пул, легитимные клиенты не получают IP.

Защита — на уровне свитча: **DHCP snooping** (свитч знает какие порты — trusted, пропускает только оттуда OFFER/ACK).

## В BADASS

Субъект требует **"No IP address should be configured by default"** — то есть образы голые, DHCP отключен. Все адреса в P2–P3 назначаются руками через `ip addr add` в `vtysh` или `ifconfig` на хостах. Это учебная среда — в реальном дата-центре, конечно, всё через DHCP или IPAM.
