```
         физический свитч (один)
   ┌──────────────────────────────────┐
   │                                  │
  PC-1 ┤ port 1  [VLAN 10]            │
  PC-2 ┤ port 2  [VLAN 10]            │
  PC-3 ┤ port 3  [VLAN 20]            │  ← одна железка,
  PC-4 ┤ port 4  [VLAN 20]            │     два логических
   │                                  │     broadcast-домена
   └──────────────────────────────────┘
   
   PC-1 ↔ PC-2 видят друг друга (один VLAN)
   PC-1 ↔ PC-3 НЕ видят (разные VLAN, изолированы)
```

**TL;DR:** VLAN (Virtual LAN, 802.1Q) — способ разделить один физический L2-сегмент на несколько **логических** broadcast-доменов. Делается через 4-байтный тег в Ethernet-кадре, указывающий VLAN ID (12 бит → 4094 сегмента). Это **логика внутри одного свитча/LAN**, не через роутеры.

## Проблема — один broadcast-домен на большой сети

Подключили 100 компьютеров к одному свитчу. Все в одном L2-сегменте:

- **Broadcast-шум** — каждый ARP, DHCP, обнаружение соседей летит ко всем 100 машинам. CPU тратится на обработку чужого трафика.
- **Нет изоляции** — любая машина может слать пакеты любой другой, видеть их broadcast'ы. Плохо для безопасности и сегрегации по отделам.
- **Единая failure domain** — один broadcast storm кладёт всю сеть.

Можно купить **два свитча** и разделить физически — работает, но дорого и inflexible: перенёс сотрудника в другой отдел — перетыкать кабели.

## Что такое VLAN

VLAN — **логическое** разделение одного физического свитча на несколько независимых L2-сегментов. На уровне пользователя выглядит как будто это разные свитчи; на уровне железа — один чип, но с виртуальными перегородками.

Ключевые свойства:
- Порты свитча назначаются в определённые VLAN'ы (по номеру ID)
- Трафик между VLAN'ами **не ходит** на L2 — только через L3 (роутер/L3-свитч)
- Broadcast внутри VLAN ограничен только портами этого VLAN
- Один физический линк между свитчами может переносить трафик **нескольких** VLAN'ов через тегирование

## Как это работает на проводе — 802.1Q

Ethernet-кадр в "обычном" виде:

```
  ┌──────────┬──────────┬─────────────┬────────┬──────┐
  │ dst MAC  │ src MAC  │ EtherType   │payload │ FCS  │
  │  6 байт  │  6 байт  │   2 байта   │  ...   │ 4 B  │
  └──────────┴──────────┴─────────────┴────────┴──────┘
```

Стандарт **802.1Q** вставляет **4 байта** между src MAC и EtherType:

```
  ┌──────────┬──────────┬─────────┬─────────────┬────────┬──────┐
  │ dst MAC  │ src MAC  │  TAG    │ EtherType   │payload │ FCS  │
  │  6 байт  │  6 байт  │ 4 байта │   2 байта   │  ...   │ 4 B  │
  └──────────┴──────────┴─────────┴─────────────┴────────┴──────┘
                          │
                          ▼
                  ┌─────────────────┐
                  │ TPID  (16 бит)  │ = 0x8100 (маркер "тегированный кадр")
                  │ Prio  (3 бита)  │ = приоритет (QoS)
                  │ DEI   (1 бит)   │ = drop eligible
                  │ VID   (12 бит)  │ = VLAN ID (0–4095)
                  └─────────────────┘
```

Тег — это просто 12-битное число, говорящее "этот кадр принадлежит VLAN такому-то". Свитчи при форвардинге читают тег и **не выпускают** кадр на порты, которые не в том же VLAN.

Итого **4094 пригодных VLAN ID** (0 и 4095 зарезервированы). Для маленькой компании более чем достаточно, для облака с тысячами клиентов — уже мало.

## Access vs trunk — два типа портов

Порты свитча работают в одном из двух режимов:

### Access port

- Принадлежит **одному** VLAN
- Подключается к обычной машине (хост не знает про VLAN)
- Свитч добавляет тег на входе кадра в порт, снимает на выходе
- Хост видит обычный нетегированный Ethernet

```
  PC ── access port (VLAN 10) ── [switch]
  
  кадр от PC: без тега
  внутри свитча: с тегом VLAN 10
  кадр к PC: без тега
```

### Trunk port

- Переносит **несколько** VLAN'ов одновременно
- Подключается к другому свитчу/роутеру/гипервизору
- Кадры идут **с тегом** — получатель по тегу понимает в какой VLAN положить
- Один физический линк переносит все VLAN'ы разом

```
  [switch-1] ── trunk (VLAN 10, 20, 30) ── [switch-2]
  
  на линке идут тегированные кадры, перемешанные из всех VLAN'ов
  приёмник смотрит тег и разводит по нужному VLAN
```

Без trunk'ов пришлось бы пускать отдельный физический кабель для каждого VLAN между свитчами. Trunk решает это мультиплексированием.

## Native VLAN

На trunk-порту можно назначить **один** VLAN как **native** — его кадры идут **без тега**. Нужно для совместимости с устройствами, которые тегирование не понимают. По умолчанию native = VLAN 1.

Частый источник misconfiguration: если на разных концах trunk'а выставлены разные native VLAN'ы — нетегированные кадры попадают не туда, трафик протекает между сегментами (VLAN hopping — известная атака).

## Ограничения

1. **4094 сегмента** — не хватает для облачных платформ (AWS, Azure, GCP обслуживают миллионы тенантов).
2. **Только в пределах L2-сегмента** — VLAN не растягивается через роутеры. Через L3 — либо L3VPN, либо [[vxlan|VXLAN]], либо другие overlay-технологии.
3. **Весь underlay должен знать про VLAN'ы** — все свитчи по пути должны быть настроены на trunk и знать какие VLAN'ы пропускать.
4. **STP проблемы** — в больших L2-доменах Spanning Tree Protocol становится узким местом, сеть плохо масштабируется.
5. **Broadcast внутри VLAN** — внутри одного VLAN весь broadcast по-прежнему ходит на все порты; VLAN'ы **ограничивают** размер домена, но не отменяют его.

## Inter-VLAN routing

Трафик между VLAN'ами **не идёт на L2**. Чтобы PC в VLAN 10 общался с PC в VLAN 20 — нужен роутер:

```
  VLAN 10 ─┐
           ├─ [L3-свитч или роутер] ─ маршрутизирует между VLAN
  VLAN 20 ─┘
```

L3-свитч (современные Cisco Catalyst, Arista, Nokia) умеет и VLAN'ы, и L3-маршрутизацию в одном устройстве — даёт IP-адреса на интерфейсы каждого VLAN и роутит между ними.

## VLAN и VXLAN — две стороны одной задачи

Может показаться что VLAN и [[vxlan|VXLAN]] противоположны:
- VLAN **разделяет** одну сеть на сегменты
- VXLAN **объединяет** несколько сетей в один сегмент

На деле обе технологии решают одну и ту же задачу: **создать виртуальные L2-сегменты, не совпадающие с физической топологией**. Разница в стартовых условиях.

```
  стартовая физика                      результат
  ─────────────────                     ────────────
  
  ┌─ один физический сегмент ─┐
  │  свитч, все машины в нём  │  →  N логических сегментов   ← VLAN
  │  (по факту одна LAN)      │     ("разделение")
  └───────────────────────────┘
  
  ┌──── много физ. сегментов ─┐
  │  хост A ── L3 ── хост B   │  →  один логический сегмент  ← VXLAN
  │  (физически разные сети)  │     ("объединение")
  └───────────────────────────┘
```

Обе дают одинаковый **результат** — виртуальный broadcast-домен, независимый от физики. Приложение не видит разницы между "я в VLAN 100" и "я в VNI 100" — и там, и там это просто L2-сегмент со своей изоляцией и broadcast'ами.

Ощущение "противоположности" возникает из-за разного отношения к физике:
- VLAN работает **внутри** существующего физического L2 → кажется что "режет"
- VXLAN работает **поверх** физического L3 → кажется что "склеивает"

Но с точки зрения машины в сегменте обе технологии дают одно и то же: "мои соседи по broadcast-домену — вот эти хосты, остальные изолированы".

## Сравнение параметров

| | VLAN | VXLAN |
|---|---|---|
| Сегментов | 4094 | 16 миллионов |
| Транспорт | L2 (trunk-линки между свитчами) | L3 (маршрутизируемый underlay, UDP) |
| Overhead | 4 байта | 50 байт |
| Где применяется | один сайт, офис, внутри ДЦ | между хостами, между ДЦ, облака |
| Требования к underlay | L2-fabric с VLAN-awareness на всех свитчах | любая L3-сеть |
| Масштабируемость | ограничена STP, broadcast в сегменте | ограничена только control plane |

## VLAN-to-VXLAN mapping — работают вместе

В проде VLAN и VXLAN часто используются **одновременно**: VLAN внутри хоста/свитча, VXLAN между ними.

```
  хост A (гипервизор)                       хост B (гипервизор)
  ┌──────────────────┐                      ┌──────────────────┐
  │  VM1  VM2  VM3   │                      │   VM4  VM5       │
  │   │    │    │    │                      │    │    │        │
  │  VLAN VLAN VLAN  │                      │  VLAN VLAN       │
  │  100  100  200   │                      │  100  200        │
  │   │    │    │    │                      │    │    │        │
  │  [bridge]───────vxlan10 (VNI=100)────────[bridge]           │
  │  [bridge]───────vxlan20 (VNI=200)────────[bridge]           │
  └──────────────────┘                      └──────────────────┘
             ▲                                       ▲
             │         underlay L3-fabric            │
             └───────────────────────────────────────┘
```

Логика:
- Внутри хоста VM подключены в свои VLAN'ы (привычная модель виртуализации)
- На границе хоста — bridge, который мапит VLAN ID на VNI
- VXLAN переносит трафик через L3-underlay на удалённый хост
- На удалённом хосте обратный mapping — VNI снова становится VLAN ID нужного номера

**Результат:** VM1 на хосте A и VM4 на хосте B в одном L2-сегменте (общий VLAN 100), хотя физически разделены L3-сетью. VM об этом не знают — для них просто работает ARP и broadcast.

Это каноническая архитектура современного ДЦ: физика L3, клиенту виден L2 нужного масштаба.

## Настройка в Linux

Linux-ядро тоже понимает 802.1Q — можно создавать VLAN-интерфейсы:

```bash
# создать VLAN-интерфейс "eth0.10" для VLAN 10 на физическом eth0
ip link add link eth0 name eth0.10 type vlan id 10
ip link set eth0.10 up

# теперь eth0.10 — это виртуальный интерфейс, который
# тегирует все исходящие кадры и принимает только тегированные VLAN 10
ip addr add 192.168.10.5/24 dev eth0.10
```

С точки зрения остального стека `eth0.10` ведёт себя как обычный интерфейс. Снаружи на провод идут кадры с тегом 10. Можно подключить такой интерфейс к [[linux-bridge|bridge]], чтобы в одном bridge объединить локальные контейнеры и удалённую сеть через VLAN trunk.

## В BADASS

VLAN в BADASS напрямую не используется. Но концепт важен для понимания мотивации VXLAN: VLAN решил ту же задачу на уровне одной физической сети, VXLAN — на уровне распределённого дата-центра.
