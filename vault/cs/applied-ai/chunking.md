```
  документ 20 стр.
  ┌──────────────────────────────────────────┐
  │ ...Scope 3 screening. Categories 1,3,5   │ chunk 14
  ├────────────── граница ───────────────────┤
  │ 6,7 calculated. Categories 8-15: n/a ... │ chunk 15
  └──────────────────────────────────────────┘
   ▲ факт разрезан: ни один кусок не содержит его целиком

  с overlap:   [ chunk 14 ][~~перекрытие~~][ chunk 15 ]
```

**TL;DR:** Chunking — нарезка документов на куски (chunks) перед поиском. Ищут и отдают LLM куски, а не документы целиком. Размер и границы кусков напрямую определяют, что поиск сможет найти.

## Зачем резать

- эмбеддинг всего 200-страничного отчёта = одна точка, смысл размыт → искать нечем
- в контекст LLM нужен короткий релевантный текст, а не весь корпус
- чем меньше кусок, тем точнее его вектор описывает одну мысль

## Способы

| Способ | Как | Минус |
|---|---|---|
| fixed-size | каждые N токенов (например, 500) | режет посреди предложения и таблицы |
| fixed + overlap | куски перекрываются на 10–20% | дубли, больше кусков |
| по структуре | по заголовкам, абзацам, страницам | куски разного размера |
| semantic | граница там, где меняется тема (по эмбеддингам) | дороже, непредсказуемо |
| таблица = строка | каждая строка Excel со своими заголовками колонок | нужен отдельный парсер |

## Компромисс размера

- **мелкие** (100–200 токенов): точный поиск, но теряется контекст («2 117» — чего? за какой год?)
- **крупные** (1000+): контекст есть, но вектор размыт и в top-k влезает меньше разных фактов

Частый приём: искать по мелким кускам, а LLM отдавать кусок вместе с соседями или всю страницу (parent-document retrieval).

## Важно для evidence-задач

Хранить у каждого куска **метаданные**: файл, страница, раздел, год. Без них нельзя указать `proving_document` и страницу, а таблица без заголовков колонок превращается в набор чисел без смысла.
