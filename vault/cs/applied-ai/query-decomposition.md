```
"Доля зелёного электричества ≥ 80% в 2024?"
               │  LLM разбивает
   ┌───────────┼──────────────┬──────────────┐
 q1: сколько  q2: какие       q3: сколько    q4: когда
 всего кВт·ч  сертификаты GO  кВт·ч по GO    погашены
   │            │               │              │
 retrieval    retrieval       retrieval      retrieval   (каждый отдельно)
   └───────────┴───────┬───────┴──────────────┘
              все найденные фрагменты → ответ
```

**TL;DR:** Сложный вопрос LLM заранее разбивает на несколько простых подвопросов. Для каждого делается отдельный поиск, результаты объединяются. Один «общий» поиск по сложному вопросу находит фрагменты про что-то одно и пропускает остальное.

## К чему относится

Не метод поиска, а **обёртка над любым [[retrieval]]**: внутри каждого подвопроса работает тот же [[bm25]], dense или [[hybrid-search-rrf]]. Семейство — query transformation (переписывание запроса перед поиском). Соседи: query rewriting (переформулировать), HyDE (сгенерировать гипотетический ответ и искать по нему), multi-query (несколько перефразов одного вопроса).

## Почему один запрос не работает

Вектор сложного вопроса — «среднее» его частей. Ближе всего к нему окажутся фрагменты, где много слов про электричество в целом. Фрагмент «сертификаты погашены 14.03.2025» с вопросом похож слабо → не попадает в top-k. А он нужен для ответа.

После разбиения у подвопроса q4 этот фрагмент — лучшее совпадение.

## Как делается

1. LLM получает вопрос и возвращает список подвопросов (обычно JSON)
2. Для каждого — поиск, свой top-k
3. Фрагменты объединяются (дубли убираются), иногда через RRF
4. LLM отвечает по объединённому набору или каждый подвопрос отвечается отдельно

## Ограничение

Разбиение делается **один раз заранее**. Если ответ на q1 меняет, что спрашивать дальше («электричество считается в двух юрлицах»), декомпозиция об этом не знает → нужен [[iterative-retrieval]].

Хорошо ложится на задачу с objectives: условия цели уже перечислены в тексте → подвопросы = условия.
