```
  PDF ─► парсинг ─► чанки ─► индекс ─► top-50 ─► rerank ─► top-5 ─► LLM ─► ответ
   │        │         │         │         │          │         │       │
   ①        ①         ②         ③         ③          ④         ④       ⑤
  факт     факт      факт      факт     факт        факт      факт    ответ
  есть?    в тексте? целиком?  найден?  в top-50?   в top-5?  дошёл?  верен?

  Идём слева направо. Первый «нет» = стадия, которую чинить.
```

**TL;DR:** Чтобы понять, что менять, для каждого проваленного вопроса находят первую стадию pipeline, где факта уже нет, и чинят именно её. Менять по одному параметру на одном замороженном наборе ([[rag-eval-set-freeze]]), иначе нельзя назвать причину роста.

## Проблема

Recall низкий, вариантов правки много: чанкинг, hybrid, reranker, модель embeddings, очистка PDF. Перебор вслепую даёт «стало лучше» без объяснения, почему. Стадии зависят друг от друга: reranker не вернёт факт, которого нет среди кандидатов, а лучшая модель embeddings не склеит разрезанную таблицу.

## Таблица диагностики

| Проверка (по порядку) | Ответ «нет» значит | Что менять |
|---|---|---|
| ① Факт есть в тексте после парсинга? | колонки склеены, таблица развалилась, скан без OCR, шапки/футеры в тексте | парсер, OCR, очистка PDF |
| ② Есть чанк, где факт целиком? | факт разрезан или чанк без контекста | [[chunking]] |
| ③ Чанк в top-50 от ретривера? | точные термины, коды, артикулы не ловятся эмбеддингом; или язык/домен чужой для модели | hybrid ([[hybrid-search-rrf]], [[bm25]]); другая модель embeddings ([[dense-retrieval-embeddings]]) |
| ④ В top-50 есть, в top-5 нет? | ретривер нашёл, но поставил низко | reranker ([[reranking-cross-encoder]]) |
| ⑤ В top-5 есть, ответ неверный? | поиск ни при чём | промпт, модель, формат контекста |

## Как проверять на практике

Для каждого проваленного вопроса из dev-части набора:

1. Найти в исходнике фрагмент с ответом (ты знаешь, где он, из разметки).
2. Искать его по стадиям: в тексте после парсинга (grep), среди чанков, в top-50, в top-5.
3. Записать номер стадии. Получится гистограмма: «12 провалов — ②, 5 — ③, 2 — ④».
4. Чинить самую частую стадию.

Быстрый индикатор без ручного разбора — сравнить recall@50 и recall@5 ([[retrieval-metrics]]):

| recall@50 | recall@5 | Вывод |
|---|---|---|
| высокий | низкий | проблема ранжирования → reranker |
| низкий | низкий | проблема раньше: чанки или ретривер → ③ или ② |
| высокий | высокий, а ответы плохие | поиск в порядке → ⑤ |

## Правила эксперимента

- Одна правка за раз, замер на том же dev-наборе; итоговая цифра на held-out.
- Фиксировать вклад каждой правки: «чанкинг +20, hybrid +6, reranker +2». Это ответ на «что именно улучшило recall».
- Правка на стадии левее обычно меняет всё правее: после смены чанкинга индекс пересобирается, а метрики последующих стадий нужно мерить заново.

## Порядок правок

Чинить слева направо (①→⑤): правое не лечит левое, а цена эксперимента растёт вправо (reranker и LLM-вызовы дороже пересчёта чанков в локальном тесте). Это тот же принцип, что «левый слой первым» в коде.

## Для интервью

Вопрос «что улучшило recall» проверяет, видел ли ты причину. Ответ строится так: «разобрал N провалов по стадиям, M из них — факт разрезан чанкером → переделал чанкинг по структуре с префиксом заголовков → recall@5 на held-out с 50 до 72; остаток — ранжирование, добавил reranker, +2».
