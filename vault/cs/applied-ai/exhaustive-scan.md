# Exhaustive scan-all

---

```
  dataroom: 63 файла → 1200 страниц → 600 кусков

  MAP (каждый кусок, параллельно, без пропусков):
   кусок 1 ─▶ LLM: есть факты про цель? ─▶ []
   кусок 2 ─▶ LLM ─▶ [Scope1=2117 т, стр.8]
   кусок 3 ─▶ LLM ─▶ []
   ...
   кусок 600 ─▶ LLM ─▶ [кат. 4 n/a, стр.3]

  REDUCE: все найденные факты ─▶ объединить ─▶ решение
```

**TL;DR:** LLM просматривает *каждый* кусок каждого документа и для каждого отвечает «есть ли тут нужный факт». Никакого top-k: ни один кусок не пропущен по вине поиска. Самый дорогой и самый полный способ.

## К чему относится

Противоположность [[retrieval]]: retrieval выбирает, что читать; scan-all читает всё. Паттерн — **map-reduce**: map = один и тот же вопрос к каждому куску отдельно, reduce = собрать ответы. По сути [[long-context-reading]], разрезанный на маленькие части, чтобы не было lost in the middle.

## Сравнение

| | Retrieval top-k | Agentic | Scan-all |
|---|---|---|---|
| Что читается | k фрагментов | что агент решил | всё |
| Может пропустить из-за поиска | да | да | **нет** |
| Может пропустить из-за LLM | да | да | да (но на маленьком куске реже) |
| Цена | ~1 вызов | 5–30 вызовов | вызов на каждый кусок × цель |
| Детерминизм пути | да | нет | да |

## Почему всё равно не 100%

1. LLM может не заметить факт даже в маленьком куске
2. Факт разрезан границей кусков (половина таблицы в одном, половина в другом)
3. Плохо распознанный скан → факта в тексте просто нет
4. После map часто фильтруют (оставить «самые релевантные») → снова top-k, снова потеря

Пункт 3 особенно важен: «не найдено» честно только если известно, что *все страницы прочитаны успешно*.

## Когда оправдан

Корпус маленький (десятки документов), цена ошибки высокая, нужно доказать отсутствие («категория 2 нигде не упомянута»). Dataroom Colvea — как раз такой случай. На миллионе документов — нереально, там retrieval.
