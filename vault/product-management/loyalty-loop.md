# Loyalty loop — лояльность через предсказуемый результат

back: [[customer-journey-map]]
next:
- [[loyalty-loop-vs-involvement-spiral]]
- [[monthly-active-users]]

---

```text
Первый раз: задача → сравнение → выбор → результат
                                          │
                            доверие к сервису
                                          │
Следующий: задача → сразу знакомый сервис → результат
                       ↑                      │
                       └──── новый повод ─────┘
```

**TL;DR:** Loyalty loop возникает, когда надёжный результат делает знакомый сервис естественным выбором при следующей потребности. Продукт сохраняет контекст и убирает повторную работу пользователя.

## Как реализовать в приложении

Петля — следствие всего повторного сценария, а не отдельной кнопки или программы бонусов. Ниже — практическое применение модели.

| Механика | Что убирает | Пример |
|---|---|---|
| Память о контексте | Повторный ввод и настройку | Сохранённые адреса, фильтры, «повторить заказ» |
| Быстрый вход | Повторный поиск нужного места | Сохранённая сессия, восстановление сценария, deep link |
| Релевантный повод | Необходимость проверять вручную | Уведомление по подписке: появились подходящие объявления |
| Надёжное исполнение | Сомнение «получится ли в этот раз» | Актуальные данные, понятный срок, устойчивый основной flow |
| Короткое завершение | Лишние действия перед результатом | Предзаполненная форма, доступный контакт, сохранённая оплата |

Сохранять только уместный контекст: устаревший адрес или фильтр должен быть виден и легко изменяться. Для рискованных действий подтверждение может быть полезнее одного клика.

## Пример: поиск жилья в Scrypo

Проектируемый сценарий, без предположений о текущих функциях:

1. Пользователь сохраняет город и фильтр.
2. Возвращается к новым подходящим объявлениям; просмотренные остаются различимыми.
3. По желанию подписывается на новые совпадения, например через Telegram.
4. Уведомление открывает конкретный листинг или нужную выдачу.
5. Контакт автора доступен без повторного поиска.

«Новое» требует явной точки отсчёта: последний визит или просмотр объявления. Иначе обещание интерфейса расходится с результатом.

Нашёл жильё и ушёл — успешное завершение задачи. Следующая петля возможна при новом переезде; удержание внутри активного поиска и возврат при следующей потребности — разные горизонты.

## Как проверить

- Время и число действий до **успешного результата** при повторном сценарии.
- Доля успешных завершений и ошибок; сокращение кликов само по себе не доказывает пользу.
- Возврат при следующей потребности, если её можно наблюдать; отсутствие возврата не всегда означает потерю лояльности.
- Для уведомлений: переход к полезному действию, отключения и жалобы.

[[monthly-active-users|MAU]] не показывает, решил ли человек задачу. Время в приложении тоже не цель: короткая успешная сессия может быть лучшим результатом.

## Концепция шире

- Банк: сохранённый получатель сокращает следующий перевод.
- Доставка: повтор заказа использует уже выбранные товары и адрес.
- B2B-сервис: шаблон отчёта сохраняет параметры следующего рабочего цикла.

Общее везде: повторная потребность → сохранённый контекст → надёжный результат с меньшими усилиями.
