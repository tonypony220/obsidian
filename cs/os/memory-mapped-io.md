# Memory-mapped I/O

---

```
CPU ──адресная шина──▶ ┌ RAM      (0x00000...)
                       ├ VGA RAM  (0xB8000)  ← «память», а на деле железо
                       └ ROM      (0xF0000...)

CPU ──in/out──────────▶ порты (отдельное пространство):
                        0x60 клавиатура, 0x3D4/0x3D5 VGA-регистры
```

**TL;DR:** устройства подключаются к тем же шинам, что и память: часть адресов «ведёт» не в RAM, а в железо (MMIO), а на x86 есть ещё отдельное пространство портов (in/out) — читая и записывая эти адреса, ты разговариваешь с устройством.

## Два механизма на x86

- **MMIO** — диапазон адресов замаплен на устройство: запись в 0xB8000 уходит в видеопамять ([[vga-text-mode]]). Обычные `mov`-инструкции, обычные указатели в C.
- **Port-mapped I/O** — отдельное 16-битное пространство портов и специальные инструкции `in`/`out`; в C не выразимо (язык знает только память) — inline-asm обёртки `inb`/`outb`: одна инструкция, операнды прибиты к AL (данные) и DX (порт) самой инструкцией — отсюда constraints `"a"`/`"Nd"`. Клавиатура (0x60/0x64), регистры VGA (0x3D4/0x3D5), PIC, PIT…
- Паттерн **index/data** поверх PMIO: портов два, внутренних регистров десятки — первый порт «какой регистр» (0x3D4), второй «данные» (0x3D5); так же CMOS/RTC (0x70/0x71). Детали на курсоре — [[vga-text-mode]]

Исторически PMIO — из эпохи дефицита адресного пространства; современное железо (PCIe BARs) почти целиком MMIO.

## Шина физически

Пучок проводов из CPU наружу, три группы: **адресные** (выставить номер), **данных** (сами байты), **управляющие** (read/write + «память или порт»). Провод = один бит (высокое/низкое напряжение): 20 адресных проводов 8086 вместе несут ОДНО 20-битное число → комбинаций 2^20 = 1 МБ адресов — отсюда «заповедник» и `. = 1M` ([[linker-script]]). У «области» своих проводов нет — это множество адресов с одинаковыми старшими битами (0xA0000–0xBFFFF = все адреса с A19..A17 = 101); **декодер** чипсета — логика на старших битах, активирующая chip-select нужной микросхемы. Рост пространства = рост числа бит: 286 — 24 (16 МБ), 386 — 32 (4 ГБ), x86-64 — 46+; росло вверх, нижний мегабайт заморожен. Отдельное пространство портов — буквально отдельная нога CPU (M/IO#): номер тот же, нога говорит «это порт, не память». Современно параллельных проводов уже нет (point-to-point линки, контроллер RAM внутри CPU), но модель «выставил номер → кто-то ответил» жива.

Частая ошибка: считать младшие биты адреса «сообщением». В адресе нет payload'а — все биты только «где»: старшие съедает декодер (выбор микросхемы через chip-select), младшие получает выбранная микросхема как **номер ячейки внутри себя**. Данные («что») едут по отдельному пучку D15–D0 **одновременно** с адресом. Цикл шины ≠ пересылка пакета: это интервал, пока на всех пучках держатся стабильные напряжения и выбранный чип по сигналу W защёлкивает данные.

Адресное пространство — **нумерация, не место**. Не «всё замаплено в RAM», а наоборот: RAM замаплена в ЧАСТЬ номеров. По номерам 0xA0000–0xBFFFF планка RAM не отвечает вовсе — байт физически уезжает в чип на видеокарте. Маршрутизирует **чипсет-декодер**: смотрит номер, пересылает запрос нужному устройству; CPU разницы не видит.

Планка RAM — такое же устройство за декодером, как видеокарта: получает смещение внутри своего диапазона, а контроллер планки превращает смещение в ряд/колонку ячеек DRAM. Линейное «1:1» между адресами оси и байтами планки существует только ВНУТРИ назначенного диапазона.

Судьба каждого адреса оси — одна из трёх: **прошито** (в декодере платформы навсегда: заповедник первого МБ, порт 0xCF8), **назначено** (firmware записал базу в BAR при этой загрузке — [[buses-and-controllers]]; после перезагрузки может быть иначе), **пусто** (никто не отвечает: чтение вернёт все-единицы, запись потеряется). `info mtree -f` в QEMU — снимок текущей таблицы маршрутизации: строка = «на этот диапазон есть ответчик», дыры между строками = пусто.

## Три вещи со словом «регистр»

- **Регистры CPU** (EAX, ESP, EIP…) — ячейки внутри кристалла процессора: адресов НЕ имеют, зовутся по имени в инструкции, через шину не ходят. «Карманы» CPU
- **Регистры устройств** (VGA 0x3D4, клавиатура 0x60) — ячейки внутри самих устройств, выставленные наружу через порты/MMIO. «Кнопки на корпусе» ([[buses-and-controllers]])
- Позже (KFS_2+): **системные регистры** CR0/GDTR/IDTR — тоже внутри CPU, управляют его режимами

## Увидеть карту глазами

QEMU-монитор ([[binary-inspection-cheatsheet]]): `info mtree -f` печатает таблицу маршрутизации «номер → устройство»: посреди `pc.ram` дыра `0xa0000–0xbffff (i/o): vga-lowmem`, а FlatView "I/O" — отдельное пространство портов (0x60 i8042-клавиатура, 0x3d4 vga). `xp /32xb 0xb8000` — прочитать надпись SeaBIOS прямо из видеопамяти: чётные байты — ASCII, нечётные — атрибут 0x07.

## volatile обязателен

Для компилятора MMIO-адрес — обычная память: он не видит сайд-эффекта в железе и может выкинуть «лишние» обращения или переставить их местами. `volatile` запрещает обе оптимизации. В Rust — `core::ptr::read_volatile` / `write_volatile`.

Механизм — правило **as-if**: компилятор обязан сохранить только «наблюдаемое поведение», а обычный доступ к памяти по стандарту НЕ наблюдаем (наблюдаемы только volatile-доступы и I/O). `volatile` = объявить сам доступ наблюдаемым событием: обязан случиться, столько раз, в этом порядке.

Эксперимент (-O2, i686-elf-gcc 16): одиночные записи в 0xB8000 выживают и БЕЗ volatile — для удаления нужно доказательство «никто не прочтёт», а запись по неизвестному адресу консервативно считается читаемой извне. Осторожность ≠ контракт (другой компилятор/LTO вправе иначе). Где реально стреляет: (1) две записи в одну ячейку — первая удалена (перекрыта до чтения; спиннер/анимация теряет кадры); (2) poll-цикл `while (vga[0] != X);` — чтение вынесено из цикла: проверка один раз, дальше вечный `jmp self`, память не перечитывается (так виснут ожидания флага устройства — KFS_2). Записи выживают по везению, чтения — нет.

## Большая видеопамять vs окно 128 КБ

Окно 0xA0000–0xBFFFF — интерфейс контроллера карты, не сама память: за ним VRAM любого размера. VGA-эпоха: **bank switching** — регистр карты выбирает, какой кусок VRAM подставлен в окно. Современно: firmware при перекличке PCI ([[buses-and-controllers]]) записывает в **BAR** (Base Address Register) карты базовый адрес большого окна высоко в выросшем пространстве — в QEMU `info mtree -f` это `0xfd000000 vga.vram` (вся VRAM целиком). Гигабайты GPU: раньше CPU видел часть (aperture) + DMA, теперь Resizable BAR мапит всё. Legacy-окно с 0xB8000 живёт параллельно — им и пользуемся.

## Концепция шире

- ARM/RISC-V: портов нет вообще — вся периферия (UART, GPIO, таймеры) только через MMIO
- GPU/сетевые карты: драйвер общается с устройством через MMIO-регистры из PCI BAR
- `mmap` файлов: тот же приём «не-RAM, видимая как память», но со стороны ОС

Общее везде: адресное пространство — универсальная шина; «прочитать адрес» не обязано означать «прочитать RAM».
