```
kernel.bin, первые 8 КБ:
┌───────────────────────────────┐
│ dd 0x1BADB002   ← magic       │
│ dd flags                      │
│ dd -(magic+flags) ← checksum  │  сумма трёх слов = 0
└───────────────────────────────┘
GRUB сканирует → нашёл → грузит → jmp _start
              EAX = 0x2BADB002, EBX = &boot_info
```

**TL;DR:** multiboot — контракт между загрузчиком и ядром: ядро помечает себя заголовком в первых 8 КБ файла, GRUB за это обещает загрузить его и передать управление в точно описанном состоянии CPU.

## Заголовок

- 3 × 32-бит слова: `magic` (0x1BADB002), `flags`, `checksum = -(magic + flags)` — сумма трёх равна нулю, так GRUB валидирует.
- Должен лежать в первых 8192 байтах файла, выровнен на 4 → в коде это отдельная секция, которую [[linker-script]] ставит первой (`KEEP(*(.multiboot))`).
- `flags`: бит 0 — выравнивать модули по страницам, бит 1 — просить memory map (понадобится для менеджера памяти, KFS_2).

## Состояние машины после handoff

Handoff — не состояние, а **момент**: GRUB исполняет `jmp _start` и перестаёт существовать как работающая программа — эстафетная палочка передана. Ниже — гарантии, «в каком виде тебе отдали машину» в этот момент:

- 32-битный [[protected-mode]], paging выключен, прерывания выключены, линия A20 включена.
- `EAX` = 0x2BADB002 («тебя загрузил multiboot-загрузчик»), `EBX` = физический адрес структуры boot info (карта памяти, cmdline, модули).
- GDT — загрузчика: полагаться нельзя; своя GDT — тема следующих KFS.
- **ESP не определён** → первая инструкция ядра — поставить свой стек ([[stack-is-a-convention]]).

## Зачем это формализовано

Загрузчик и ядро — независимые программы разных авторов. Без спеки GRUB не мог бы грузить «любое» ядро, а ядро не знало бы, в каком состоянии ему отдали CPU. Multiboot 2 — та же идея в расширяемом формате тегов; для KFS хватает v1.

## `qemu -kernel` — тоже multiboot-загрузчик

Контракт не говорит, КТО его исполняет: `qemu -kernel` выполняет те же обещания (ELF разложен, protected mode, EAX/EBX, jmp на entry) — ядро НЕ МОЖЕТ отличить его от GRUB, в этом смысл контракта ([[interface-contracts]]). Разница — цепочка доставки: GRUB это программа НА диске, которую исполняет CPU машины (BIOS → boot-сектор → стадии GRUB → чтение ядра из ФС), а `-kernel` — «рука бога»: эмулятор кладёт байты в RAM снаружи, внутри машины загрузчик не исполнялся, диска нет. Поэтому для сдачи нужен ISO ([[boot-process]]): проверяется не контракт, а вся дорога до него — GRUB установлен, grub.cfg корректен, ядро найдено на диске.

## Концепция шире

- ELF header — тот же контракт, но между ядром-загрузчиком и user-программой
- ABI / calling convention — контракт между отдельно скомпилированными единицами
- OCI image manifest — контракт между registry и container runtime

Общее везде: два независимых артефакта стыкуются через формально описанный заголовок и состояние, а не через знание внутренностей друг друга.
