# Linker script

```
.o + .o + .o ──── ld ────▶ kernel.bin
                  │
   linker.ld решает раскладку (адреса растут ↑ вверх):
         │ свободная RAM    │  ← ничья до KFS_2
         ├──────────────────┤  конец ядра
         │ .bss    стек     │  ← стек растёт вниз, к .data
         │ .data   глобалы  │
         │ .rodata константы│
         │ .text   код      │
         │ .multiboot 12 б  │  ← первым = самый младший адрес (окно 8 КБ)
0x100000 ├──────────────────┤  . = 1M
         │ BIOS, VGA, ROM   │  ← железо, сюда нельзя
0x000000 └──────────────────┘
```

**TL;DR:** linker script говорит линкеру, в каком порядке и по каким адресам склеить секции объектных файлов; ядру нужен свой, потому что дефолтный раскладывает бинарник под запуск ОС-ой, которой нет.

## Когда он работает: сборка, не загрузка

`linker.ld` — не программа, его никто не «запускает». Это техзадание архитектору: линкер читает его **один раз, при `make`, на машине сборки**, решает адреса и вшивает их в ELF-заголовок kernel.bin ([[elf-format]] — «план дома»). GRUB при загрузке работает только по плану — техзадание ему недоступно и не нужно. В бинарнике от скрипта остаются только последствия: числа-адреса.

Почему линковка — отдельный шаг: компилятор видит один файл за раз (`call kmain` в boot.asm = `call <дырка>` + пометка), и только линкер видит все объектники сразу — склеивает, назначает финальные адреса, заполняет дырки. `extern kmain` = «оставь дырку, линкер заполнит».

## Почему хостовый .ld не подходит

Дефолтный скрипт собирает user-space программу: entry из crt0 (стартап-код libc), виртуальные адреса процесса, динамическая линковка. У ядра всё иначе: entry — твой ASM-символ, адреса физические, грузит GRUB по контракту [[multiboot]].

Посмотреть дефолтный скрипт глазами: `i686-elf-ld --verbose`. Улики, что он не для нас:
- `. = 0x08048000 + SIZEOF_HEADERS` — классический ВИРТУАЛЬНЫЙ адрес 32-бит Linux-процесса; виртуальность создают ОС+paging, которых у нас нет
- `.interp` — «подгрузи /lib/ld-linux» — просьба к несуществующей ОС
- `.dynsym`, `.rel.*` — динамическая линковка, дырки дольёт loader ОС
- `.multiboot` не упомянут → GRUB его в первых 8 КБ не найдёт

## Ключевые элементы

- `ENTRY(_start)` — символ, на который прыгнет загрузчик.
- `. = 1M` — location counter: класть код начиная с 1 МБ. Почему именно 1M: у 8086 (1978) было 20 бит адреса = потолок ровно 1 МБ, и IBM PC (1981) разложил в этот мегабайт ВСЁ системное: внизу таблица прерываний + данные BIOS, 0xA0000–0xBFFFF видеопамять ([[vga-text-mode]], наш 0xB8000 здесь), 0xC0000–0xFFFFF ROM'ы. Совместимость заморозила эту карту навсегда → первый мегабайт = мозаика из чужих кусков, а 1M = первый адрес, с которого начинается сплошная свободная RAM («extended memory»). Multiboot-конвенция: ядра грузят туда.
- Порядок секций: `.multiboot` первой — заголовок должен попасть в первые 8 КБ файла. `KEEP()` — запрет выкидывать секцию (при `--gc-sections` линкер удаляет всё, на что нет ссылок, а на заголовок ссылок нет).
- `.text` код → `.rodata` константы → `.data` инициализированные глобалы → `.bss` неинициализированные (места в файле не занимают — загрузчик занулит; здесь же живёт стек ядра).
- `ALIGN(4K)` — выравнивание секций по страницам: пригодится с приходом paging (KFS_3).

## Симптомы ошибок

- Заголовок не попал в первые 8 КБ → GRUB: «no multiboot header found»
- Секции ниже 1 МБ → затирание BIOS-областей, triple fault / перезагрузка по кругу
- Забыт `KEEP` → header выкинут при сборке мусора секций
