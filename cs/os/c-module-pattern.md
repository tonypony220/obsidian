```
tty.h (интерфейс)          tty.c (реализация)
┌──────────────────┐       ┌────────────────────────────┐
│ void term_init() │ ◀───  │ void term_init() {...}     │
│ void putchar(c)  │       │ static term_row, col, color│ ← имена заперты
└──────────────────┘       │ static vga_entry() {...}   │   внутри файла
  видно всему ядру         └────────────────────────────┘
```

**TL;DR:** модуль в C = header (публичный контракт) + .c (реализация); `static` на уровне файла запирает имя внутри — инкапсуляция без классов. Чего нет в header'е, того снаружи не существует.

## static: два разных смысла одного слова

- **Вне функций** (file-scope): переменная и так живёт всю жизнь программы — `static` меняет только ВИДИМОСТЬ имени (linkage). Без него любой файл дотянется через `extern uint8_t term_row;` мимо интерфейса
- **Внутри функции**: другая работа — переменная переживает вызовы (время жизни, storage duration)
- Ловушка: «функция вызывается один раз, зачем static?» — вопрос из второго смысла к первому

## Состояние принадлежит модулю, не функции

Курсор терминала (`row/col/color`) нужен МЕЖДУ вызовами `putchar` → живёт на уровне файла. Менять его может только код этого файла — интерфейс определяет, что доступно снаружи.

## Увидеть приватность глазами

`nm -n kernel.bin`: РЕГИСТР буквы = видимость. `T term_init` — экспорт (заглавная), `d term_color`, `b term_row` — static (строчные). [[binary-inspection-cheatsheet]]

## Концепция шире

- ООП: `private` поля класса — та же идея, встроенная в язык
- Rust: наоборот — всё приватно по умолчанию, экспорт явный (`pub`)
- ELF: local vs global символы — механизм, которым linkage реализован ([[linker-script]])
- Микросервисы: публичный API vs внутренние эндпоинты

Общее везде: контракт снаружи, свобода внутри; чем меньше экспортировано, тем дешевле менять реализацию ([[interface-contracts]]).
