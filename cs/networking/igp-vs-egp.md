```
                          │
                         BGP                  ← EGP между AS
                          │                    (выбор по политике)

        │           AS 65002               │
        └──────────────────────────────────┘
```

**TL;DR:** IGP оптимизирует маршруты по физическим метрикам внутри одной AS, EGP выбирает маршруты между AS по административной политике. В реальной сети работают одновременно: IGP поднимает связность между внутренними роутерами, BGP поверх неё несёт внешние префиксы.

## Суть разделения

Протоколы маршрутизации делятся по области действия:

- **IGP** (Interior Gateway Protocol) — внутри одной [[autonomous-system|AS]]
- **EGP** (Exterior Gateway Protocol) — между разными AS

Разделение не техническое, а функциональное. Внутри AS и между AS решаются **разные задачи** с разными приоритетами. Один протокол не может быть одновременно быстрым, масштабируемым и политически гибким — приходится разделять.

## Сравнение

| | IGP | EGP |
|---|---|---|
| Область работы | внутри AS | между AS |
| Главная цель | минимальная стоимость пути | выбор по политике |
| Метрика | физическая (cost, hop count, пропускная способность) | path-vector (AS-path) + атрибуты политики |
| Алгоритм | link-state (OSPF, IS-IS) или distance-vector (RIP) | path-vector (BGP) |
| Сходимость | секунды | минуты (на масштабе интернета) |
| Модель доверия | все роутеры внутри AS считаются надёжными | между AS доверия нет, всё фильтруется |
| Масштаб | тысячи роутеров в одной AS | миллионы префиксов, ~75 тыс. AS |
| Актуальные представители | OSPF, IS-IS | BGP (единственный живой EGP) |

## IGP — оптимизация внутри AS

Задача IGP: для каждого префикса найти **путь с минимальной стоимостью** по сети своей AS. Стоимость определяется физикой:

- **OSPF cost** — обратно пропорционален пропускной способности линка (по умолчанию `10^8 / bandwidth`)
- **IS-IS metric** — назначается вручную или по формуле, концептуально то же самое
- **RIP hop count** — просто число хопов (устаревший подход, не учитывает скорость линков)

Все роутеры внутри AS управляются одной организацией, поэтому:
- обмениваются полной информацией о топологии (link-state) или векторами расстояний
- доверяют друг другу — нет политик фильтрации
- оптимизированы под быструю сходимость (секунды): упал линк → flooding → SPF на всех роутерах → новый FIB

## EGP — выбор по политике между AS

Задача EGP: выбрать путь из множества **политически допустимых** вариантов. BGP не ищет кратчайший путь — он применяет правила, заданные администратором.

Набор BGP-атрибутов, определяющих выбор:

- **LOCAL_PREF** — "какой путь предпочитает сама AS". Настраивается локально, выше = лучше. Выше всего в иерархии выбора.
- **AS_PATH** — список AS, через которые прошёл маршрут. Короче = лучше (при равных LOCAL_PREF). Также используется для детекции петель: если AS видит свой ASN в path — дропает.
- **ORIGIN** — откуда изначально пришёл маршрут (IGP / EGP / incomplete).
- **MED** (Multi-Exit Discriminator) — подсказка соседу "через какой из моих линков заходить лучше".
- **COMMUNITIES** — теги для группировки префиксов (например "не анонсировать за пределы континента").

Реальная политика кодируется через эти атрибуты:
- "анонсирую соседу A всё, соседу B — только свои префиксы" — через фильтры на исходящих UPDATE
- "предпочитаю путь через ISP-X" — через LOCAL_PREF на входящих маршрутах от X
- "блокирую суспишес AS-path длиннее 30" — через prefix-list + AS-path filter

Сходимость медленная — BGP оптимизирован под стабильность и масштаб, не под скорость. На интернете ~1 млн префиксов в full table; реагировать на каждое дрожание слишком дорого.

## Почему нельзя обойтись одним протоколом

### IGP не масштабируется на интернет

Link-state требует полной топологии у каждого роутера. Для OSPF:
- роутер хранит LSDB (Link State Database) со всеми линками своей area
- при любом изменении — flooding на всю area + пересчёт SPF у всех

На масштабе интернета (миллионы линков, десятки тысяч AS) это невозможно:
- размер LSDB растёт линейно, память роутеров не бесконечна
- SPF на графе с миллионами вершин занимает секунды-минуты CPU
- любое дрожание линка вызывает пересчёт у всех роутеров мира

Плюс — нет механизма политики. IGP доверяет соседям; между AS доверия нет.

### BGP не подходит для внутренней сети

BGP не решает задачу "найди кратчайший путь". Его метрика основана на политике, не на физике.

Внутри AS:
- политик нет — все роутеры свои
- хочется **минимальной задержки**, BGP этого не даёт
- BGP сходится минутами — при падении линка в дата-центре это неприемлемо

Поэтому IGP и EGP решают каждый свою задачу, и используются **вместе**.

## Как работают вместе

```
  ┌── AS 65001 ──────────────────────────────────┐
  │                                              │
  │  R1 ═══ OSPF ═══ R2 ═══ OSPF ═══ R3          │   IGP — физическая связность
  │  ▲                ▲               ▲          │   loopback R1 ↔ loopback R3
  │  │                │               │          │
  │  iBGP ═══════════ iBGP ══════════ iBGP       │   iBGP — согласование
  │                                              │   внешних маршрутов
  │  │                                   │       │   (поверх IGP-связности)
  │ eBGP ─────────────────────────── eBGP        │
  └──┼───────────────────────────────────┼───────┘
     │                                   │
  [AS 65002]                        [AS 65003]      ← eBGP общается
                                                     с другими AS
```

Рабочая структура:

1. **IGP (OSPF)** строит связность между внутренними роутерами. Каждый роутер знает как дойти до loopback каждого другого.
2. **iBGP** пирится между всеми BGP-роутерами AS по их loopback-адресам. IGP обеспечивает, что iBGP-пакеты доходят.
3. **eBGP** на границах AS — общение с соседними AS, передача внешних префиксов.
4. Когда `R1` получает по eBGP маршрут `1.1.1.0/24` от соседней AS, он через iBGP рассказывает это `R3`. `R3` теперь знает что для трафика на `1.1.1.0/24` надо отправлять в сторону `R1` (next-hop — loopback `R1`, путь до него — по OSPF).

## iBGP ≠ IGP — частая путаница

Ключевое различение:

```
  IGP          = OSPF, IS-IS, RIP          ← внутренние link-state/distance-vector
  EGP          = BGP                        ← path-vector с политиками
    ├── eBGP   = BGP-сессия между AS
    └── iBGP   = BGP-сессия внутри AS
```

**iBGP — это BGP, не IGP.** Разница между iBGP и eBGP — только в том, что сосед в той же AS или в другой; алгоритмы и атрибуты те же. У iBGP отдельное [[rib-vs-fib|administrative distance]] (200) — ниже чем у eBGP (20) и чем у IGP (OSPF=110), потому что iBGP-маршруты обычно транзитные и менее надёжные чем внутренние IGP-маршруты.

iBGP нужен потому что в AS может быть много BGP-роутеров, и они должны согласованно знать что пришло с границ. IGP про это не знает — IGP несёт только внутренние маршруты.

## В BADASS

P3 использует обе ветки одновременно:

- **OSPF** — IGP, поднимает связность между роутерами через loopback-адреса
- **BGP (MP-BGP с EVPN AFI)** — работает поверх OSPF-связности, переносит не классические IP-префиксы, а MAC-адреса хостов за VXLAN-фабрикой

Это каноничная иллюстрация паттерна "IGP для физики + BGP для логики более высокого уровня".
