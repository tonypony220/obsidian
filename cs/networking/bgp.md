```
  R1 ════════ TCP:179 ════════ R2
       "у меня есть 10.0.0.0/24"  →   UPDATE (announce)
       "10.0.0.0/24 больше нет"   →   UPDATE (withdraw)
       "ты жив?"                  →   KEEPALIVE
```

**TL;DR:** BGP — протокол обмена маршрутной информацией между роутерами через постоянную TCP-сессию (порт 179). Изначально — для обмена IP-префиксами между [[autonomous-system|автономными системами]] (EGP). Расширение **MP-BGP** позволяет нести разные типы данных через **address families** — в том числе `l2vpn evpn` (AFI 25/SAFI 70) для распространения MAC-адресов и VNI-membership в VXLAN. В ДЦ используется как iBGP с **Route Reflector'ом** для масштабируемого control plane.

## Суть — TCP-сессия и обмен UPDATE'ами

Два роутера устанавливают TCP-соединение (порт 179), становятся **peers**. По этой сессии ходят три типа сообщений:

- **UPDATE** — «у меня появился/исчез маршрут» (announce / withdraw)
- **KEEPALIVE** — «я жив» (по умолчанию раз в 60 сек, hold timer 180 сек). Если не пришёл — пир считается мёртвым, все его маршруты снимаются. Подробнее о liveness — [[neighbor-liveness]].
- **OPEN** — начальное рукопожатие при установке сессии (AS number, capabilities, hold timer)

Это **не** broadcast/multicast, не flooding. Два роутера просто обмениваются таблицей «что я знаю» через надёжное TCP-соединение. Этим BGP отличается от IGP (OSPF/ISIS), которые используют flooding по сегментам.

## Зачем BGP, если есть OSPF

[[igp-vs-egp|IGP vs EGP]] — два класса протоколов с разной моделью доверия и масштаба:

| | IGP (OSPF / ISIS) | EGP (BGP) |
|---|---|---|
| Где | внутри одной организации | между организациями (или большими зонами) |
| Доверие | все роутеры доверяют друг другу | каждый пир — отдельная политика |
| Что обменивают | **всю топологию** (link-state DB) | **только маршруты** (path-vector) |
| Политика | минимальная (метрики) | богатая — route-maps, communities, фильтры |
| Масштаб | сотни роутеров | весь интернет (900K+ префиксов) |
| Сходимость | быстрая (мс–секунды) | медленнее, но управляемая |

В ДЦ BGP используется и **внутри** одной сети (iBGP) — потому что BGP даёт **политику** (фильтровать, приоритизировать, тегировать маршруты) и **расширяемость** (нести не только IPv4-префиксы). Именно расширяемость делает его пригодным для EVPN.

## MP-BGP и address families — ключ к расширяемости

Изначально BGP нёс только IPv4-маршруты. **Multiprotocol BGP (MP-BGP)** позволяет нести **разные типы информации** через одну и ту же TCP-сессию, различая их по address family (AFI/SAFI):

| AFI/SAFI | Что несёт | Пример |
|---|---|---|
| 1/1 | IPv4 Unicast | обычные IP-маршруты |
| 2/1 | IPv6 Unicast | IPv6-маршруты |
| 1/128 | VPNv4 | L3VPN (MPLS) |
| **25/70** | **L2VPN EVPN** | **MAC-адреса, VNI-membership** |

EVPN — не новый протокол. Это **ещё один формат данных** в уже существующем BGP-транспорте. Роутер активирует `address-family l2vpn evpn` на пиринге, и по тому же TCP-соединению начинают ходить MAC-адреса вместе с (или вместо) IP-префиксами.

## iBGP и Route Reflector

В ДЦ все VTEP'ы в одной [[autonomous-system|AS]] → это **iBGP**. У iBGP есть правило: маршрут от iBGP-пира **нельзя переанонсировать** другому iBGP-пиру (split-horizon). Значит для обмена маршрутами нужен **full mesh** — каждый пирится с каждым:

```
  4 VTEP'а = 6 пирингов     10 = 45     50 = 1225
  не масштабируется
```

Решение — **Route Reflector (RR)**: один выделенный роутер, с которым пирятся все. RR отражает маршруты от одного клиента всем остальным, обходя split-horizon:

```
  V1 ──┐
  V2 ──┼──▶ RR ──▶ раздаёт всем
  V3 ──┤
  V4 ──┘

  N VTEP'ов = N пирингов (вместо N*(N-1)/2)
```

RR **не меняет** маршруты — только отражает. Это чисто [[control-plane-data-plane|control-plane]] роль: RR не обязан быть на пути data-plane трафика.

## Применение к EVPN — минимальный набор

Для VXLAN + EVPN в ДЦ (и в BADASS P3):

1. **BGP-стек на каждом VTEP'е** — в BADASS это FRR с `router bgp <ASN>`
2. **Один Route Reflector** — один из роутеров или отдельный
3. **Каждый VTEP пирится с RR** через iBGP (`neighbor <RR> remote-as <ASN>`)
4. **Активирована address-family** `l2vpn evpn` на пирингах
5. **`advertise-all-vni`** — VTEP анонсирует все свои VNI автоматически

Когда host появляется за VTEP'ом:
- VTEP видит MAC → генерирует BGP Type 2 UPDATE
- Шлёт его RR
- RR отражает всем VTEP'ам
- Все VTEP'ы записывают в FDB: «MAC X → remote VTEP Y»
- **Без flood, без learning, без multicast в underlay**

Детально о Type 2, Type 3 и остальных EVPN-маршрутах — в [[vxlan-modes]].
