# Linux Routing Table

moc: [[l3-routing-moc]]
back: [[packet-forwarding]]
next: [[packet-forwarding]], [[l3-routing-moc]]

---

```
  $ ip route show
  ┌─────────────────────────────────────────────────────────────┐
  │ default     via 192.168.1.1  dev eth0   proto dhcp  metric 100│ ← весь прочий трафик
  │ 10.0.0.0/24 via 192.168.1.5  dev eth0   proto static          │ ← руками
  │ 192.168.1.0/24              dev eth0   proto kernel scope link│ ← connected
  └─────────────────────────────────────────────────────────────┘
     префикс       next-hop       интерфейс   откуда взялся
```

Таблица маршрутов — это **инструкция для ядра**: "увидишь пакет с таким `dst IP` — отправляй его туда-то". То самое, что ядро смотрит при [[packet-forwarding|форвардинге]].

## Где она живёт

В ядре Linux. Смотреть и менять — через `iproute2`:

```bash
ip route show          # показать
ip route add ...       # добавить запись
ip route del ...       # удалить
ip route get 8.8.8.8   # спросить "а куда пойдёт пакет на этот адрес?"
```

Старые гайды показывают `route -n` — это устаревшая утилита из `net-tools`. Делает то же самое, но `iproute2` новее и умеет больше.

## Структура записи — что значат поля

```
10.0.0.0/24  via 192.168.1.5  dev eth0  proto static  scope global  metric 100
─────┬─────  ──────┬────────  ───┬────  ─────┬──────  ─────┬──────  ─────┬────
   префикс     next-hop      интерфейс   источник       область      приоритет
```

- **Префикс** (`10.0.0.0/24`) — какие адреса матчит эта запись. `/24` = первые 24 бита должны совпасть, то есть `10.0.0.0 – 10.0.0.255`.
- **`via`** — next-hop, адрес соседнего роутера, которому отдаём пакет. Может отсутствовать, если сеть подключена напрямую.
- **`dev`** — через какой интерфейс отправлять.
- **`proto`** — маркер "кто добавил эту запись":
  - `kernel` — ядро добавило само (connected-сеть)
  - `static` — админ руками (`ip route add`)
  - `dhcp` — DHCP-клиент
  - `bgp`, `ospf` — FRR-демон (через zebra)
  Это **просто метка для дебага**, на работу не влияет.
- **`scope`** — насколько "далеко" known next-hop:
  - `link` — next-hop в одной подсети с нами, достижим напрямую по L2 (ARP)
  - `global` — next-hop сам маршрутизируется
- **`metric`** — приоритет. Если две записи на один префикс — побеждает меньшая.

## Три источника записей

### 1. Connected — ядро добавляет само

Как только [[linux-network-interface|поднимаешь интерфейс с адресом]] — ядро автоматически добавляет маршрут до этой подсети:

```bash
ip addr add 192.168.1.10/24 dev eth0
ip link set eth0 up
ip route show
# 192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.10
```

Логика простая: "раз у меня адрес в `192.168.1.0/24`, значит хосты оттуда достижимы через `eth0` напрямую". Никакого next-hop, `scope link`, `proto kernel`.

**Это база.** Даже без единой ручной настройки у тебя уже есть маршруты до подключённых сетей.

### 2. Static — руками

```bash
ip route add 10.0.0.0/24 via 192.168.1.1 dev eth0
```

"Пакеты на `10.0.0.0/24` отдавай роутеру `192.168.1.1`". Работает до перезагрузки (живёт в памяти ядра). Чтобы сохранить — это уже дистро-специфично: `netplan`, `/etc/network/interfaces`, `NetworkManager`.

### 3. Dynamic — протоколы

OSPF/BGP через [[l3-routing-moc|FRR]] наполняют ту же таблицу с `proto bgp` / `proto ospf`. Для ядра это такие же записи, как static — оно просто форвардит по ним.

Но на самом деле здесь всё сложнее: у FRR есть **своя** таблица в userspace (RIB), в которую стекаются кандидаты от всех протоколов; в ядре (FIB) остаются только winners. См. [[rib-vs-fib]].

## Default route — "всё остальное"

```
default via 192.168.1.1 dev eth0
```

Это псевдоним для `0.0.0.0/0` — матчит **вообще всё**. Куда слать пакет, если точнее ничего не нашлось. На домашнем ноуте это маршрут до роутера провайдера.

На магистральных роутерах интернета **default не бывает** — они знают явные маршруты до всех /24 и меньше (около 1 млн записей в BGP full table). Default есть только на "листьях" сети.

## Longest prefix match — как выбирается запись

Ключевое правило lookup'а. Ядро ищет **самый длинный совпадающий префикс**.

Пример таблицы:

```
default        via 192.168.1.1         ← /0  (всё)
10.0.0.0/8     via 192.168.1.2         ← /8
10.0.5.0/24    via 192.168.1.3         ← /24
```

Пакет на `10.0.5.77`:
- матчит default — но длина 0
- матчит `10.0.0.0/8` — длина 8
- матчит `10.0.5.0/24` — длина 24 ← **победитель**

Более **специфичный** маршрут всегда побеждает более общий. Это позволяет делать "исключения": общий `default` на все, плюс точечные маршруты для конкретных сетей.

Проверить руками — `ip route get`:

```bash
$ ip route get 10.0.5.77
10.0.5.77 via 192.168.1.3 dev eth0
```

## Мини-лаба — роутер без FRR

Простейшая топология: два хоста в разных сетях, между ними Linux-машина.

```
  host-A                  R (Linux)                host-B
  10.0.1.10 ── eth0     eth0 / eth1     eth0 ── 10.0.2.10
            10.0.1.1 ─────┘    └───── 10.0.2.1
              LAN A                     LAN B
```

**На роутере R:**

```bash
sysctl -w net.ipv4.ip_forward=1
ip addr add 10.0.1.1/24 dev eth0
ip addr add 10.0.2.1/24 dev eth1
ip link set eth0 up
ip link set eth1 up

ip route show
# 10.0.1.0/24 dev eth0 proto kernel scope link src 10.0.1.1
# 10.0.2.0/24 dev eth1 proto kernel scope link src 10.0.2.1
```

Обе connected-записи появились сами. Этого достаточно — роутер видит обе сети, умеет в них отправлять.

**На host-A:**

```bash
ip addr add 10.0.1.10/24 dev eth0
ip route add default via 10.0.1.1        # default-маршрут на R
```

**На host-B:**

```bash
ip addr add 10.0.2.10/24 dev eth0
ip route add default via 10.0.2.1
```

Всё. `ping 10.0.2.10` с host-A работает. Роутер форвардит пакет из LAN A в LAN B, обратный идёт тем же путём.

**Это полноценная сеть без единой строчки FRR/BGP/OSPF.** Connected + default — хватает для 80% домашних/офисных сценариев.

## Где static перестаёт хватать

Добавим третью сеть — LAN C за **другим** роутером R2:

```
  LAN A ── R1 ── LAN B ── R2 ── LAN C
  10.0.1      10.0.2      10.0.3
```

Теперь на R1 нужно **вручную** добавить:

```bash
ip route add 10.0.3.0/24 via <адрес R2 в LAN B>
```

А на host-A default указывает на R1 — R1 знает куда слать, всё ок.

Но представь:
- **5 сетей** за R2 — 5 записей на R1 руками
- **Три параллельных роутера** — на каждом те же 5 записей
- **R2 упал**, трафик надо перенаправить через R3 — руками во все таблицы

А теперь **10 роутеров × 20 сетей = 200 записей**, каждое изменение — правки в куче мест. Из-за этого и придумали протоколы маршрутизации: **роутеры сами обмениваются "что я знаю" и сами обновляют таблицы** при изменениях.

Но физически таблица в ядре всё равно выглядит так же, как в нашей мини-лабе. Просто вместо `proto static` там будет `proto ospf` или `proto bgp`.

## Cheatsheet

```bash
ip route show                                   # посмотреть все
ip route show table all                         # включая системные таблицы
ip route get <ip>                               # куда пойдёт пакет

ip route add 10.0.0.0/24 via 192.168.1.1       # через next-hop
ip route add 10.0.0.0/24 dev eth0               # через интерфейс (для point-to-point)
ip route add default via 192.168.1.1            # default

ip route del 10.0.0.0/24                        # удалить
ip route replace 10.0.0.0/24 via 192.168.1.2    # поменять next-hop

sysctl -w net.ipv4.ip_forward=1                 # включить форвардинг
```
