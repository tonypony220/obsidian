```
     L2-кадр                                         L2-кадр
         │                                              │
   ┌─────▼─────┐     UDP tunnel (порт 4789)    ┌─────▼─────┐
   │   VTEP A  │ ═══════════════════════════▶  │  VTEP B   │
   │ (encap)   │     поверх L3-сети            │ (decap)   │
   └───────────┘                                └───────────┘
         │                                              │
         │ outer: IP(src=VTEP_A, dst=VTEP_B)            │
         │ inner: оригинальный Ethernet-кадр            │
```

**TL;DR:** VXLAN (RFC 7348) инкапсулирует Ethernet-кадры внутрь UDP-пакетов, создавая виртуальные L2-сегменты поверх маршрутизируемой L3-инфраструктуры. Идентификатор сегмента — **VNI** (24 бита, до 16M сегментов). Точка инкапсуляции/декапсуляции — **VTEP**.

## Зачем нужен L2-оверлей — от простого к сложному

Ключевой вопрос: если L3 уже умеет маршрутизировать, зачем нужен L2 поверх L3? Пройдём четыре сценария, постепенно усложняя.

### Сценарий 1 — две машины в одной LAN (L2 работает "сам")

Машина A и машина B подключены к одному физическому свитчу. Они в одном L2-сегменте, в одной IP-подсети:

```
  A (192.168.1.10) ── switch ── B (192.168.1.20)
```

- A хочет пинговать B → шлёт ARP-broadcast "кто такой .20?"
- Свитч флудит ARP на все порты → B отвечает
- A узнаёт MAC B, шлёт ICMP напрямую

Всё работает **без конфигурации маршрутов**. Это базовое свойство L2: машины в одном сегменте находят друг друга через broadcast.

### Сценарий 2 — две машины в разных сегментах через роутер

Теперь A и B в разных подсетях, между ними роутер:

```
  A (192.168.1.10) ── [R] ── B (10.0.0.20)
                   L3-граница
```

- A не может ARP'ить B — broadcast не проходит через роутер
- Нужны **явные маршруты** на обеих машинах и на роутере
- `ping` работает только если правильно настроены default gateway / static routes
- **Broadcast-домены разные** — ни DHCP без relay, ни обнаружение соседей, ни кластерные heartbeat'ы, ни прямой ARP

L3 даёт связность, но **теряет свойства L2**: всё что зависит от broadcast и общего сегмента — ломается.

### Сценарий 3 — две машины в разных зданиях, но хотим чтобы думали что в одной LAN

Ситуация: машина A в одном дата-центре, B в другом. Физически между ними L3-сеть (маршрутизируемая, с роутерами, возможно через интернет). Но мы хотим чтобы они **вели себя как в одном L2-сегменте**:

- одна подсеть `192.168.1.0/24`
- ARP между ними работает
- broadcast-сервисы работают
- IP можно переназначить с A на B без перенастройки маршрутов

Чистый L3 этого не даёт — между ними физически L3-граница. Нужен **туннель**, который перенесёт L2-кадры от A к B поверх L3-транспорта. Это и есть VXLAN.

### Сценарий 4 — облако на 10 000 виртуальных машин

Дата-центр с сотней физических хостов, на каждом — сотня виртуальных машин разных клиентов. Требования:

- Каждый клиент видит **свою** сеть, изолированную от других
- VM одного клиента на разных физических хостах — в одном L2-сегменте
- Клиентов много (тысячи), сегментов нужно много
- Подложка дата-центра — маршрутизируемая L3-fabric (Spine-Leaf), потому что L2 на таком масштабе не работает (STP, broadcast-шторма)

Варианты:

- **Отдельная физическая сеть каждому клиенту** — невозможно, слишком дорого
- **[[vlan|VLAN]]** — только 4094 сегмента, для облака мало; плюс требует L2-связности underlay, которой в современном ДЦ нет
- **Только L3 с явной маршрутизацией** — ломает приложения, которые ждут L2-семантики (миграция VM, broadcast-обнаружение, кластеры)
- **VXLAN** — закрывает все требования: 16M сегментов, underlay L3-only, L2-семантика поверх

### Что даёт VXLAN

- **24-bit VNI** — 16 миллионов сегментов (vs 4094 у VLAN)
- **L2 поверх L3** — underlay может быть полностью маршрутизируемой сетью, VXLAN прозрачно переносит L2
- **Мобильность** — VM переезжает между хостами сохраняя MAC/IP; меняется только локальный VTEP
- **Гибкость топологии** — виртуальные сегменты собираются программно, независимо от физики underlay

Это не "L3 не умеет" — это про то, что **некоторые задачи требуют именно L2-семантики**, а растянуть физический L2 через ДЦ или между ДЦ невозможно/неразумно. VXLAN — мост между этими мирами.

### Сходство с VPN

VXLAN и VPN (IPsec, WireGuard, OpenVPN) — одно семейство: **туннели**, инкапсулирующие один протокол в другой. Но цели разные:

| | VPN | VXLAN |
|---|---|---|
| Инкапсулирует | L3 (IP) | **L2** (Ethernet) |
| Главная цель | безопасность, удалённый доступ через недоверенную сеть | виртуализация L2-сегментов, multi-tenancy |
| Шифрование | встроено и обязательно | нет (полагается на безопасность underlay) |
| Сегментов | обычно единицы | до 16M (VNI) |
| Применение | офис↔офис, удалённый сотрудник | внутри/между ДЦ |

Ближайший аналог VXLAN из VPN-мира — не OpenVPN, а **L2VPN / VPLS / EVPN-MPLS** (операторские технологии для растягивания L2 между офисами клиента). VXLAN — "дешёвая версия для ДЦ" поверх обычного IP вместо MPLS.

### Параллель с VLAN

[[vlan|VLAN]] и VXLAN — не противоположности, хотя на первый взгляд кажется что VLAN "разделяет", а VXLAN "объединяет". Обе решают **одну задачу**: дать виртуальные L2-сегменты независимо от физической топологии. Разные стартовые условия:

```
  один физический сегмент  →  VLAN  →  N логических сегментов
  много физических через L3 →  VXLAN →  один логический сегмент
```

В проде используются вместе: VLAN внутри хоста (для изоляции VM на одном гипервизоре), VXLAN между хостами (чтобы одинаковый VLAN-номер на разных хостах стал одним L2-сегментом через L3-underlay). Детально — в [[vlan|VLAN → "Две стороны одной задачи" и "VLAN-to-VXLAN mapping"]].

## Формат пакета

```
  ┌────────────────────────────────────────────────┐
  │ OUTER Ethernet (14 B)                          │
  │   dst MAC: MAC следующего hop'а                │
  │   src MAC: MAC VTEP-A                          │
  │   EtherType: 0x0800 (IPv4)                     │
  ├────────────────────────────────────────────────┤
  │ OUTER IP (20 B)                                │
  │   src IP: VTEP-A                               │
  │   dst IP: VTEP-B (unicast или multicast group) │
  │   protocol: 17 (UDP)                           │
  ├────────────────────────────────────────────────┤
  │ OUTER UDP (8 B)                                │
  │   dst port: 4789 (IANA для VXLAN)              │
  │   src port: hash(inner) — для ECMP             │
  ├────────────────────────────────────────────────┤
  │ VXLAN header (8 B)                             │
  │   flags (1 B): I-бит, означает VNI присутствует│
  │   reserved (3 B)                               │
  │   VNI (3 B = 24 бита)                          │
  │   reserved (1 B)                               │
  ├────────────────────────────────────────────────┤
  │ INNER Ethernet                                 │ ← оригинальный
  │   dst MAC: MAC реального получателя            │    L2-кадр,
  │   src MAC: MAC реального отправителя           │    нетронутый
  │   EtherType: inner payload                     │
  ├────────────────────────────────────────────────┤
  │ INNER payload (IP, ARP, что угодно)            │
  └────────────────────────────────────────────────┘
```

**Overhead — 50 байт** (14 + 20 + 8 + 8). Это важно для MTU (см. ниже).

## Ключевые понятия

### VNI — VXLAN Network Identifier

24-битное поле в VXLAN-заголовке, идентифицирующее конкретный [[l2-segment|L2-сегмент]] в overlay. Одна пара VTEP'ов переносит миллионы независимых сегментов через один UDP-туннель, разделяя их по VNI. Подробнее — [[vni]].

### VTEP — VXLAN Tunnel Endpoint

- Устройство (или софтверная точка), которое делает encap/decap
- На стороне encap: получает L2-кадр → добавляет VXLAN+UDP+IP+Ethernet заголовки → отправляет по L3
- На стороне decap: получает outer-пакет → снимает заголовки → выдаёт оригинальный кадр в локальный bridge/интерфейс
- У VTEP есть собственный **IP-адрес** в underlay-сети. Через этот адрес другие VTEP'ы к нему адресуются.

### Underlay vs overlay

```
  OVERLAY:  виртуальная L2-сеть между контейнерами/VM
            работает по MAC + [[arp|ARP]], прозрачна для них
            
  UNDERLAY: реальная L3-сеть между хостами/VTEP'ами
            работает по IP, OSPF/BGP/static
```

VXLAN — клей между этими двумя слоями. Underlay обеспечивает IP-связность между VTEP'ами, overlay даёт приложениям L2-домен. Концепт шире VXLAN — см. [[overlay-underlay]].

## Как VTEP узнаёт куда слать

Это главный концептуальный вопрос VXLAN. VTEP должен знать:

1. **Для unicast** — за каким удалённым VTEP'ом лежит MAC получателя
2. **Для BUM-трафика** ([[bum-traffic|broadcast/unknown unicast/multicast]]) — всех членов данного VNI

Тонкость: **сам VXLAN-протокол этого не решает** — RFC 7348 описывает только формат конверта, discovery-механизма внутри нет. Почему у VTEP'а принципиально не получается узнать это самому — см. [[vtep-mac-learning-problem]].

Поэтому нужен внешний источник. Три канонических подхода:

- **Static** (ручной) — админ прописывает remote VTEP'ы руками
- **Multicast** — каждый VNI привязан к IP-multicast группе; BUM идёт в группу, все VTEP'ы на неё подписаны
- **EVPN** (control plane) — BGP несёт информацию о MAC'ах и VTEP'ах

Детально — в [[vxlan-modes]]. В BADASS P2 используются static и multicast, в P3 — EVPN.

## MTU и фрагментация

VXLAN добавляет **50 байт** overhead. Если underlay имеет стандартный MTU=1500, то inner-кадр максимум 1450 байт — иначе outer-пакет не влезет в underlay без фрагментации.

Варианты решения:

- **Jumbo frames в underlay** — поднять MTU до 9000 байт, тогда VXLAN с inner=1500 проходит без проблем
- **Уменьшить MTU в overlay** — приложения шлют максимум 1450 байт
- **Фрагментация IP** — работает, но медленно и ломается если DF-бит выставлен

В проде почти всегда включают jumbo frames в underlay дата-центра.

## Настройка в Linux — базовые команды

Linux-ядро реализует VXLAN нативно (модуль `vxlan`). VTEP создаётся как виртуальный интерфейс:

```bash
# базовая команда создания VTEP
ip link add vxlan10 type vxlan \
    id 10 \                      # VNI = 10
    dstport 4789 \               # UDP порт (стандарт IANA)
    dev eth0 \                   # через какой физ. интерфейс
    local 192.168.1.1            # IP этого VTEP'а в underlay

ip link set vxlan10 up
```

Дальше VXLAN-интерфейс подключается к [[linux-bridge]] вместе с интерфейсами локальных контейнеров/хостов:

```bash
ip link add br0 type bridge
ip link set br0 up
ip link set vxlan10 master br0      # vxlan в мост
ip link set veth0 master br0        # контейнер в мост
```

Логика: с точки зрения bridge `vxlan10` — это просто ещё один порт. Всё что входит в `br0` с одного порта — флудится на остальные. `vxlan10` при получении кадра инкапсулирует и отправляет на удалённые VTEP'ы; при получении пакета из underlay декапсулирует и отдаёт в мост.

```
  контейнер ──── veth ──── [ br0 ] ──── vxlan10 ──── underlay ──── удалённый VTEP
   (L2 хост)              (свитч)       (VTEP)      (L3 сеть)
```

## Где используется

- **Kubernetes** — Flannel, Calico (в VXLAN-режиме), Cilium (в VXLAN-режиме)
- **OpenStack** — Neutron с VXLAN/ML2 для изоляции тенантов
- **Дата-центры** — Spine-Leaf фабрики с EVPN-VXLAN
- **NSX (VMware)** — изначально на VXLAN, сейчас Geneve

## В BADASS

P2 поднимает VXLAN вручную между двумя роутерами:

```
  host_wil-1 ── routeur_wil-1 ── switch_wil ── routeur_wil-2 ── host_wil-2
   30.1.1.1    bridge + vxlan10            vxlan10 + bridge    30.1.1.2
               VNI=10                       VNI=10
```

Оба хоста — в одном L2-сегменте `30.1.1.0/24` благодаря VXLAN, хотя между роутерами underlay-сеть L3. Part 2 проходит два режима: сначала static (ручной пиринг VTEP'ов), затем multicast — см. [[vxlan-modes]].
