```
  A ── [switch] ── R1 ── [cloud] ── R2 ── [switch] ── B
                   │                 │
             broadcast-домен 1   broadcast-домен 2
             (L2-сегмент)        (L2-сегмент)

  L3 (IP):   src=A           dst=B              ← не меняется end-to-end
  
  L2 (MAC):  A→R1:  src=MAC_A,  dst=MAC_R1      ← меняется на каждом hop
             R1→R2: src=MAC_R1, dst=MAC_R2
             R2→B:  src=MAC_R2, dst=MAC_B
```

**TL;DR:** L2 и L3 — **разные слои с разными задачами**. L2 локален (один broadcast-домен, адресация по MAC, один hop). L3 глобален (end-to-end, адресация по IP, маршрут hop-by-hop). **IP не меняется по пути, MAC меняется на каждом hop.** [[arp|ARP]] — мост между слоями: «дай MAC по IP».

## Разделение задач

| | L2 | L3 |
|---|---|---|
| Адрес | MAC (48 бит, привязан к железу) | IP (логический, меняется) |
| Область видимости | один сегмент (broadcast-домен) | вся сеть, end-to-end |
| Как узнаёт «куда» | flood-and-learn + ARP | таблица маршрутов ([[linux-routing-table]]) |
| Меняется ли заголовок по пути | **да**, на каждом hop | нет (TTL и checksum — не в счёт) |
| Протоколы | Ethernet, [[arp\|ARP]], 802.1Q | IP, [[icmp\|ICMP]], OSPF, BGP |

Главное: **L2 не знает про IP**. Свитч не читает IP-заголовок, ему это не нужно. Он смотрит только dst MAC и VLAN-тег. Всё «интеллектуальное» решение «куда вообще слать пакет через всю сеть» принимает L3.

## Как живёт пакет «через всю сеть»

1. **Приложение** просит послать на `B (dst IP = 10.0.0.20)`.
2. **L3** смотрит `ip route`: «10.0.0.0/24 — через `R1` (next-hop)». Next-hop — это **IP соседа по моему L2-сегменту**.
3. **[[arp|ARP]]** переводит IP next-hop'а в MAC: «MAC_R1 = aa:bb…».
4. **L2** упаковывает пакет в кадр `src MAC=A, dst MAC=R1` и кладёт в провод.
5. **R1** принимает кадр, снимает L2-заголовок, смотрит dst IP → свой `ip route` → next-hop R2 → ARP(R2) → новый L2-заголовок `src=R1, dst=R2`.
6. И так до последнего hop'а, где next-hop = сам получатель (`scope link`).

**Ключевой инсайт:** роутинг — это цепочка локальных L2-доставок, склеенных L3-решениями. Каждый роутер решает **только следующий шаг**, не весь путь.

## L3 «поверх» L2 — в одном кадре оба заголовка

```
  ┌──────────────────────────────────────────┐
  │ Ethernet (L2)  src MAC, dst MAC, EtherType│  ← локальный hop
  ├──────────────────────────────────────────┤
  │ IP (L3)        src IP, dst IP, TTL        │  ← end-to-end
  ├──────────────────────────────────────────┤
  │ TCP/UDP (L4)   src port, dst port         │
  ├──────────────────────────────────────────┤
  │ payload                                   │
  └──────────────────────────────────────────┘
```

Каждый роутер **переписывает L2-заголовок** (новый src/dst MAC), но **не трогает L3** (IP остаются те же от A до B).

**Пример роутируемого пакета на первом hop'е** (A шлёт B, B в чужой сети, gateway = R1):

```
  src MAC = MAC_A          ← L2: я — отправитель в этом hop'е
  dst MAC = MAC_R1         ← L2: next-hop = gateway в моём сегменте
  ─────────────────────
  src IP  = IP_A           ← L3: исходный отправитель
  dst IP  = IP_B           ← L3: конечный получатель (в другой сети)
```

`dst MAC` указывает на gateway, `dst IP` — на конечного получателя. Это не противоречие, а разделение ответственности: L2 везёт «до следующего соседа», L3 — «до конца». Поэтому `tcpdump` на промежуточном линке покажет MAC соседних роутеров, а не MAC хостов A и B.

## Откуда L2 знает, куда слать кадр

Три механизма, ни один не требует чтения L3-заголовка:

1. **[[arp|ARP]]** — перевод IP next-hop'а в MAC. Это единственный способ для отправителя узнать MAC по IP в обычной сети.
2. **MAC learning на свитче/[[linux-bridge|bridge]]** — пассивное обучение: свитч смотрит `src MAC` входящих кадров и запоминает «MAC X живёт за портом N». При неизвестном `dst MAC` — flood на все порты (см. [[bum-traffic|BUM]]).
3. **Роутинг на L3** — если `dst IP` за пределами сегмента, ядро находит gateway через [[linux-routing-table|ip route]], ARP'ит уже **gateway** (он в моём сегменте), и кадр уходит с `dst MAC = gateway`. Дальше gateway повторяет ту же процедуру для своего следующего hop'а.

## L3-хоп vs L2-устройство — кто что делает на пути

**L3-хоп** — устройство, которое читает IP, уменьшает TTL и переписывает dst MAC: роутер, L3-свитч, firewall в routed mode, NAT. Между двумя L3-хопами может быть сколько угодно обычных свитчей и [[linux-bridge|bridge]]'ей — для L3 они **прозрачны**.

```
  A ── sw1 ── sw2 ── R1 ── [WAN] ── R2 ── sw3 ── B
         L2          L3              L3        L2
          ╰── один L3-hop ──╯ ╰── один L3-hop ──╯

  traceroute покажет: R1, R2, B  (свитчи невидимы)
  TTL уменьшается только на R1 и R2
```

«Next-hop в моём сегменте» означает «следующий L3-хоп достижим через L2 без других роутеров на пути». Сколько свитчей по дороге — неважно.

**L2-свитч не читает IP и не делает ARP.** Видит `dst MAC` → MAC-таблица → форвард на нужный порт. Всё. ARP делает тот, кто **кладёт кадр в L2-сегмент** — исходный хост или роутер на каждом L3-хопе. Промежуточные свитчи только доставляют кадр до адресата по MAC.

```
  A ── sw1 ── sw2 ── R1 ── sw3 ── R2 ── sw4 ── B

  A:   ip route → R1 в сегменте → ARP(R1) → MAC_R1
       кадр: src=MAC_A, dst=MAC_R1, dst IP=IP_B
  sw1: ── смотрю dst MAC → форвард (IP не читаю, ARP не делаю)
  sw2: ── то же
  R1:  снимаю L2 → dst IP → ip route → next-hop R2 → ARP(R2)
       новый кадр: src=MAC_R1, dst=MAC_R2
  sw3: ── форвард по MAC
  R2:  та же процедура → ARP(B) → src=MAC_R2, dst=MAC_B
  sw4: ── форвард по MAC
  B:   MAC мой → снимаю L2 → dst IP мой → отдаю в стек
```

Правило:

- **L2-хоп** (свитч/bridge): только `dst MAC` → форвард. Без L3, ARP, TTL.
- **L3-хоп** (роутер): `dst IP` → `ip route` → next-hop → ARP → новый src/dst MAC, TTL−1.

## Когда L2 «хватает» без L3

Если `dst IP` **в твоей подсети** (совпадает по маске с твоим интерфейсом) — L3 говорит: «next-hop = сам получатель, `scope link`». Тогда не нужен gateway, не нужна маршрутизация — просто ARP и отдать в провод. Это то, что происходит внутри одного VLAN или в обычной домашней сети.

Когда `dst IP` **не в твоей подсети** — включается L3 и выбирает gateway.

## Что из этого следует для VLAN и VXLAN

- **[[vlan|VLAN]]** — чисто L2-механизм. Разделяет один свитч на несколько логических broadcast-доменов. К L3 отношения не имеет: для маршрутизации между VLAN нужен отдельный роутер.
- **[[vxlan|VXLAN]]** — L2-сегмент растянут через L3-сеть (см. [[overlay-underlay]]). Внутри overlay всё работает как обычный L2 с ARP и flood-and-learn. Underlay — обычная L3-сеть, ничего про L2-сегмент не знающая. Прямое следствие: VTEP на стыке L2/L3 не может сам узнать, за каким удалённым VTEP'ом живёт чужой MAC — см. [[vtep-mac-learning-problem]].
