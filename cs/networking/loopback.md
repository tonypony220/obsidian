```
  ┌──────────────────────────────────────────┐
  │ host                                     │
  │                                          │
  │   eth0 = 10.0.0.5/24 ─── провод ──▶      │
  │   eth1 = 192.168.1.5/24 ─ провод ──▶     │
  │                                          │
  │   lo   = 127.0.0.1/8                     │
  │   lo:1 = 10.255.255.1/32                 │
  │   (виртуальный интерфейс, всегда up,     │
  │    физически никуда не подключён)        │
  │                                          │
  │   процесс A ──▶ 127.0.0.1:5432 ──▶ proc B│
  │              (через ядро, без NIC)       │
  └──────────────────────────────────────────┘
```

**TL;DR:** Loopback (`lo` в Linux) — виртуальный сетевой интерфейс, существует только в ядре, физически никуда не подключён. **Всегда up**, не зависит от физических интерфейсов. Стандартный IP `127.0.0.1/8` — special-диапазон, не уходит на провод. Используется для локальной коммуникации процессов, диагностики, и как стабильный endpoint для роутинговых протоколов и сервисов независимо от состояния физических линков.

## Что это

`lo` — виртуальный NIC, создаётся ядром при загрузке, всегда up, MAC `00:00:00:00:00:00`, не подключён к проводу. Пакеты, отправленные на адрес назначенный loopback'у, ядро **разворачивает обратно** в свой же IP-стек.

## Зачем нужен — пять ролей

**1. Локальная коммуникация процессов.** PostgreSQL слушает `127.0.0.1:5432`, веб-приложение коннектится туда же. Пакет идёт через ядро, не выходит на NIC, не виден извне (`127.0.0.0/8` не маршрутизируется).

**2. Тест IP-стека.** `ping 127.0.0.1` — базовая проверка «жив ли стек». Не пингуется → проблема в ядре или TCP/IP-стеке.

**3. Стабильный IP, не привязанный к физическому железу.** На роутерах добавляют доп. IP на lo и используют как:

- **router-id для BGP/OSPF** — идентификатор роутера в протоколе
- **endpoint BGP-сессии** — peer'ы коннектятся на этот IP, а не на физический интерфейс

Преимущество: **lo всегда up**. Если один физический линк упал, но есть альтернативный путь — BGP-сессия не порвётся.

```
  router-A (lo:1 = 10.255.255.1/32)        router-B (lo:1 = 10.255.255.2/32)
   │                                        │
   ├── eth0 ─── link 1 ──── eth0 ───────────┤
   │                                        │
   └── eth1 ─── link 2 ──── eth1 ───────────┘

  BGP-сессия: 10.255.255.1 ↔ 10.255.255.2
  link 1 упал → BGP идёт через link 2, сессия жива
  если бы привязка была к eth0 — сессия порвалась бы
```

**4. Bind сервисов к стабильному адресу.** DNS, control-plane-демоны биндятся на IP loopback'а. Смена IP физических портов не ломает привязку.

**5. Anycast / VIP.** На нескольких машинах вешают **один и тот же** IP на lo, каждая анонсирует через BGP. Клиент попадает на ближайший живой инстанс — так работают Cloudflare `1.1.1.1`, Google `8.8.8.8`.

## Loopback IP = идентификатор роутера, не порта

Концептуальная рамка, которая объясняет почему работают роли 3–5:

```
  физический IP                    loopback IP (router-id)
  ─────────────                    ──────────────────────
  "адрес ЭТОГО ПОРТА"              "адрес РОУТЕРА"
  привязан к eth0                  привязан к роутеру как сущности
  упал eth0 → IP недостижим        упал eth0 → IP жив через eth1
```

Технически IP всё ещё **на интерфейсе** (`lo`) — других мест ему жить негде, ядро так устроено. Но `lo` — особый интерфейс, не зависящий от железа. Поэтому **формально** «IP интерфейса», а **по сути** «IP роутера».

Параллель с hostname:

- `hostname` = «имя машины», не привязано к сетевой карте
- IP на eth0 = «адрес этой карты»
- IP на lo = «адрес машины» (как hostname, но в IP-форме)

Поэтому в BGP/OSPF конфигах прямо пишут `router-id 10.255.255.1` — это **идентификатор роутера**, не порта. Другие пиры видят его как «адрес роутера R1», а не «адрес eth0 на R1». Им неважно через какой физический порт идёт трафик — для них это один и тот же endpoint. Loopback-IP — стандартный способ дать роутеру стабильный «паспортный номер», переживающий падение любого линка.

## Тонкость: 127.x vs другие IP на loopback

`127.0.0.0/8` — **специальный диапазон**, ядро гарантирует что пакеты с/на эти адреса **никогда не уходят на провод**. Это свойство **адресов**, не интерфейса.

Если повесить на lo обычный IP (`10.255.255.1/32`) — он уже **не «локальный»**. Пакеты к нему **могут прийти извне**, если другие хосты знают как до него добраться через маршрутизацию. Именно поэтому BGP router-id на loopback достижим другим роутерам.

```
  127.0.0.1/8 на lo     →  никогда не уходит наружу
  10.255.255.1/32 на lo →  обычный IP, достижим извне через маршрутизацию
```

`lo` — просто **интерфейс с особым свойством "всегда up"**. «Локальность» `127.0.0.1` — отдельное свойство адреса.

## Зачем `/32` маска

При навешивании доп. IP на loopback используют `/32` (один адрес, не подсеть). Объявлять подсеть на lo нет смысла — там нет соседей по L2. `/32` означает «это конкретный host-route доступный через этот интерфейс». Маршрут к нему другие роутеры получают через OSPF/BGP как **host route** (`/32`).

## Команды

```bash
ip addr show lo                         # всё что висит на loopback
ip addr add 10.255.255.1/32 dev lo      # добавить router-id
ip addr del 10.255.255.1/32 dev lo      # убрать

ping 127.0.0.1                          # базовый тест IP-стека
ss -tlnp | sport = :5432                # кто слушает на этом порту
ss -tlnp | grep 127.0.0.1               # сервисы привязанные к loopback

ip route show table local               # видны все «свои» IP, включая loopback
```

## Не только в сетях

Паттерн «стабильный логический endpoint, отвязанный от физических ресурсов» встречается везде:

- **DNS-имена** — логическое имя сервиса, IP за ним может меняться
- **VIP / floating IP** — IP плавает между хостами в кластере, клиент знает только VIP
- **Service discovery** (Consul, k8s Service) — логический endpoint, конкретные pod'ы за ним меняются
- **Symbolic links** — стабильное имя над меняющимся ресурсом
- **Stable identifier vs transient state** в распределённых системах (id сущности vs её текущее место)

Общее везде: **разделение логического имени/адреса и физического носителя**. Клиент знает стабильную абстракцию, инфраструктура подменяет под ней реальные ресурсы. Loopback — частный случай: адрес, не привязанный ни к одному физическому порту, и потому переживающий падение любого из них.
