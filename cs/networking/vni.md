```
  VXLAN header (8 байт)
  ┌─────────────────────────────┐
  │ flags   (1 B)               │
  │ reserved (3 B)              │
  │ VNI     (3 B = 24 бита) ◀───┼── идентификатор L2-сегмента в overlay
  │ reserved (1 B)              │
  └─────────────────────────────┘

  VTEP-A                                      VTEP-B
  ├─ bridge br-100 ──┐                    ┌── bridge br-100
  │                  ▼                    ▼
  ├─ vxlan100 ── UDP 4789, VNI=100 ── vxlan100 ──┤
  │                                                │
  ├─ bridge br-200 ──┐                    ┌── bridge br-200
  │                  ▼                    ▼
  └─ vxlan200 ── UDP 4789, VNI=200 ── vxlan200 ──┘
```

**TL;DR:** **VNI** — 24-битное число в заголовке [[vxlan|VXLAN]], идентифицирующее конкретный виртуальный [[l2-segment|L2-сегмент]] в overlay. Одна пара VTEP'ов может переносить **миллионы** независимых сегментов через один UDP-туннель, разделяя их по VNI. Функционально = VLAN ID для overlay.

## Роль — мультиплексирование сегментов

Один VTEP обычно обслуживает **много** overlay-сегментов (тенантов, клиентских сетей). Все они идут через один underlay-IP и один UDP-порт (4789). VNI — **ярлык**, по которому получатель при decap понимает в какой локальный bridge положить кадр.

Без VNI пришлось бы поднимать отдельный UDP-порт / отдельный туннель на каждый сегмент. VNI решает это одним полем в заголовке.

## Размер и последствия

- **24 бита → 16 777 214** полезных значений (0 и max зарезервированы)
- vs **4094** у [[vlan|VLAN ID]] (12 бит)
- Хватает для облачных провайдеров с миллионами тенантов

Это главная мотивация VXLAN: VLAN размер пространства исчерпывается в средних облаках, VNI — почти нет.

## Изоляция — ядро работы VNI

**Кадры разных VNI никогда не пересекаются.** Механика:

- VTEP при encap ставит VNI в заголовок, исходя из того, в какой локальный bridge/VXLAN-интерфейс пришёл кадр
- VTEP при decap читает VNI из заголовка, ищет локальный `vxlanN` интерфейс с `id=N`, отдаёт кадр именно в его bridge
- Нет совпадения VNI — нет доставки

Поэтому хосты в разных VNI на том же физическом VTEP **не видят друг друга**, не получают чужой broadcast, могут использовать перекрывающиеся IP.

## VNI = один [[l2-segment|L2-сегмент]]

Всё, что обсуждается в [[l2-segment]] (broadcast-домен, ARP, flood-and-learn), применимо к одному VNI:

- Broadcast внутри VNI долетает до всех членов (через underlay multicast / head-end replication / EVPN — см. [[vxlan-modes]])
- [[arp|ARP]] работает как в обычной LAN
- MAC-learning — либо flood-and-learn в data plane, либо распространение через EVPN в control plane

## VNI vs VLAN ID

| | VLAN ID | VNI |
|---|---|---|
| Размер | 12 бит | 24 бита |
| Сегментов | 4094 | 16M |
| Где живёт | 802.1Q тег в Ethernet-кадре | VXLAN-заголовок поверх UDP |
| Транспорт | L2 (trunk-линки) | L3 (underlay IP) |
| Границы | один L2-fabric | любая IP-связность между VTEP'ами |

Типовой паттерн в ДЦ — **маппинг 1:1**: VLAN ID внутри хоста ↔ VNI между хостами. На границе хоста bridge переводит одно в другое. См. «VLAN-to-VXLAN mapping» в `vlan.md`.

## Настройка в Linux

```bash
ip link add vxlan100 type vxlan \
    id 100 \                 # ← VNI
    dstport 4789 \
    dev eth0 \
    local 192.168.1.5
```

Один интерфейс `vxlanN` соответствует **одному** VNI. На хосте с N тенантами поднимается N VXLAN-интерфейсов, каждый привязан к своему bridge.

## Не только VXLAN — аналоги в других overlay

Концепция «идентификатор overlay-сегмента в заголовке туннеля» шире VXLAN:

- **Geneve** — VNI (24 бита, совместимо с VXLAN) + расширяемые TLV-опции
- **NVGRE** — VSID (24 бита) в GRE-заголовке
- **MPLS L2VPN** — VC label в стеке MPLS-меток
- **802.1Q (VLAN)** — VLAN ID (12 бит), тот же принцип, но в L2-транспорте

Общее везде: **число-идентификатор в заголовке инкапсуляции, по которому приёмник разводит трафик по изолированным сегментам**.
