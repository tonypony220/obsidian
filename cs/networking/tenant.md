  │  ┌── tenant A ────┐   ┌── tenant B ────┐           │

  │  └────────────────┘   └────────────────┘    же IP  │
  │                                                    │
  │  общий underlay, свитчи, VTEP'ы — но A и B         │
  │  не видят друг друга и имеют независимые адреса    │
  └────────────────────────────────────────────────────┘

**TL;DR:** **Tenant** (тенант, арендатор) — изолированная логическая среда для одного пользователя/клиента/команды на общей физической инфраструктуре. **Multi-tenancy** — принцип, когда одна инфра обслуживает много тенантов одновременно, сохраняя между ними **полную изоляцию** (сети, данных, ресурсов). В сетях изоляция достигается через [[vlan|VLAN]], [[vxlan|VXLAN]] (VNI = один тенант), namespace, VPC.

## Зачем нужно

Физическая инфра дорогая, поэтому её **шарят**. Но клиенты не должны видеть чужой трафик, чужие IP-пространства, чужие данные. Требования multi-tenancy:

- **Сетевая изоляция** — тенант A не получает broadcast от тенанта B, не видит его хостов
- **Независимость адресных пространств** — оба тенанта могут использовать `10.0.0.0/24` без конфликта
- **Изоляция ресурсов** — CPU/память/диск не утекают между тенантами
- **Биллинг** — учёт по тенантам
- **Безопасность** — компрометация одного тенанта не затрагивает других

## Механизмы изоляции в сетях

| Уровень | Механизм | Сегментов |
|---|---|---|
| L2 (один свитч) | [[vlan|VLAN ID]] | 4094 |
| L2 overlay | [[vxlan|VXLAN VNI]] | 16M |
| L3 (Linux) | network namespace | сколько угодно |
| Cloud (AWS/GCP) | VPC / Virtual Network | тысячи per account |
| Kubernetes | NetworkPolicy + CNI | по namespace/policy |

Всё это — **реализации одной концепции**: дать каждому тенанту свой [[l2-segment|L2-сегмент]] или свою L3-сеть, не покупая отдельное железо.

## VNI и тенанты — типовой маппинг

В облаках и современных ДЦ часто **один тенант = один или несколько VNI**:

- VM клиента подключены к локальному bridge
- Bridge привязан к VXLAN-интерфейсу с VNI тенанта
- На удалённом хосте — такой же bridge + VXLAN с тем же VNI
- VM клиента на разных физических хостах **в одном L2-сегменте**, хотя underlay между хостами — L3

Хосты с **разными VNI** на том же VTEP полностью изолированы: VTEP при decap смотрит VNI из VXLAN-заголовка и кладёт кадр в **соответствующий** bridge. Кадры разных VNI никогда не пересекаются.

## Перекрытие адресов

Ключевое свойство: тенанты **могут использовать одни и те же IP**. Тенант A с `10.0.0.0/24` и тенант B с `10.0.0.0/24` не конфликтуют — они в разных [[l2-segment|L2-сегментах]]/VNI/namespace. Когда пакет выходит наружу (в интернет или на shared сервис) — применяется NAT, который разводит тенантов по уникальным внешним IP.

Это делает тенанта **переносимым**: клиент может миграцию из on-prem в облако делать без переназначения IP.

## Не только в сетях

Концепция шире сетей:

- **БД** — один инстанс PostgreSQL обслуживает много tenant'ов через отдельные schemas/row-level security
- **SaaS-приложение** — один backend обслуживает тысячи организаций, данные разделены по `tenant_id`
- **Kubernetes** — namespace как единица изоляции workloads
- **VM hypervisor** — одна железка, много VM разных владельцев

Общее везде: **shared инфра + изоляция на уровне логики**. Сеть — один из слоёв, где эта изоляция должна быть построена явно.
