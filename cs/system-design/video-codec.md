# Video Codec — intra/inter compression

```
кадры:  I ──▶ P ──▶ P ──▶ P ──▶ P ──▶ ... ──▶ I ──▶ P
        │     │
        │     └─ только diff: motion vectors + residual
        └─ keyframe: полный кадр, сжат intra (как JPEG)

пиксели ───▶ [codec: intra + inter] ───▶ битстрим ───▶ [container / протокол] ───▶ сеть
1.5 GB/s                                 ~1-3 MB/s
```

**TL;DR:** Видеокодек (H.264/HEVC/AV1) жмёт видео ~1000×: intra-frame выкидывает незаметные глазу детали внутри кадра, inter-frame шлёт только diff между кадрами. Кодек ≠ протокол: HLS/WebRTC ничего не сжимают, они везут готовый битстрим.

## Проблема

Raw 4K60: `3840 × 2160 × 3 байта ≈ 25 MB/кадр` → `× 60 fps ≈ 1.5 GB/s` → 5 минут ≈ 450 GB. Слать по сети невозможно → сжатие обязательно. Raw как файл обычно не существует вообще — камера кодирует в момент записи.

## Intra-frame (внутри кадра)

Кадр сжимается сам по себе, без соседей — как JPEG:
- блоки → выкинуть детали, которые глаз не различает (quantization)
- оставшиеся похожие значения закодировать компактно (entropy coding — «группировка байтов»)
- даёт ~10–20×; результат = **I-frame (keyframe)**

## Inter-frame (между кадрами)

Основной множитель. Keyframe шлётся редко (раз в 1–2 сек), кадры между ними хранят не пиксели, а **разницу с опорным кадром**:
- «блок не изменился» → 0 байт
- «блок сдвинулся на N пикселей» → **motion vector** + маленькая поправка (residual)
- статичный фон почти бесплатен; P-frame — diff от предыдущего, B-frame — от предыдущего и следующего

Следствие: перемотка прыгает к ближайшему keyframe — P/B-кадры без опоры не декодируются.

## Кодек vs контейнер vs протокол

| Слой | Что делает | Примеры |
|---|---|---|
| Кодек | сжимает пиксели → битстрим | H.264, HEVC, VP9, AV1 |
| Контейнер | упаковывает битстримы (видео+аудио+субтитры) | MP4, MKV, WebM |
| Протокол | доставляет по сети | HLS, DASH, WebRTC/RTP |

Кодек — стандарт сжатия, не протокол. Encoder/decoder реализованы и софтом (x264), и отдельным кремнием в GPU/SoC (NVENC, Apple Media Engine) — поэтому 4K играется на слабом железе, а запись экрана не ест CPU.

## Когда происходит сжатие

| | VOD (YouTube, Netflix) | Live (Twitch, Zoom) |
|---|---|---|
| Encode | 1 раз заранее, при загрузке; хранится в нескольких качествах | реалтайм, покадрово, аппаратным энкодером |
| Стрим | доставка готовых байтов по HTTP | кадр → encode → сеть, цикл 60 раз/сек |

Инвариант общий: сырые пиксели по сети не летят никогда — сжатие всегда на стороне источника до отправки.

## Концепция шире: delta encoding

«Слать только изменения» — общий паттерн, не видео-специфика:

- **git** — packfile хранит объекты как delta от похожих, не полные копии
- **rsync** — передаёт только изменившиеся блоки файла (rolling checksum)
- **React** — virtual DOM diff: в реальный DOM применяются только изменения
- **Репликация БД** — реплике шлётся поток изменений (WAL/binlog), не снапшоты
- **Мультиплеерные игры** — state sync: только изменившиеся поля мира

Общее везде: полное состояние дорого, дельта дёшева — платим за это зависимостью от опорной точки (потерял base → нужен полный снапшот, у видео это keyframe).
