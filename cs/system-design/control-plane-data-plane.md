# Control Plane vs Data Plane

back: [[rib-vs-fib]]
next: [[rib-vs-fib]] [[vxlan-modes]]

---

```
  ┌─────── CONTROL PLANE ─────────┐
  │  кто принимает решения        │
  │  - медленный                  │
  │  - сложный (логика, политики) │
  │  - обновляется часто          │
  │  - высокоуровневый язык       │
  └──────────────┬────────────────┘
                 │ конфигурация / правила / state
                 ▼
  ┌─────── DATA PLANE ────────────┐
  │  кто исполняет                │
  │  - быстрый (hot path)         │
  │  - простой (минимум логики)   │
  │  - стабильный                 │
  │  - низкоуровневый (C, ASIC)   │
  └───────────────────────────────┘
```

Фундаментальный архитектурный паттерн: **разделить "кто думает" и "кто делает"**. Применяется везде, где есть асимметрия между "медленное умное решение" и "быстрое тупое исполнение".

## Суть

Любая система, которая **что-то обрабатывает по правилам**, имеет две логики:
1. **Откуда берутся правила** — это control plane
2. **Как применяются к каждому объекту** — это data plane

Пока объём маленький, они совмещены в одном коде. Но когда обработка попадает на hot path (миллионы запросов, wire-speed forwarding), разделение становится **обязательным**.

## Классические примеры

### Сетевая маршрутизация

Прямо то, что разбирали в [[rib-vs-fib]]:

- **Control plane:** OSPF, BGP, zebra. Считают маршруты, договариваются с соседями, выбирают winner.
- **Data plane:** ядро Linux (или ASIC в железном роутере). Форвардит пакеты по готовой FIB на скорости провода.

Control plane может пересчитывать минутами — data plane всё это время форвардит по текущему FIB без остановки.

### SDN — радикальная версия

Software-Defined Networking. Весь control plane **вынесен в централизованный контроллер**, свитчи становятся "тупыми исполнителями":

```
       ┌────── SDN Controller ──────┐
       │  (один на весь дата-центр) │
       │  принимает все решения     │
       └─────────────┬──────────────┘
                     │ OpenFlow
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
    switch       switch        switch
    (data        (data         (data
     plane)       plane)        plane)
```

Каждый свитч только форвардит. Вся логика — в контроллере. Преимущество: видна вся топология, легко делать сложные политики. Риск: контроллер = single point of failure.

### Service mesh (Istio, Linkerd) — канонический пример

Сегодня это учебный кейс паттерна.

- **Control plane:** Istio Pilot раздаёт конфиги, Citadel — сертификаты, Galley — валидация.
- **Data plane:** сайдкар Envoy в каждом поде перехватывает весь трафик и применяет правила (mTLS, retries, timeouts, routing).

Можно обновлять Istio control plane — сайдкары продолжают работать по последним полученным правилам.

### Kubernetes

- **Control plane:** `kube-apiserver`, `scheduler`, `controller-manager`, `etcd`. Принимают решения "какой под где запустить".
- **Data plane:** `kubelet` на каждой ноде, `kube-proxy`, сами контейнеры. Запускают, обрабатывают трафик.

Если упадёт control plane — уже запущенные поды продолжат работать (data plane автономен). Новых подов запустить не получится (решения принимать некому), но существующий сервис не упадёт.

### Базы данных

- **Master-replica:** master принимает writes (control над состоянием), replicas отдают reads (data plane чтений).
- **Распределённые БД** (Spanner, CockroachDB, TiDB): слой координации (Placement Driver, транзакционный координатор) vs слой хранения (хранят данные, исполняют локальные операции).

### Хранилища

- **HDFS/GFS:** NameNode (знает где лежат блоки) vs DataNodes (хранят сами блоки).
- **S3:** метаданные (владельцы, права, местоположение) vs data nodes (хранят байты).

### Другие

- **L4/L7 прокси** (HAProxy, Nginx): конфиг (control) vs обработка соединений (data).
- **Kafka:** controller broker (metadata, assignments) vs brokers (hot path — пишут и отдают сообщения).
- **CI/CD:** планировщик пайплайнов vs воркеры, исполняющие джобы.

## Выгоды паттерна

### 1. Независимое масштабирование

Data plane растёт с трафиком (может быть тысячи инстансов). Control plane — один или небольшое количество. Нет смысла масштабировать их одинаково.

### 2. Обновление без даунтайма (graceful restart)

Рестартуешь control plane — data plane работает по последним правилам. Когда control plane поднимется — синхронизируется. Применяется:
- в FRR: рестарт `bgpd` не прерывает трафик
- в Envoy: hot reload конфига без drop'а соединений
- в k8s: рестарт `kube-apiserver` не ломает работающие поды

### 3. Разные технологии для разных задач

- Control plane — Go/Python/Java, для удобной работы с логикой
- Data plane — C/C++/Rust или вообще железо (ASIC, FPGA, eBPF)

### 4. Границы отказа

Баг в сложной логике control plane (например ошибка в политике BGP) не рушит горячий путь. Роутер продолжит форвардить по существующему FIB, пока админ чинит.

### 5. Тестируемость

Control plane легче мокать, покрывать unit-тестами, прогонять сценарии. Data plane тестируется нагрузочно и через integration.

## Когда НЕ применять

Маленькие системы — **оверкилл**. Если у тебя один веб-сервер обслуживает 100 RPS, разделять "решатель" и "исполнитель" — лишняя сложность. Паттерн окупается когда:
- hot path критичен к латентности/пропускной
- система распределённая (много исполнителей, которым надо синхронизировать состояние)
- нужен graceful restart или independent scaling

## Мнемоника

> **"Кто-то умный настраивает, кто-то быстрый исполняет."**

Как только видишь такое разделение — знай, это **control/data plane**. И сразу понятно что делать: скейлить по-разному, обновлять по-разному, тестировать по-разному, ошибки изолировать между слоями.
