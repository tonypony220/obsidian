# Obsidian Vault — инструкции для агента

## Структура

```
cs/
  front/            — фронтенд: состояние, навигация, UI (front-moc.md)
  ml/               — машинное обучение: классификация, метрики, обучение (ml-moc.md)
  networking/       — сети, протоколы, API: REST, gRPC, GraphQL
  os/               — ОС/ядро (os-moc.md). Канонические файлы ЗДЕСЬ, версионируются этим репо.
                      В репо kfs (~/ecole42-projects/kfs) на Маке есть обратный симлинк docs/notes → сюда (у них в .gitignore) — править можно с любой стороны
  system-design/    — архитектура, паттерны, трейдоффы
  observability/    — метрики, логи, трейсинг, алерты
  fp-patterns-moc.md — паттерны ФП (иммутабельность, чистые функции, Option/Result...)
french/             — французский язык
templates/          — шаблоны заметок
inbox/              — быстрые заметки для последующей сортировки
```

## Git-синк

Vault = git-репо `github.com/tonypony220/obsidian`. Пишут агенты с нескольких машин (Mac, VPS), читается с iPhone → расхождение возможно в любой момент, локальное состояние не считать актуальным.

- **Начало сессии:** `git pull --rebase` — до того как читать или писать. Иначе рискуешь дописать заметку, которой на другой машине уже нет, или пересоздать существующую
- **После каждой законченной заметки:** `git add -A && git commit && git push`. Не копить пачками: чем дольше держишь локально, тем крупнее будущий конфликт
- **Push отклонён** (`non-fast-forward`, кто-то запушил раньше) → `git pull --rebase` → `git push` снова
- **Rebase дал конфликт** → остановиться и спросить оператора. Обе стороны писал агент, автоматически выбранная сторона = стёртая работа, которую негде восстановить
- **Commit message:** `notes(<раздел>): <что>`, англ. Пример: `notes(ml): add gradient clipping`
- Идентичность машины задавать в локальном конфиге репо (`git config user.name`), чтобы в истории было видно, кто писал: `claude-mac`, `claude-vps`
- `.obsidian/` в `.gitignore` — у каждого устройства свой конфиг, версионировать нечего

## Правила создания заметок

### Формат
- Каждая заметка — отдельный `.md` файл
- Обязательный YAML frontmatter: `title`, `tags`, `date`
- Имя файла: kebab-case на английском (`edge-vs-serverless.md`)
- Контент: на русском (кроме терминов и кода)

### Структура заметки

```markdown
---
title: ...
tags: [...]
date: ...
---

# Title

moc: [[some-moc]]
back: [[parent-note]]
next:
- [[a]]
- [[b]]
- [[c]]

---

<ASCII-иллюстрация>

**TL;DR:** одно-два предложения — суть заметки.

## Остальной контент
```

Правила:
- **Блок ссылок вверху** сразу после H1 — ссылки это основа навигации в Obsidian, они должны быть видны первыми
- Порядок: `moc:` → `back:` → `next:` (от глобального к локальному к следующему шагу)
- Пустые поля опускать: нет `back:` — не писать строку
- `next:` может дублировать wikilinks из тела — это полный навигационный индекс, независимый от текста
- **`next:` — всегда вертикальным списком буллетов**, по одной ссылке на строку. Даже если ссылок 2–3. Одна длинная строка с кучей `[[...]]` нечитабельна. `moc:` и `back:` обычно одиночные — остаются на одной строке
- Горизонтальный разделитель `---` после блока ссылок — визуально отделяет навигацию от контента
- **ASCII-иллюстрация** — визуальный якорь для памяти, даже если тема плохо ложится на схему
- **TL;DR** — одно-два предложения жирным inline (`**TL;DR:** ...`). Если не помещается — сокращать, а не расширять

### Атомарность
- Одна заметка — одна идея/концепция. Цель — граф маленьких связанных идей, а не длинные статьи
- Когда оператор просит добавить контент в существующую заметку — сначала оценить: можно ли выделить отдельные идеи в самостоятельные заметки? Если да — создать главную заметку + зависимые, связать ссылками
- Но не разбивать ради разбиения: если идеи сильно связаны и по отдельности теряют смысл — держать вместе. Атомарность не значит "одно предложение", а значит "одна самодостаточная мысль"
- Признаки что заметку пора разбить: несколько H2-секций про разные концепции, длина > 80 строк, "а ещё вот это связанное"

### Обобщение концепций за пределы домена
- Когда концепция является **паттерном** (а не узкоспециализированной реализацией) — добавить в конец заметки секцию «Не только в …» / «Концепция шире»
- Цель — показать, что та же абстракция встречается в других доменах. Это помогает видеть паттерны, а не запоминать их как разрозненные факты
- Формат: 3–5 коротких буллетов, каждый — один домен + одно предложение «как выглядит там». Затем одна строка «Общее везде: …» с фундаментальным инвариантом
- Примеры паттернов с обобщением: tenant (сеть / БД / SaaS / k8s / гипервизор), идемпотентность (HTTP / очереди / миграции), кэширование (CPU / CDN / браузер / БД), разделение слоёв (L2/L3 / OSI / микросервисы)
- Не натягивать: если концепция специфична (например, `veth-pair`) — не выдумывать обобщения ради формы. Секция есть только там, где она честная
- Обобщение — **не** аналогия. Не «роутер как почтальон», а «та же формальная структура встречается в X, Y, Z»

### Размещение
- Класть в папку по **основной** теме
- Кросс-тематические связи — через `[[wikilinks]]`, не через дублирование
- Не уверен куда — кидай в `inbox/`

### Связи и навигация
- Ссылки — основной инструмент навигации, важнее папок. Папка = грубая сортировка по теме, ссылка = смысловая связь
- Ссылаться щедро: если упоминаешь концепцию для которой есть (или должна быть) заметка — ставь `[[wikilink]]`
- Три типа навигационных ссылок (в блоке вверху заметки):
  - `moc:` — ссылка на MOC темы (глобальный индекс). Обычно одна
  - `back:` — родительская/обзорная заметка (например `linux-virtual-network-devices` для `veth-pair`). Не MOC, а concept-родитель
  - `next:` — связанные заметки того же уровня, куда идти дальше. **Всегда вертикальным списком буллетов**, по одной ссылке на строку (не в одну строку через пробел — нечитабельно)
- При создании новых заметок — **всегда** прошивать ссылки в обе стороны: новая ссылается на существующие через `moc:`/`back:`/`next:`, существующие получают обратную ссылку через `next:`
- Теги — для сквозных категорий: `#concept`, `#pattern`, `#tradeoff`, `#tool`, `#cheatsheet`
- Не плодить теги — переиспользовать существующие

### MOC (Map of Content)
- MOC — заметка-оглавление по теме. Не содержит контент, а собирает ссылки с короткими пояснениями
- Создавать MOC когда по теме накопилось 7+ заметок и нужна точка входа
- Имя файла: `<тема>-moc.md` (например `networking-moc.md`)
- Формат: список `[[ссылок]]` сгруппированных по подтемам, каждая с однострочным пояснением
- MOC может ссылаться на другие MOC — это создаёт иерархию навигации без вложенных папок
- При создании новой заметки — проверить, есть ли подходящий MOC, и добавить туда ссылку

### Папки
- Максимум 2 уровня вложенности
- Новую папку создавать только когда набралось 5+ заметок по теме
- Не создавать пустые папки заранее
